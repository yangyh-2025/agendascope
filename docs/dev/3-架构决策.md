## ADR-001: 模块化单体 API + 独立 worker 进程组，而非微服务

### 背景

系统由两类截然不同的负载构成：一类是面向分析师的交互式 API（看板查询、规则配置、人工确认/否决），QPS 低（估算 <50）但要求低延迟与事务一致性；另一类是重计算的后台管线（采集 → 正文抽取 → NLP 向量化 → 聚类 → LLM 标注），吞吐约 2.2 万篇文章/天（估算）、CPU/内存密集且允许异步。交付形态被 D-005 锁死为**单机 Docker Compose 私有化离线内网部署**，客户侧无人运维，目标是 8C16G + 可选 24GB GPU 的单台服务器（估算）跑全部组件。开发团队假定仅 1 后端 + 1 前端 + 0.5 NLP 顾问。

### 决策

**选择模块化单体 API 服务 + 独立 worker 进程组**（collector / extractor / nlp_pipeline / agenda_engine / llm_service / alerting 作为独立进程，api_server 为模块化单体），进程间用 Redis Streams 解耦，单机 Docker Compose 编排。

### 方案对比

| 维度 | 模块化单体 + worker（选择） | 微服务 | 纯单体（单进程内跑管线） |
|------|--------------------------|--------|------------------------|
| 部署复杂度（单机 Compose） | ★★★★★ | ★★☆☆☆（服务发现/网关/配置中心） | ★★★★★ |
| 重计算与 API 隔离 | ★★★★☆（进程级隔离，可独立扩 worker 副本数） | ★★★★★ | ★★☆☆☆（LLM 推理可拖垮 API） |
| 团队规模匹配（1 后端） | ★★★★★ | ★★☆☆☆ | ★★★★☆ |
| 水平扩展粒度 | ★★★★☆（worker 按类型加副本） | ★★★★★ | ★☆☆☆☆ |
| 故障域 | ★★★★☆（worker 挂不影响 API 读） | ★★★☆☆（级联失败面大） | ★★☆☆☆ |
| 数据一致性 | ★★★★★（共享 PostgreSQL，单库事务） | ★★★☆☆（分布式事务/最终一致） | ★★★★★ |

### 方案详述

#### 方案 A: 模块化单体 API + 独立 worker 进程组 — ✅ 选择

- **优势**: 1. 业务代码为单一 Python 包（FastAPI 应用 + 共享领域模型），worker 与 API 复用同一套 ORM/配置/日志设施，无跨服务契约维护成本；2. 计算密集任务（NLP、LLM、聚类）以独立进程运行，通过 Redis Streams 消费，可用 `--scale worker-nlp=2` 独立扩容，LLM 推理抖动不会拖慢 API 响应；3. 单一 PostgreSQL 提供 ACID，自我纠错的"归并 + revision_log 写入 + 置信度更新"可在单事务内完成；4. Docker Compose 单机即可表达全部拓扑，符合客户零运维前提。
- **劣势**: 1. 模块边界靠纪律维持（import 约束 + 分层检查），长期有腐化风险；2. API 进程与 worker 共享数据库连接池，需限流保护；3. 吞吐若增长 10 倍以上需重新拆分。
- **适用场景**: 中小吞吐（日文章数万级）、单机交付、小团队——本项目全部命中。

#### 方案 B: 微服务

- **优势**: 1. 服务独立扩缩容与发布；2. 技术栈可异构。
- **劣势**: 1. 需要服务发现、API 网关、分布式追踪等基础设施，单机离线内网部署包体积与复杂度爆炸；2. 客户侧无人有能力运维 10+ 个进程；3. 1 名后端无法维护。
- **放弃原因**: 与 D-005"单机、离线、零运维"硬约束直接冲突；吞吐规模（估算百级 QPS 以内）远未到需要微服务的程度。

#### 方案 C: 纯单体（管线在 API 进程内跑）

- **优势**: 1. 部署最简；2. 无消息队列依赖。
- **劣势**: 1. LLM/聚类的 CPU 尖峰会直接拖慢 API P95，威胁"看板可用"体验；2. 无法按负载类型独立扩缩。
- **放弃原因**: NLP/LLM 管线资源消耗与交互式 API 的 SLO 冲突不可调和，进程级隔离是底线要求。

### 影响

- **正面影响**: 部署拓扑简化为 `api_server + collector + extractor + nlp_worker + agenda_engine + llm_service + alerting + PostgreSQL + Elasticsearch + Redis` 十个左右容器，Compose 一键拉起；自我纠错的多步写操作保持单库事务。
- **负面影响**: 模块边界需 CI 静态检查（如 import-linter）守护；数据库成为天然单点（见 1-技术方案.md 非功能方案的备份/RTO 设计）。
- **波及范围**: 全部 8 个模块（collector / extractor / nlp_pipeline / agenda_engine / llm_service / api_server / frontend / alerting）；2-详细设计.md 的模块划分与本 ADR 一致。

### 后续动作

- [ ] 在 CI 中引入 import-linter，固化"api_server 不得 import worker 内部实现、共享代码只能放 shared 包"的边界
- [ ] 为每个 worker 类型定义独立的 Docker Compose service 与资源限制（mem_limit / cpus）
- [ ] 定义 worker 与 api_server 共享的 `shared/` 包清单（ORM 模型、配置、日志、常量）

## ADR-002: PostgreSQL + pgvector + Elasticsearch 存储组合，而非 MongoDB + 独立向量库

### 背景

系统有四类存储需求：1. 结构化业务数据（users / sources / collection_jobs / articles / topics / topic_articles / agenda_events / agenda_event_evidence / persons_orgs / alert_rules / alerts / report_exports），其中 topics 与 agenda_events 存在强关联与事务性更新（归并、revision_log 追加、置信度升降）；2. 向量数据（文章/议题的 768 维跨语言 embedding，paraphrase-multilingual-mpnet-base-v2），用于次日归并比对与增量归簇；3. 文章全文检索（分析师按关键词检索百万级文章，估算年增 800 万条）；4. 流式队列与缓存（已由 ADR-003 的 Redis 覆盖）。借鉴对象 IIS 使用 MongoDB + 独立向量库进程（HTTP 调用），需要评估是否照搬。部署约束仍为单机 Compose、离线内网、零运维。

### 决策

**选择 PostgreSQL 16（主库，含 pgvector 扩展存向量）+ Elasticsearch 8（全文检索）+ Redis 7（Streams + 缓存）**，不引入 MongoDB 与独立向量数据库进程。

### 方案对比

| 维度 | PostgreSQL 16 + pgvector（选择） | MongoDB（IIS 方案） | PostgreSQL + 独立向量库（Qdrant/Milvus） |
|------|-------------------------------|--------------------|---------------------------------------|
| 事务与关联（归并/留痕多表写） | ★★★★★ | ★★★☆☆（多文档事务成本高） | ★★★★☆（向量侧无事务） |
| JSONB 灵活性（revision_log） | ★★★★★ | ★★★★★ | ★★★★★ |
| 向量检索能力 | ★★★★☆（HNSW 索引，百万级足够） | ★☆☆☆（需外挂） | ★★★★★ |
| 单机进程数/运维面 | ★★★★★（向量与主库同进程） | ★★★☆☆ | ★★★☆☆（多一个有状态服务） |
| 数据一致性（向量与元数据同事务） | ★★★★★ | ★★☆☆☆ | ★★☆☆☆（双写问题） |
| 离线打包复杂度 | ★★★★★ | ★★★★☆ | ★★★☆☆ |

### 方案详述

#### 方案 A: PostgreSQL 16 + pgvector + Elasticsearch 8 — ✅ 选择

- **优势**: 1. pgvector 使向量与业务行同库同表（articles.embedding / topics.centroid_embedding），次日归并的"查历史议题向量 + 更新 topic_id 归属 + 追加 revision_log"可在**单事务**内完成，消除向量库与主库双写不一致问题；2. 百万级向量规模下 pgvector HNSW 召回与延迟足够（向量总量估算：年 800 万文章 + 数万议题质心，远低于 pgvector 的舒适区上限）；3. JSONB 完美承载 revision_log（修正前/后值、触发证据、模型与 prompt 版本）与 sources 的弹性字段；4. 少一个有状态进程 = 离线安装包更小、备份策略更统一（pg_basebackup 一套）；5. Elasticsearch 专职全文检索与聚合分析，职责单一。
- **劣势**: 1. 向量规模到千万级以上时 pgvector 性能弱于专用向量库；2. ES 与 PG 之间仍需同步管线（文章双写），存在短暂不一致窗口。
- **适用场景**: 向量百万级、强事务一致性要求、单机部署——本项目全部命中。

#### 方案 B: MongoDB（IIS 采用）

- **优势**: 1. 文档模型对异构文章元数据友好；2. IIS 已验证可行。
- **劣势**: 1. 无原生向量检索，仍需外挂向量库，存储组件反而更多；2. 自我纠错的核心操作（议题归并跨 topics/topic_articles/agenda_events 三表 + revision_log 追加）本质是关系型多写事务，MongoDB 多文档事务代价高；3. 团队 SQL 生态更熟。
- **放弃原因**: 本项目的写路径以"多实体关联更新 + 留痕"为主，与文档数据库的强项错配；且不解决向量存储问题，组件总数不降反升。

#### 方案 C: PostgreSQL + 独立向量库（Qdrant / Milvus / IIS 式独立向量进程）

- **优势**: 1. 向量检索性能上限更高；2. 向量库可独立扩缩。
- **劣势**: 1. 单机离线部署增加一个有状态服务，内存与备份成本上升（IIS 调研报告明确指出"向量库独立进程 HTTP 调用性能上限"且属"不宜照搬"项）；2. 向量与元数据双写引入一致性窗口，归并/回滚操作需补偿逻辑。
- **放弃原因**: 当前向量规模（估算百万级）远未到 pgvector 瓶颈，为不存在的规模付出运维复杂度不划算；保留迁移可能（向量访问收敛在 repository 层）。

### 影响

- **正面影响**: 12 张核心表 + 向量全部落 PostgreSQL，DDL 可直接进 Alembic migration；自我纠错事务化；备份 = pg_dump + ES snapshot 两套即可。
- **负面影响**: 需维护 articles → ES 的同步任务与失败重放；pgvector 索引占用内存需纳入资源预估（估算百万向量 HNSW 约数 GB）。
- **波及范围**: 存储层全部模块；2-详细设计.md 的 DDL、缓存策略、ES 同步时序图。

### 后续动作

- [ ] 编写 Alembic 初始 migration（12 张核心表 + `CREATE EXTENSION vector`）
- [ ] 向量访问封装进 repository 层接口，屏蔽 pgvector 语法细节，为将来迁移专用向量库留口
- [ ] 压测 pgvector HNSW 在 100 万 / 800 万向量下的召回率与 P95 延迟（估算目标：召回 ≥95%，P95 ≤50ms）
- [ ] 定义 articles → ES 双写的失败重放队列（Redis Streams 死信流）

## ADR-003: Redis Streams + Celery 任务调度，而非 Kafka

### 背景

采集 → 抽取 → NLP → 聚类 → 议程判定是多级异步管线，需要一个支撑"生产者-消费者组 + 积压可见 + 失败重试"的消息层。同时系统还需要去重缓存（URL 哈希、标题向量判重）与热点数据缓存。吞吐估算：日 2.2 万篇文章、峰值数百条/分钟，百级 QPS 以内（估算）。单机 Docker Compose 部署（ADR-001），客户零运维。调研报告 2 §8 明确建议"中小规模用 celery + Redis Streams 即可，不必一开始上 Kafka"（对应 PM 决策 D-004）。

### 决策

**选择 Redis 7 Streams + Celery** 作为任务调度与事件流方案，不上 Kafka。Redis 同时承担去重缓存与业务缓存，一举两用。

### 方案对比

| 维度 | Redis Streams + Celery（选择） | Kafka | RabbitMQ |
|------|------------------------------|-------|----------|
| 吞吐能力 | ★★★★☆（万级 msg/s，远超需求） | ★★★★★ | ★★★★☆ |
| 单机资源占用 | ★★★★★（内存百 MB 级） | ★★☆☆☆（JVM + ZooKeeper/KRaft，GB 级） | ★★★★☆ |
| 运维复杂度（客户零运维） | ★★★★★ | ★★☆☆☆ | ★★★★☆ |
| 消费者组/重放/死信 | ★★★★☆（XREADGROUP/XPENDING/XAUTOCLAIM） | ★★★★★ | ★★★★☆ |
| 与 Celery 生态契合 | ★★★★★ | ★★☆☆☆ | ★★★★★ |
| 复用（去重缓存/业务缓存同组件） | ★★★★★ | ★☆☆☆☆ | ★☆☆☆☆ |

### 方案详述

#### 方案 A: Redis Streams + Celery — ✅ 选择

- **优势**: 1. Redis 本就是缓存与去重的必选组件，消息层复用同一进程，部署拓扑不增加任何新组件；2. Streams 的消费者组（XREADGROUP）、待确认列表（XPENDING）、自动认领（XAUTOCLAIM）完整覆盖"worker 崩溃后消息不丢、积压可监控（XLEN 超阈值 10,000 触发扩容告警）"的需求；3. Celery 提供定时任务（每小时全局重聚类、每日归并、24h 黑名单统计）与重试策略的成熟实现；4. 内存占用与运维成本对 8C16G 单机（估算）友好。
- **劣势**: 1. 消息持久化依赖 Redis AOF，极端断电场景可靠性弱于 Kafka；2. 无跨机器分区扩展能力；3. Redis 许可证（RSALv2/SSPL）需跟踪（PM 风险 L3）。
- **适用场景**: 日消息十万级、单机部署、已引入 Redis 的系统——本项目全部命中。

#### 方案 B: Kafka

- **优势**: 1. 吞吐与生态最强；2. 消息多副本持久化，重放能力最好。
- **劣势**: 1. JVM 堆 + 页缓存需求在 8C16G 单机上与 ES/PG 抢资源；2. 客户侧无人具备 Kafka 运维能力，私有化交付"零运维"前提被破坏；3. 为百级 QPS（估算）引入 Kafka 属于过度设计。
- **放弃原因**: 与单机离线交付形态直接冲突，规模完全不匹配。

#### 方案 C: RabbitMQ

- **优势**: 1. 成熟稳定，Celery 官方支持最好。
- **劣势**: 1. 调研中无优势论据；2. 增加一个独立中间件，却无法像 Redis 那样复用为缓存/去重存储。
- **放弃原因**: 组件复用度为零，违背单机最小化组件原则。

### 影响

- **正面影响**: 部署组件锁定为 PostgreSQL + Elasticsearch + Redis 三个有状态服务；积压指标（XLEN）直接接入监控看板，与"先入库后聚类"降级策略联动（积压 >10,000 持续 10 min 自动扩 worker 并降级，PRD §4.2 异常流程）。
- **负面影响**: 消息可靠性依赖 Redis AOF 配置（appendfsync everysec）；极端场景可能丢失秒级消息，需以"采集任务可重放（collection_jobs 记录游标）"兜底。
- **波及范围**: collector / extractor / nlp_pipeline / agenda_engine / alerting 全部异步链路；2-详细设计.md 的时序图与降级分支。

### 后续动作

- [ ] 定义 Streams 拓扑：`stream:articles.raw → stream:articles.extracted → stream:articles.embedded → stream:topics.events` 及各自消费者组与死信流命名
- [ ] 配置 Redis AOF everysec + 最大内存策略，编写积压（XLEN）与 PEL 老化（XPENDING）监控指标
- [ ] 在 Celery 层实现统一重试策略（指数退避，最大 5 次（估算）后进死信流）
- [ ] 跟踪 Redis 许可证动态，评估 Valkey 替代预案（不重评估不行动）

## ADR-004: 本地 LLM（Qwen 系列）推理，而非云端 API

### 背景

议题命名、主题分类、重复议题归并、摘要、首发表述判定、终审审查官（1-10 分评分，<5 降级）等 NLP 环节若用传统方法需逐任务建模与标注，工程量不可承受（对应 PM 决策 D-006）。LLM 以提示词策略即可覆盖全部任务。但目标场景是国家安全机关与涉密研究机构的**完全离线内网**：数据不出用户服务器、不出境是不可谈判的硬约束（PRD 第六章 NFR），云端商用 API 默认不可用，仅"经机构批准的 API"可作为例外。客户硬件估算为 1×24GB 显存 GPU 或 64GB 内存 CPU 量化推理档。

### 决策

**选择本地部署开源 LLM（Qwen 系列）做全部议题管线任务**，推理服务（llm_service）独立进程，LLM 调用走异步批处理队列不阻塞采集与告警主链路；保留完整降级链：LLM 不可用 → BERTopic c-TF-IDF 关键词标签 → 关键词匹配。

### 方案对比

| 维度 | 本地 Qwen（选择） | 云端商用 API（GPT 等） | 纯传统 NLP（c-TF-IDF + 规则） | 自训小模型逐任务建模 |
|------|------------------|------------------------------|------------------------------|---------------------|
| 数据不出境/保密 | ★★★★★ | ★☆☆☆☆（默认违规） | ★★★★★ | ★★★★★ |
| 多任务覆盖成本 | ★★★★★（提示词即任务） | ★★★★★ | ★★☆☆☆ | ★☆☆☆☆ |
| 输出可读性（议题命名/摘要） | ★★★★☆ | ★★★★★ | ★★☆☆☆ | ★★★☆☆ |
| 离线内网可运行 | ★★★★★ | ★☆☆☆☆ | ★★★★★ | ★★★★☆ |
| 推理时延/吞吐（低算力） | ★★★☆☆ | ★★★★★ | ★★★★★ | ★★★★★ |
| 工程量 | ★★★★☆ | ★★★★★ | ★★★☆☆ | ★☆☆☆☆ |

### 方案详述

#### 方案 A: 本地 Qwen 系列 — ✅ 选择

- **优势**: 1. 模型权重随离线安装包分发，断网可运行，满足 L4 保密审查的"组件来源可控、支持断网验收"要求；2. Qwen 系列中英双语与多语种能力在开源模型中第一梯队，24GB 显存可跑中档尺寸量化版本（估算），CPU 量化（GGUF/llama.cpp 或类似框架）可作无 GPU 档兜底；3. 提示词即任务，议题命名/分类/归并/首发判定/终审共用同一推理服务，工程面收敛为"prompt 模板 + 结构化输出校验 + 版本留痕"；4. 每次调用记录模型名与 prompt 版本（写入 revision_log），支持换 prompt 后重跑对比（借鉴 IIS 的留痕设计）。
- **劣势**: 1. 低算力下时延与吞吐是真实风险（PM 风险 T6）——议题标注 P95 时延可能超 10 分钟（估算）；2. 低资源语言的命名/归并质量需逐任务评估集验证；3. 引入 GPU 可选硬件，安装包体积增大（权重数 GB 级）。
- **适用场景**: 保密内网、可异步批处理的 NLP 标注类任务。

#### 方案 B: 云端商用 LLM API

- **优势**: 1. 效果上限最高；2. 无本地硬件要求。
- **劣势**: 1. 数据出网，违反保密硬约束——对国家安全机关客户是"一票否决"；2. 离线内网物理不可达；3. 按 token 计费与私有化授权模式不匹配。
- **放弃原因**: 数据不出境是不可谈判前置条件；仅保留"经机构批准的 API"为配置级例外（默认关闭，安装向导明示）。

#### 方案 C: 纯传统 NLP（c-TF-IDF + 规则）

- **优势**: 1. 零 LLM 依赖，速度最快，无 GPU 需求；2. 行为完全确定可复现。
- **劣势**: 1. 议题命名退化为关键词堆砌，首发表述判定（判断"某表述是否首次提出"）几乎无法用规则做；2. US-06 议程溯源的可信度直接受损。
- **放弃原因**: 产品质量不达标，但**保留为降级链的末端兜底**（LLM 与聚类均不可用时系统降级而非瘫痪）。

#### 方案 D: 自训小模型逐任务建模

- **优势**: 1. 推理快、无 LLM 依赖。
- **劣势**: 1. 每个任务需标注数据与训练管线，0.5 个 NLP 顾问的配置下完全不可行；2. 多语言（含全球南方语言）标注数据不可得。
- **放弃原因**: 工程量与团队规模严重不匹配。

### 影响

- **正面影响**: NLP 工程简化为"聚类 + LLM 标注"两段式；US-04 / US-06 / US-15 / US-16 的语义判定能力全部由其支撑；降级链保证可用性红线（P95 ≤30min 可见性不被 LLM 时延绑架——LLM 标注异步补齐）。
- **负面影响**: 部署包增大（模型权重）；安装向导必须前置硬件自检（不达标即中止，与 PM 风险 F2 联动）；每类 LLM 任务需建评估集并跑 baseline 验收。
- **波及范围**: llm_service、nlp_pipeline、agenda_engine（首发判定/终审）、离线打包（ADR-010）、安装向导。

### 后续动作

- [ ] 选型定版：在候选尺寸（估算 7B~32B 量化档）上跑议题命名/归并/首发判定评估集，确定默认模型与 CPU 量化档
- [ ] 定义 llm_service 的统一任务接口（task_type + prompt_version + 结构化 JSON 输出 schema 校验）
- [ ] 实现降级链开关与指标：LLM 调用失败率、标注 P95 时延 >10min（估算）告警
- [ ] 为每类任务建评估集，上线前 baseline 验收（命名/归并人工抽检合格率 ≥85%（估算））

## ADR-005: BERTopic + Agglomerative 硬阈值双聚类策略，而非纯 HDBSCAN

### 背景

聚类是议题发现的核心：30 国、100+ 语言的文章需映射到统一议题空间（跨国议程对比的硬需求，PM 决策 D-002 已定 BERTopic + 跨语言向量）。但 BERTopic 默认的 HDBSCAN 聚类在情报类实时流场景有已验证的实战教训——IIS（调研报告3）明确记录：弃用 HDBSCAN 的原因是**超大簇黑洞**（热点大事件吸附一切相关报道）、**实体引力过载**（高频实体把不同议题黏在一起）、**孤证被当噪声丢弃**（而首发单源报道正是议程设置萌芽的最重要信号）。IIS 改用 Agglomerative 硬距离阈值（cosine distance_threshold=0.25，average linkage，估算）并保留 size=1 微簇。此外系统还需"在线增量归簇 + 定期全局校正"两层机制（IIS：在线双阈值 T_event=0.85 / T_dup=0.95 + 每小时全量重聚类 24h 窗，均为估算）。

### 决策

**选择 BERTopic 框架 + Agglomerative 硬阈值（cosine 0.25，average linkage，估算）的双聚类策略**：BERTopic 负责议题建模与 c-TF-IDF 表征/降级标签，Agglomerative 硬阈值负责实时流的议题归属判定；孤证保留为 size=1 微簇（对应议题生命周期"萌芽"态）；在线增量双阈值（T_event=0.85 归簇 / T_dup=0.95 判重，估算）+ 每小时全局重聚类校正（估算）；配套动态高频实体黑名单（24h 统计近 30 天 Top-50，估算）防超级节点污染。

### 方案对比

| 维度 | BERTopic + Agglomerative 双策略（选择） | 纯 HDBSCAN（BERTopic 默认） | LDA | 全文翻译后单语聚类 |
|------|--------------------------------------|---------------------------|-----|-------------------|
| 超大簇/黑洞控制 | ★★★★★（硬阈值封顶簇直径） | ★★☆☆☆（IIS 实战教训） | ★★★☆☆ | ★★☆☆☆ |
| 孤证（首发萌芽）保留 | ★★★★★（size=1 微簇） | ★☆☆☆☆（噪声点丢弃） | ★★☆☆☆ | ★★☆☆☆ |
| 跨国统一议题空间 | ★★★★★（跨语言向量） | ★★★★☆ | ★☆☆☆☆ | ★★★☆☆（翻译误差） |
| 增量/在线能力 | ★★★★☆（双阈值增量 + 定期校正） | ★★★☆☆ | ★☆☆☆☆ | ★★★☆☆ |
| 学术认可度 | ★★★★☆ | ★★★★☆ | ★★★☆☆（传统） | ★★☆☆☆ |

### 方案详述

#### 方案 A: BERTopic + Agglomerative 硬阈值双策略 — ✅ 选择

- **优势**: 1. 硬距离阈值从机制上杜绝超大簇——簇内任意点与质心距离超阈值即不并入，热点大事件无法吸附一切；2. size=1 微簇保留孤证，首发单源报道进入"萌芽"议题而非噪声池，直接支撑 US-16 的议题萌芽检测与 US-06 的首发源识别；3. 动态实体黑名单（Top-50 高频实体，估算）削弱实体引力，防止"某大国领导人"这类超级节点把不同议题黏合；4. 在线双阈值 + 每小时全局重聚类校正，兼顾实时性（秒级归簇）与误差纠偏（定期重算）；5. BERTopic 的 c-TF-IDF 同时是 LLM 降级链的中间层。
- **劣势**: 1. 双策略叠加参数多（0.25 阈值、0.85/0.95 双阈值、重聚类窗口，均估算），调参复杂；2. 每小时全局重聚类期间需快照隔离（前端读上一版并标注"校正中"）；3. Agglomerative 全量重算在大数据量下成本高（需限制在 24h 滚动窗）。
- **适用场景**: 实时新闻流、首发信号敏感、跨国多语言——本项目全部命中。

#### 方案 B: 纯 HDBSCAN

- **优势**: 1. BERTopic 默认集成，工程量最小；2. 密度自适应，无需预设簇数。
- **劣势**: 1. IIS 实战教训三宗罪：超大簇黑洞、实体引力过载、孤证丢弃；2. 噪声点丢弃机制与"首发萌芽必须保留"的产品需求根本冲突；3. 增量模式下漂移明显。
- **放弃原因**: 孤证被当噪声这一条就直接摧毁 US-16"萌芽→形成中"生命周期与 US-06 首发识别——属方向性错误而非调参可解。

#### 方案 C: LDA

- **优势**: 1. 学术文献沿用多；2. 结果可解释。
- **劣势**: 1. 需逐语种分词、预设话题数，无法支撑 30 国多语言统一议题空间；2. 无增量模式。
- **放弃原因**: PM D-002 已否，多语言能力不满足跨国统一议题空间硬需求。

#### 方案 D: 全文翻译为英文后单语聚类

- **优势**: 1. 聚类只面对单语言，质量稳定。
- **劣势**: 1. 100+ 语言离线翻译成本高且引入翻译误差；2. 调研报告 2 §5 明确"跨语言聚类优先用 embedding，翻译只用于展示"。
- **放弃原因**: 翻译误差会污染首发判定与归并比对，得不偿失。

### 影响

- **正面影响**: 议题萌芽（孤证微簇）成为一等公民，与生命周期状态机（ADR-006）无缝衔接；超大簇黑洞从机制上消除；误并/误拆率可监控（PM 新增监控指标）。
- **负面影响**: 调参与评估集建设工作量大；重聚类校正引入读写快照管理复杂度；阈值均为估算值，需在历史案例回放（新疆棉等）上标定。
- **波及范围**: nlp_pipeline、agenda_engine；2-详细设计.md 的聚类伪代码与时序图；4-开发计划.md 的回放测试（次日归并正确率 ≥90%（估算））。

### 后续动作

- [ ] 在历史案例集（新疆棉等）上标定 cosine 0.25 / T_event 0.85 / T_dup 0.95 阈值，记录标定过程与最终值
- [ ] 实现重聚类校正的快照读写隔离（读旧版快照 + "校正中"标注，不产生读写不一致）
- [ ] 实现动态高频实体黑名单任务（24h 周期，近 30 天 Top-50（估算），黑名单实体不参与簇归属特征）
- [ ] 建立误并/误拆率监控指标与抽样人工评估流程（话题一致率 ≥80%（估算））

## ADR-006: 回声消除 + topic_id 复用的自我纠错机制设计

### 背景

实时流上的聚类与 LLM 判定必然出错：首发源误判、议题误并/误拆是概率必然而非边缘情况；且一个新议程常"首日仅零星报道、次日才成形"。若识别结果不能随证据自动修正，议题图谱错误持续累积，"新疆棉"类关键案例的证据链可能建立在错误首发源上，直接摧毁 US-06 可信度（PM D-007 论证）。借鉴对象 IIS 提供了三件核心武器但均为半成品：**回声消除**（同日相似度 ≥0.65 / 3 日内 ≥0.85 折叠为同一节点，跟风报道进 related_docs 且保留全部来源）、**主题档案合并**（新种子与历史议题向量比对，相似则 merge 复用 topic_id，其 writeback 是 TODO）、**LLM 终审**（审查官 1-10 分，<5 REJECTED）。本平台需自行落地并超越——增加 IIS 没有的分裂与消亡机制（对应 US-16，P0）。

### 决策

**选择"回声消除 + topic_id 复用 + 增量重估 + revision_log 全程留痕"的自我纠错架构**，具体机制：

1. **回声消除折叠**：同日相似度 ≥0.65 / 3 日内 ≥0.85 的报道折叠为同一议题节点，跟风报道不进传播图但实体被吸收、全部来源保留（首发源判定的数据基础）。
2. **议题生命周期状态机**：萌芽（孤证微簇）→ 形成中 → 已确认 → 演化（合并/分裂）→ 消亡（连续 N 天无新报道自动归档，N=7（估算））。
3. **次日自动归并**：新议题先与历史议题做跨语言向量比对，相似度 ≥0.85（估算）则并入旧议题（topic_id 复用），否则开新议题。
4. **首发源判定与自动修正**：节点内最早 TIME_PUB + 人物首发检测；新证据（更早报道、新来源）出现时自动重跑判定，判定变化写入 revision_log（修正前/后值、触发证据、模型与 prompt 版本）。
5. **置信度自动升降**：AgendaEvent 状态机 watching → suspected → confirmed / dismissed / revised / archived，随证据自动流转。
6. **人工否决优先**：分析师确认/否决每条自动修正；否决即回滚并记为新 revision_log；机器永不推翻人工结论；误并可一键拆分回滚并写入"不可归并"名单。
7. **防修正风暴**：单议题 24h 内修正 >5 次（估算）冻结自动修正，转人工复核队列。
8. **LLM 终审审查官**：议程设置事件判定经 LLM 审查官 1-10 分评分，<5 分自动降级为疑似/驳回。

### 方案对比

| 维度 | 自动纠错 + 留痕 + 人工否决（选择） | 纯人工整理修正 | 纯在线增量、无校正（IIS 现状） | 识别后不可变（只读快照） |
|------|----------------------------------|---------------|------------------------------|------------------------|
| 错误累积控制 | ★★★★★ | ★★★★☆（质量高但滞后） | ★★☆☆☆（只增不减、只合不分） | ★☆☆☆☆ |
| 次日成形议程的处理 | ★★★★★（次日归并 topic_id 复用） | ★★★☆☆ | ★★☆☆☆ | ★☆☆☆☆ |
| 可审计/可回滚 | ★★★★★（revision_log 全留痕） | ★★★☆☆ | ★★☆☆☆ | ★★☆☆☆ |
| 人力可扩展性 | ★★★★★ | ★☆☆☆☆（30 国日增数千条） | ★★★★★ | ★★★★★ |
| 实现复杂度 | ★★☆☆☆ | ★★★★★ | ★★★★★ | ★★★★★ |
| 误判污染风险 | ★★★☆☆（T7，靠否决+回滚+监控缓解） | ★★★★☆ | ★★☆☆☆ | ★★★☆☆ |

### 方案详述

#### 方案 A: 自动纠错 + 留痕 + 人工否决 — ✅ 选择

- **优势**: 1. 回声消除保证传播链路图不被转载洪水淹没，同时来源全保留使首发判定与跨国跟随序列可计算；2. topic_id 复用让议题跨天连续演化，解决"今日零星、明日成形"的滞后——这是 US-16 的核心价值；3. revision_log 使每次自动修正可审计、可回滚，满足安全场景的问责要求；4. 人工否决优先 + 修正风暴冻结，把机器的自治权限制在可回滚范围内；5. 超越 IIS：补齐其未完成的合并/分裂回写，并新增分裂与消亡机制。
- **劣势**: 1. 实现复杂度高——归并/拆分涉及 topics / topic_articles / agenda_events / agenda_event_evidence 多表事务与向量质心重算；2. 误并会污染议题图谱（PM 风险 T7），需误并率监控（>5%（估算）触发重评估）；3. 重聚类校正与归并的并发需快照隔离。
- **适用场景**: 实时监测 + 结果需持续演化 + 审计要求高的情报分析系统。

#### 方案 B: 纯人工定期整理

- **优势**: 1. 质量最高；2. 无自动误并风险。
- **劣势**: 1. 30 国数百源日增数千条报道（估算），人工周期以周计，实时监测价值归零；2. 人力不可扩展。
- **放弃原因**: PM D-007 已否——业务节奏（实时、次日成形）根本不允许人工回路。

#### 方案 C: 纯在线增量聚类、无全局校正与生命周期（IIS 现状）

- **优势**: 1. 实现最简；2. 实时性好。
- **劣势**: 1. 增量归簇误差随时间累积；2. 议题只增不减、只合不分，图谱逐渐失真（IIS 即止步于此，writeback 为 TODO）。
- **放弃原因**: 无消亡机制导致议题无限膨胀，无分裂机制导致误并无解，不满足 US-16。

#### 方案 D: 识别后不可变（只读快照）

- **优势**: 1. 最简单、无并发问题。
- **劣势**: 1. 误判永久存在，证据链可信度归零。
- **放弃原因**: 与产品差异化根基（US-06 可信度）直接冲突。

### 影响

- **正面影响**: US-06 与 US-16 边界清晰落地（一个管识别、一个管演化纠错）；AgendaEvent 的 watching/suspected/confirmed/dismissed/revised/archived 状态机与 Topic 的 lifecycle_state/confidence/merged_into/last_seen_at 字段在数据模型层固化；分析师信任度靠"留痕 + 否决 + 回滚"三件套建立。
- **负面影响**: 数据模型与事务复杂度显著上升；需防误并污染（"不可归并"名单、误并率监控、风暴冻结）；回放测试成本高（次日归并正确率 ≥90%、首发修正留痕率 100%，均估算目标）。
- **波及范围**: agenda_engine（核心）、nlp_pipeline、llm_service（终审）、api_server（修正历史/确认/否决 API）、frontend（"该判定已于 X 时修正"标注、复核队列）。

### 后续动作

- [ ] 实现归并/拆分多表事务与议题质心向量重算逻辑（单 PostgreSQL 事务，依赖 ADR-002）
- [ ] 实现 revision_log JSONB schema（修正前后值、触发证据 article_ids、model_name、prompt_version、created_at、actor=system/user）
- [ ] 实现"不可归并"名单与修正风暴冻结（24h >5 次（估算））
- [ ] 历史案例回放测试集建设（新疆棉等）：首发源判定准确率 ≥85%、次日归并正确率 ≥90%（估算目标）
- [ ] LLM 终审审查官 prompt 与评分校准规则（借鉴 IIS 评分自我校准：回顾类压分、高相似低新颖惩罚）

## ADR-007: 自研 React 18 + TypeScript + Apache ECharts 前端，而非 Metabase/Superset

### 背景

产品差异化视图有四个：全球议程地图（藏蓝深色底 + 离线瓦片）、议程时间线、议题网络图（NAS 议题-属性关联网络可视化）、跨国传播链路图（首发源 → 跟随国序列 + 时滞）。另有红蓝视觉规范（藏蓝 #0B2A5B 深色底、主蓝 #1D4E9E、中国红 #C8102E 预警高亮）的硬设计要求。目标用户零编程基础——通用 BI 的查询构建器本身就是门槛（PM 决策 D-003）。调研报告 2 §7 结论：Metabase 对非技术用户最友好，但上述四类专属视图通用 BI 无法实现，"若要定制专属视图，自研 React + ECharts 是必经之路"。

### 决策

**选择自研 React 18 + TypeScript + Apache ECharts（Apache-2.0）前端**，深色主题，不采用 Metabase/Superset/Grafana 拼装。Metabase 仅允许作内部运营数据核查，不进交付包。

### 方案对比

| 维度 | React + ECharts 自研（选择） | Metabase 嵌入 | Superset | Grafana |
|------|---------------------------|---------------|----------|---------|
| 专属视图能力（地图/NAS 网络图/链路图/时间线） | ★★★★★ | ★☆☆☆☆ | ★★☆☆☆ | ★☆☆☆☆ |
| 小白用户可用性（≤3 步/≤10 分钟） | ★★★★★ | ★★☆☆☆（查询构建器是门槛） | ★★☆☆☆ | ★★☆☆☆ |
| 许可证（私有化商业分发） | ★★★★★（ECharts Apache-2.0） | ★★☆☆☆（AGPL 不友好） | ★★★★☆ | ★★★☆☆（AGPL） |
| 红蓝视觉规范落地 | ★★★★★ | ★★☆☆☆ | ★★★☆☆ | ★★★☆☆ |
| 开发工期 | ★★☆☆☆（估算 +6~8 周） | ★★★★★ | ★★★★☆ | ★★★★★ |
| 离线内网适配（离线瓦片/无 CDN） | ★★★★★ | ★★★☆☆ | ★★★☆☆ | ★★★☆☆ |

### 方案详述

#### 方案 A: React 18 + TypeScript + ECharts — ✅ 选择

- **优势**: 1. 四大专属视图（地图/时间线/NAS 网络图/传播链路图）完全自主可控，ECharts 的 graph/geo/lines 系列直接支撑网络图与跨国流向图；2. 红蓝视觉规范（#0B2A5B / #1D4E9E / #C8102E）与深色主题可精确落地，预警与议程设置事件用中国红高亮；3. 许可证干净（Apache-2.0，无传染性），满足 L4 保密审查的组件清单要求；4. 静态构建产物可完全离线分发，配合离线地图瓦片无外部依赖；5. TypeScript 与 `/api/v1` 统一响应 `{code, data, message}` 契约类型化对接。
- **劣势**: 1. 工期增加（估算 +6~8 周，已纳入 4-开发计划.md Phase 4）；2. 需自研图表交互细节（缩放、下钻、快照导出）；3. worldmonitor 等开源仪表盘可参考不可照搬。
- **适用场景**: 专属可视化是产品差异化核心、用户零技术基础——本项目全部命中。

#### 方案 B: Metabase 嵌入

- **优势**: 1. 快速验证数据模型可用；2. 非技术用户友好度在 BI 中最高。
- **劣势**: 1. 地图/NAS 网络图/链路图三类核心视图缺失；2. AGPL 许可证对私有化商业分发不友好；3. 查询构建器对小白用户仍是门槛。
- **放弃原因**: 核心视图缺失是方向性不满足；仅保留为内部运营核查工具（与交付形态无关）。

#### 方案 C: Superset / Grafana

- **优势**: 1. Superset 可视化丰富度高；2. Grafana 时序面板成熟。
- **劣势**: 1. Superset 学习曲线更陡且无 NAS 网络图；2. Grafana 偏技术指标监控，业务分析弱；3. 均为 AGPL，许可证风险同 Metabase。
- **放弃原因**: 专属视图与许可证双重不满足。

### 影响

- **正面影响**: 四大专属视图成为差异化壁垒；视觉规范统一落地；离线打包无外部 CDN/字体依赖。
- **负面影响**: 前端工期为各 Phase 中最重之一（见 4-开发计划.md）；ECharts 大数据量网络图需性能优化（节点 >1000 时降级为聚合视图，估算）。
- **波及范围**: frontend 模块全部；api_server 的聚合查询 API 设计（看板接口为视图定制而非通用查询）。

### 后续动作

- [ ] 验证 ECharts 在 NAS 网络图（估算数百节点）与传播链路图上的性能基线

## ADR-008: RSS + GDELT 混合采集，而非纯爬虫

### 背景

需覆盖约 30 国主流新闻媒体（每国受众覆盖率 ≥70%，逐国标注置信度），硬指标为新闻发布 → 平台可见 P95 ≤30 分钟、红线 ≤2 小时。采集方案直接决定延迟、覆盖率、维护成本与合规风险（反爬、版权、GDPR cookie 墙）。调研报告 1 §2.5：RSS 轮询延迟分钟级到几十分钟、结构化、成本极低（Media Cloud 生产配置即每 5 分钟增量同步 feed）；GDELT DOC 2.0 免费、100+ 语言、15 分钟更新、免 key，最坏延迟 15-30 分钟正好兜住 2 小时红线；纯爬虫虽实时但 30 国数百源的 per-publisher 解析器维护成本不可承受（PM 决策 D-001）。

### 决策

**选择 RSS + GDELT 混合采集**：重点源 RSS 1-5 分钟高频轮询（feedparser）为主，GDELT DOC 2.0（15 分钟更新）做广度补充与兜底，RSSHub（自建实例）补无 RSS 的源，正文抽取用 trafilatura（readability-lxml 降级兜底）；不建大规模 HTML 爬虫体系。

### 方案对比

| 维度 | RSS + GDELT 混合（选择） | 纯爬虫（scrapy + fundus） | 商业新闻 API（Event Registry / Aylien） |
|------|------------------------|--------------------------|----------------------------------------|
| 延迟（P95 ≤30min） | ★★★★☆（RSS 分钟级 + GDELT 15min 兜底） | ★★★★★ | ★★★★☆ |
| 覆盖率（30 国 ≥70%） | ★★★★☆（RSSHub 补源 + GDELT 广度） | ★★★★☆ | ★★★★☆ |
| 维护成本（数百源） | ★★★★★ | ★☆☆☆☆（per-publisher 解析器） | ★★★★★ |
| 数据成本 | ★★★★★（≈0） | ★★★★☆ | ★☆☆☆☆（$70K+/年） |
| 合规风险（反爬/版权/GDPR） | ★★★★☆（RSS 为主规避） | ★★☆☆☆ | ★★★★★ |
| 离线内网适配 | ★★★★☆（外网采集单向导入/批准代理） | ★★★★☆ | ★★☆☆☆ |

### 方案详述

#### 方案 A: RSS + GDELT 混合 — ✅ 选择

- **优势**: 1. 采集层收敛为 feedparser + RSSHub + trafilatura 三件套，无解析器维护地狱；2. GDELT 兜底使任一源失效时覆盖率不滑坡（源健康看板 degraded → 自动切 GDELT 补该媒体），红线 ≤2h 有双保险；3. 数据成本 ≈0，符合私有化定价模型；4. 以 RSS/API 为主采集，合规风险低（PM 合规目标）；5. 采集与内网隔离清晰——外网采集通道可经部署方边界单向导入或经批准代理接入，分析与存储全在内网。
- **劣势**: 1. 依赖外部免费服务（GDELT 持续性、RSSHub 路由维护）——PM 风险 T1/T3；2. 部分源 RSS 摘要不全需抓正文，遇 GDPR cookie 墙需降级 GDELT 元数据；3. RSS 轮询频率过高可能被源站限流。
- **适用场景**: 主流媒体覆盖、分钟级延迟要求、小团队运维。

#### 方案 B: 纯爬虫（scrapy + fundus 按出版商定制）

- **优势**: 1. 抽取质量最高（Fundus F1 97.69，调研报告 1）；2. 延迟可控到秒级。
- **劣势**: 1. 30 国数百源的解析器开发+持续维护（页面改版即失效）远超 1 后端配置；2. 反爬对抗与 GDPR cookie 墙的合规风险高。
- **放弃原因**: 维护成本与团队规模严重不匹配；保留接口抽象，后续可为重点国家追加 per-publisher 爬虫（D-001 可逆性条款）。

#### 方案 C: 商业新闻 API

- **优势**: 1. 省心、质量好、合规清晰。
- **劣势**: 1. $70K+/年成本击穿私有化定价模型（授权 ¥5-20 万/家（估算））；2. 与"数据自有"卖点冲突；3. 离线内网场景需数据导入通道，架构更复杂。
- **放弃原因**: 成本与商业模式冲突。

#### 落地形态（v1.1 补充，详见 ADR-011）

本决策回答的是"源策略"（以 RSS 为主、GDELT 兜底、不建大规模 per-publisher 爬虫体系），采集层的**实现架构**由 ADR-011 定义：通用 RSS 采集器（承载约 80% 源（估算），每源一行配置而非每源一个代码文件）+ 配置驱动爬虫管线（无 RSS 长尾约 20% 源（估算），复刻 IIS 三段式设计与 ListPageDiscoverer 签名聚类，免手写 selector）+ 采集治理与告警（治理状态机 + 主动告警）。配置驱动管线不是"大规模 HTML 爬虫体系"——新增源零爬虫代码、配置存 DB，因此不违反本决策"维护成本可控"的前提；GDELT 兜底与 RSSHub 补源策略维持不变。

### 影响

- **正面影响**: 采集层工期显著缩短；延迟预算表（采集轮询 1-5min + 队列 + 抽取 + NLP + LLM + 索引 → P95 ≤30min）成立；源健康状态机（active/degraded/failed）+ 自动切换 GDELT 构成覆盖率保障闭环。
- **负面影响**: GDELT 与 RSS 双路去重合并逻辑（URL 哈希 + 标题向量相似度 >0.92 判转载）增加复杂度；需持续监控 GDELT 服务变更（重评估触发器：某重点国家 ≥30% 目标媒体无 RSS 且 RSSHub 无路由）。
- **波及范围**: collector、extractor；sources / collection_jobs / articles 表设计；源健康看板与告警（US-03）。

### 后续动作

- [ ] 搭建 RSSHub 自建实例并纳入离线部署包（AGPL-3.0，仅内网使用，纳入许可证清单）
- [ ] 实现双路去重合并（URL 哈希精确 + 标题向量 >0.92 转载判定，转载数计入显著性权重）
- [ ] 实现源健康状态机与 GDELT 自动补位、GDELT 恢复后 3 个月滚动窗口回补
- [ ] 建立 30 国媒体源种子库（覆盖率口径交集法，逐国置信度标注）

## ADR-009: JWT + RBAC 认证授权，而非 Session

### 背景

私有化实例内部账号体系（无 SaaS、无第三方登录），用户角色少而清晰：管理员（源/用户/备份管理）、分析师（看板/确认/否决/导出）、只读 Viewer（估算角色集，以 PRD 权限矩阵为准）。API 为 React SPA 调用的 `/api/v1` REST 接口，需无状态认证以支持多 tab 与 worker 内部服务间调用。等保 2.0 三级（估算目标）要求身份鉴别、访问控制、安全审计全量留痕（登录、查询、导出、配置变更——PM 风险 L4 的保密审计日志为标准功能）。

### 决策

**选择 JWT（access + refresh 双 token）+ RBAC 角色权限模型**：Base `/api/v1`，Header `Authorization: Bearer <JWT>`；access token 短有效期、refresh token 长有效期并支持服务端吊销（Redis 黑名单）；接口级权限校验；全部敏感操作写审计日志。

### 方案对比

| 维度 | JWT + RBAC（选择） | Session + Cookie | OAuth2.0 / OIDC 完整流程 |
|------|-------------------|------------------|--------------------------|
| 无状态/SPA 契合 | ★★★★★ | ★★★☆☆（CSRF 防护成本） | ★★★★☆ |
| 服务间调用（api_server ↔ llm_service） | ★★★★★（内部 token） | ★★☆☆☆ | ★★★★☆ |
| 吊销能力 | ★★★☆☆（需 Redis 黑名单） | ★★★★★ | ★★★★☆ |
| 实现复杂度 | ★★★★☆ | ★★★★☆ | ★★☆☆☆（无外部 IdP 场景过度） |
| 等保审计契合 | ★★★★☆ | ★★★★☆ | ★★★★☆ |
| 离线内网适配 | ★★★★★ | ★★★★★ | ★★☆☆☆（IdP 需自建） |

> **假定**: 角色集为 admin / analyst / viewer 三类；access token 有效期 30 分钟、refresh token 7 天（估算，实现时可按等保测评意见收紧）。

### 方案详述

#### 方案 A: JWT + RBAC — ✅ 选择

- **优势**: 1. 无状态认证与模块化单体 + SPA 架构天然契合，API 层无需会话存储；2. 同一套 token 机制可复用于 api_server → llm_service 的内部服务鉴权（内网仍需防横向移动）；3. RBAC 与等保"最小权限 + 角色分离"要求直接对应；4. refresh token 存 Redis 支持强制下线（管理员禁用账号即时生效）。
- **劣势**: 1. access token 吊销依赖短有效期 + Redis 黑名单折衷；2. 密钥管理需纳入部署向导（安装时生成随机密钥，不入镜像）。
- **适用场景**: 私有化 SPA + REST API、角色少而固定的机构内部系统。

#### 方案 B: Session + Cookie

- **优势**: 1. 吊销最简单；2. 服务端状态可控。
- **劣势**: 1. SPA 跨域场景 CSRF 防护成本；2. 会话存储引入额外 Redis 依赖与过期管理；3. 服务间调用需另起一套机制。
- **放弃原因**: 无状态扩展与服务间复用弱于 JWT，无差异化收益。

#### 方案 C: OAuth2.0 / OIDC

- **优势**: 1. 标准化、可对接外部 IdP。
- **劣势**: 1. 私有化实例无第三方登录需求，自建 IdP 纯属负担；2. 离线内网无外部队友方。
- **放弃原因**: 场景过度设计；保留接口演进空间（未来客户要求对接机构 AD/LDAP 时再加，属 V2 评估项）。

### 影响

- **正面影响**: 认证中间件单一、API 契约统一（`{code, data, message}` + 401/403 错误码）；审计日志中间件与 JWT 解析天然同层。
- **负面影响**: 需实现 token 刷新、吊销黑名单、密钥轮换三件套；等保测评可能要求双因子（预留 TOTP 扩展点（估算））。
- **波及范围**: api_server 全部端点、users 表设计、审计日志模块、安装向导（密钥生成）。

### 后续动作

- [ ] 实现 JWT 签发/刷新/吊销（Redis 黑名单）与 RBAC 中间件（接口级权限装饰器）
- [ ] 安装向导生成实例唯一 JWT 密钥（禁止默认值入镜像）
- [ ] 审计日志覆盖：登录、查询敏感数据、导出、确认/否决、配置变更（含操作者/IP/时间/对象）
- [ ] 评估等保三级双因子要求，预留 TOTP 扩展点

## ADR-010: 离线内网打包策略（模型权重 / 离线地图 / 依赖镜像）

### 背景

完全离线内网部署是 P0 硬约束（D-005）：安装包无外部依赖、断网可装可运行、支持部署方全盘代码审计与断网验收（L4）。离线化涉及四类大体积资产：1. Python/Node 依赖（pip/npm 离线源）；2. Docker 镜像（PG/ES/Redis/应用）；3. NLP/LLM 模型权重（fastText lid.176、paraphrase-multilingual-mpnet-base-v2、Qwen 系列量化权重、argos-translate 语言包，估算合计数 GB ~ 数十 GB）；4. 前端静态资源与离线地图瓦片（无 CDN、无在线瓦片服务）。同时安装向导需做硬件自检（1×24GB GPU 或 64GB 内存 CPU 量化档（估算），不达标即中止——与 ADR-004 联动）与"外发连接自检"（除数据源拉取外应为零外联，PRD 第六章 NFR）。

### 决策

**选择"单安装包 + 分层资产清单 + 安装向导自检"的打包策略**：全部 Docker 镜像导出为离线 tar、pip 依赖打包为 wheelhouse、npm 依赖预构建进前端静态产物、模型权重与离线地图瓦片作为独立资产包按需组装（基础包 + GPU 档 LLM 资产包 + CPU 量化档 LLM 资产包）；安装向导执行硬件自检、密钥生成、断网自检与外发连接自检。

### 方案对比

| 维度 | 单安装包分层资产（选择） | 在线拉取依赖（常规 Docker Compose） | 全部资产打入单一镜像 |
|------|------------------------|------------------------------------|---------------------|
| 离线可用 | ★★★★★ | ★☆☆☆☆ | ★★★★★ |
| 包体积管理 | ★★★★☆（按档组装，基础包不含 GPU 权重） | ★★★★★ | ★☆☆☆☆（数十 GB 单文件） |
| 升级/补丁分发 | ★★★★☆（资产分层替换） | ★★★★★ | ★★☆☆☆（全量重发） |
| 保密审计友好度（组件清单化） | ★★★★☆ | ★★☆☆☆（依赖安装时才解析） | ★★★☆☆ |
| 首次构建工程成本 | ★★☆☆☆ | ★★★★★ | ★★★☆☆ |

### 方案详述

#### 方案 A: 单安装包分层资产 — ✅ 选择

- **优势**: 1. 分层资产使无 GPU 客户不必下载 GPU 档权重（估算可省 10GB+），基础包保持可分发体积；2. wheelhouse + 离线镜像 tar + 预构建前端产物使安装过程零外联，满足断网验收；3. 每组件（含模型权重）出具来源与许可证说明，直接支撑 L4 审查的组件清单化要求；4. 外发连接自检成为安装验收标准项，给客户可演示的合规证据。
- **劣势**: 1. 打包管线（CI 中离线化）本身有工程成本：依赖锁定、镜像导出/导入脚本、瓦片裁剪；2. 依赖升级需重建 wheelhouse 并回归；3. 地图瓦片按 30 国范围裁剪以控体积（估算 GB 级，精度层级需权衡）。
- **适用场景**: 涉密内网交付、断网验收、组件审计场景。

#### 方案 B: 在线拉取依赖

- **优势**: 1. 打包最简单，标准 docker compose pull + pip install。
- **劣势**: 1. 离线内网物理不可行——直接违反 P0 约束。
- **放弃原因**: 一票否决。

#### 方案 C: 全部资产打入单一镜像

- **优势**: 1. 部署仅一步加载。
- **劣势**: 1. 单镜像数十 GB，导出/导入/分发（U 盘/内网摆渡）都痛苦；2. 任一组件升级即全量重发；3. 无 GPU 客户被迫携带无用权重。
- **放弃原因**: 分发与升级不可行。

### 影响

- **正面影响**: US-13（图形化安装向导、不依赖厂商上门）可行；O2 技术支持成本被产品化压缩；保密审查"断网验收 + 组件清单"两项硬性动作有标准交付物。
- **负面影响**: CI 需维护离线打包管线；版本升级策略需定义资产兼容性矩阵；模型权重许可证（Qwen 等）需逐模型审查入清单。
- **波及范围**: 部署/交付全部环节；frontend（离线瓦片）、llm_service（权重打包）、安装向导模块。

### 后续动作

- [ ] 编写离线打包管线：pip wheelhouse 构建、docker save/load 脚本、前端预构建、瓦片裁剪（30 国范围，估算层级）
- [ ] 定义资产分档：基础包 / GPU 档 LLM 资产包 / CPU 量化档资产包及兼容性矩阵
- [ ] 安装向导实现四步自检：硬件规格 → 密钥生成 → 断网加载 → 外发连接自检（除采集通道外零外联）
- [ ] 编制全栈组件来源与许可证清单（含 fastText / sentence-transformers / Qwen / argos-translate / RSSHub AGPL-3.0 / Redis RSALv2 等）

## ADR-011: 配置驱动采集管线 + 源清单化管理（借鉴 IIS，复刻而非照搬）

### 背景

ADR-008 确定了"RSS + GDELT 混合"的源策略，但采集层**如何实现** 600 源覆盖仍未回答：约 30 国 600 个媒体源（估算），若每源一个爬虫代码文件，需开发并持续维护数百个解析器（页面改版即失效），1 名后端的团队配置不可承受。调研报告 4（IIS 采集子系统深度分析，2026-07-24）给出关键事实：

1. **IIS 两代任务模式的教训**：A 代（RSS 手写流）每媒体一个 .py 插件，定制点仅 3 处（feed 列表、正文抓取方式、CSS selector）；B 代（配置驱动流）任务文件仅 17 行壳，逻辑全在配置文件，由通用管线驱动——新增无 RSS 媒体 = 调参生成 config，零爬虫代码。600 源规模下 A 代是反模式，B 代才是方向。
2. **"配置即爬虫"架构已验证**：IntelligenceCrawler 子模块实现三段式管线 Fetcher(Requests/Playwright) → Discoverer(RSS/Sitemap/ListPage) → Extractor(Trafilatura/Readability/GenericCSS) + 工厂按配置实例化；其中 **ListPageDiscoverer 链接签名聚类**（向上 5 层路径签名、剔除 odd/even/active 噪音类、数字泛化 item-123→item-N、签名聚类取 ≥5 链接最大簇为文章列表）免手写 selector，是无 RSS 站点的杀手锏。
3. **治理子系统值得照抄**：每 URL 状态机 PENDING/RUNNING/SUCCESS/TEMP_FAIL/PERM_FAIL/SKIPPED + retry_count + next_run_at，`should_crawl` 为去重与重试统一裁决点（TEMP_FAIL ≤3 次转 PERM_FAIL）；防重三层（持久去重 + 提交失败内存缓存下轮重发 + 任务内 URL 过滤）；/collect 解耦设计（任何采集方式皆可按统一载荷 POST 接入）。
4. **IIS 不能直接搬运**：任务文件仅覆盖 15 个媒体（12 国），距 600 源缺口 97.5%；插件热重载基于文件 watchdog 且 dev 分支未启用，文件插件模式不适合 600 源；监控只有 pull 式页面，无主动告警（弱项需自建）。

### 决策

**选择三层采集架构——通用 RSS 采集器 + 配置驱动爬虫管线 + 采集治理与告警，源全部清单化管理（配置存 DB，600 源 ≠ 600 个爬虫任务）**：

1. **通用 RSS 采集器**（承载约 80% 源（估算））：feedparser + trafilatura + 治理状态机；每源一行配置（sources 表 `crawl_config` JSONB 字段，`adapter_type='rss'`），不是每源一个代码文件。种子源清单来自 awesome-rss-feeds（按国家 OPML）+ Media Cloud 目录 + IIS 15 个媒体任务参数（BBC/VOA/TASS/NHK/DW/France24/RFI/El País/Anadolu/NTV/韩联社/新华网/中新网/半岛/CBC/ABC/Investing，Apache-2.0 可直接复用其源 URL、CSS selector、反爬参数）。
2. **配置驱动爬虫管线**（无 RSS 长尾，约 20% 源（估算），`adapter_type='pipeline'`）：复刻 IIS IntelligenceCrawler 三段式设计 Fetcher(Requests/Playwright) → Discoverer(RSS/Sitemap/ListPage) → Extractor(Trafilatura/Readability/GenericCSS) + 工厂按配置实例化；ListPageDiscoverer 链接签名聚类免手写 selector；Playwright 反爬栈（stealth、随机 UA、scroll_pages、post_extra_action 声明式点弹窗——参考 NHK 案例）。
3. **采集治理与告警**：治理状态机照抄 IIS 设计（六态 + retry_count + next_run_at；should_crawl 统一裁决，TEMP_FAIL ≤3 次转 PERM_FAIL）；防重三层；**主动告警自建**（IIS 弱项只有 pull 监控页）——源失败率超阈值触发告警（对接 alerting 模块与 US-03）。

配套机制：

- **源配置热更新**：管理界面保存即生效（DB 配置 + 重载信号），不用 IIS 的 watchdog 文件热重载（其 dev 分支该功能未启用，且文件插件模式不适合 600 源）。
- **新增源自助配置**（服务 US-02）：把 IIS CrawlerPlayground（PyQt 桌面 GUI）理念改为 **Web 表单 + 实时预览 + 配置存 DB**——用户粘贴网址，系统试运行管线并预览提取效果，确认后入库。
- **代理分流**：global_site_proxy / cn_site_proxy 国内外分级（参考 IIS）。
- **/collect 解耦**：采集端按统一载荷（uuid/title/content≥10字符/informant/authors/pub_time）POST 到中枢内部端点，token 鉴权，任何采集方式皆可接入（详见 2-详细设计.md）。

### 方案对比

| 维度 | 三层架构（选择） | 每源代码插件（IIS A 代） | 完全自研采集框架 |
|------|------------------|--------------------------|------------------|
| 600 源可扩展性 | ★★★★★（新增源 = 一行配置） | ★☆☆☆☆（每源一个代码文件） | ★★★★☆ |
| 无 RSS 长尾覆盖 | ★★★★☆（签名聚类免 selector） | ★★★☆☆（手写 selector） | ★★★★☆ |
| 开发工期 | ★★★★☆（复刻已验证设计） | ★★☆☆☆（600 源 × 插件） | ★☆☆☆☆（重新踩坑） |
| 治理/去重/重试 | ★★★★★（状态机照抄 IIS） | ★★☆☆☆（各插件自理） | ★★★☆☆ |
| 许可证风险 | ★★★★☆（复刻设计不搬代码） | ★★★★☆ | ★★★★★ |
| 维护成本（页面改版） | ★★★★☆（改配置/重跑签名聚类） | ★☆☆☆☆（改代码发版） | ★★★☆☆ |

### 方案详述

#### 方案 A: 三层架构（通用 RSS 采集器 + 配置驱动管线 + 治理告警） — ✅ 选择

- **优势**: 1. 源配置化原则使 600 源覆盖从"600 个开发任务"变为"1 个通用采集器 + 1 条配置管线 + 600 行配置"，与 1 后端团队规模匹配；2. 约 80% 源（估算）走零定制的 RSS 路径，工程量集中在约 20% 长尾的配置调参，且 ListPageDiscoverer 签名聚类使多数无 RSS 站点也无需手写 selector；3. 治理状态机 + 防重三层直接照抄 IIS 已验证设计，去重/重试/节奏控制不重新发明；4. 种子源清单（awesome-rss-feeds OPML + Media Cloud + IIS 15 媒体参数）使冷启动覆盖率有现成抓手；5. Web 表单自助配源把 IIS Playground 的调参理念产品化，直接服务 US-02。
- **劣势**: 1. 配置管线三段式 + 工厂是新增基础设施，估算工期高于"裸 feedparser 一把梭"（已纳入 4-开发计划.md Phase 1）；2. 签名聚类对结构极度异形的列表页可能失效，需保留 GenericCSS extractor 手写 selector 兜底；3. 配置存 DB 需自研重载信号机制（IIS 无可借鉴的启用实现）。
- **适用场景**: 数百源规模、源构成以有 RSS 主流媒体为主、小团队——本项目全部命中。

#### 方案 B: 每源代码插件（IIS A 代模式）

- **优势**: 1. 单源定制自由度最高；2. IIS A 代插件契约（module_init/start_task）有现成参考。
- **劣势**: 1. 600 源 = 600 个代码文件，开发+维护（页面改版即改代码发版）远超团队配置；2. IIS 自身已演进到 B 代配置驱动，A 代是其验证过的反模式；3. 配置与代码混杂，无法支撑 US-02 自助配源。
- **放弃原因**: 可扩展性是采集层的第一约束，每源代码文件在 600 源规模下方向性不可行。

#### 方案 C: 完全自研采集框架

- **优势**: 1. 无任何许可证考量；2. 可按需裁剪。
- **劣势**: 1. IIS 已用实战验证了管线三段式、签名聚类、治理状态机等关键设计，自研等于重新踩一遍坑；2. 工期不可接受（估算数倍于复刻）；3. 种子源参数（IIS 15 媒体的源 URL/selector/反爬参数）的复用价值与框架自研无关，放弃借鉴纯损。
- **放弃原因**: 复刻已验证设计的风险与工期均显著优于从零自研；许可证分析（见下）表明复刻设计无法务障碍。

### 许可证分析

- **IIS 主仓库（IntelligenceIntegrationSystem）Apache-2.0**：15 个媒体任务的源 URL、CSS selector、反爬参数可直接复用，保留许可证声明与 NOTICE 即可，纳入 ADR-010 的组件许可证清单。
- **IntelligenceCrawler 子模块无 LICENSE 文件**（法律灰色地带）：三段式管线、ListPageDiscoverer 签名聚类、治理状态机等均为**复刻设计、重新实现，不搬运任何代码**——架构理念与算法思路不受版权保护，此为法务零风险路径。
- **awesome-rss-feeds / Media Cloud 目录**：作为种子源数据来源使用（公开目录数据），使用前核对各自使用条款（估算风险低）。

### 影响

- **正面影响**: 采集层工期从"不可行"变为可排期（见 4-开发计划.md Phase 1）；US-02（自助配源）与 US-03（源失效告警）有了落地架构；源健康数据（治理状态机）直接喂养源健康看板与 ADR-008 的 GDELT 自动补位；采集层与中枢以 /collect 解耦，未来接入新采集方式（如重点国家 per-publisher 爬虫，D-001 可逆性条款）不动架构。
- **负面影响**: collector 成为基础设施最重的 worker（管线 + 治理 + 告警三件套）；配置存 DB 需新增 sources 表 `crawl_config`/`adapter_type` 字段与 collection_jobs 六态状态机（见 2-详细设计.md）；主动告警为自研新增面。
- **波及范围**: collector（全部）、alerting（源失败率告警）、api_server（sources 试运行预览端点、/internal/collect）、frontend（自助配源 Web 表单）；2-详细设计.md 的 DDL/内部 API/时序图、4-开发计划.md 的 Phase 1 任务分解同步更新。
