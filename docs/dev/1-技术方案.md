## 一、需求概述

### 1.1 业务目标

构建一套面向国家安全机关与国际关系/国家安全研究机构的**全球议程设置监控平台**：实时监控约 **30 国**主流新闻媒体（每国合计受众覆盖率 ≥70%，约 600 个媒体源，估算），识别"某国媒体/官员/重要人士首发议题 → 多国媒体跟随"的议程设置行为，自动判定首发源、跟随国序列与时滞，生成传播链路证据链并告警。系统具备自我纠错能力：议题随证据演化（萌芽→形成中→已确认→演化→消亡），次日自动归并、首发判定自动修正并全程留痕。

技术视角的规模与约束：

- **数据规模**：常态入库 ~2.2 万篇文章/天（估算），采集容量按 ≥8 万篇/天设计（估算，含 GDELT 兜底回灌与突发峰值），峰值入库 ≥100 篇/分钟不积压；一年文章 ~800 万条（估算），磁盘年增 ~300GB（估算）。
- **延迟硬指标**：新闻发布 → 平台可见 **P95 ≤ 30 分钟**，绝对红线 ≤ 2 小时（红线突破即 P0 告警）。
- **可用性**：单机部署 99.5%（年停机 < 43.8h），RTO ≤ 30 分钟，RPO ≤ 24 小时 + 当日增量 ≤ 1 小时。
- **部署约束**：私有化单机交付为唯一形态——单机 Docker Compose、数据不出域/不出境、离线地图瓦片、无外部依赖安装包、按等保 2.0 三级建设（估算目标）；LLM 与嵌入经机构批准的出网通道走云端 API（讯飞星辰 MaaS + SiliconFlow bge-m3，本地模型权重不默认保留）。
- **用户规模**：单机构 ≤50 在线用户、看板 API 20 QPS（估算，私有化场景）；用户零编程基础，部署初始化向导 ≤10 分钟。

### 2.2 架构模式

- **风格**：模块化单体 API 服务 + 独立 worker 进程组（采集 worker / NLP worker / LLM 接入），单机 Docker Compose 部署。
- **选择理由**：单机构 ≤50 并发用户的私有化单机场景不需要微服务；微服务的分布式运维成本与"零编程基础机构一键部署"目标直接冲突。模块化单体在代码层按模块隔离（collector / extractor / nlp_pipeline / agenda_engine / llm_service / api_server / frontend / alerting），重计算环节（采集、NLP、LLM 接入）拆为独立 worker 进程组以隔离资源竞争并支持并发调参扩容。对应 ADR-001（PM 决策 D-005 的技术推论）。
- **通信方式**：同步 = REST（前端 ↔ api_server，Base `/api/v1`，JWT 认证，统一响应 `{code, data, message}`）；异步 = Redis Streams + celery（采集→NLP→议程引擎→预警全链路解耦）。
- **架构原则**：
  1. **可见性优先于完整性**：管线拥塞时降级为"先入库后聚类"（文章先可见，议题标签后补），保证红线 ≤2h 优先于聚类完整性（PRD 4.2 异常流程）。
  2. **异步优先**：一切耗时处理（抽取、向量化、聚类、LLM、快照、报告生成）走队列异步，API 层只做查询与轻量写。
  3. **面向失败设计**：每一环节有声明式降级（源失效→RSSHub→GDELT；LLM→c-TF-IDF→关键词；聚类→关键词匹配），降级状态显式落库并告警，绝不静默降级。
  4. **数据不出网**：除采集通道与 LLM/嵌入云 API 调用外零外联；翻译、地图全部本地化；安装向导提供"外发连接自检"。
  5. **全链路可审计**：trace_id 贯穿采集→抽取→NLP→LLM→入库→可见；机器自动修正与人工操作均写 revision_log / 审计日志。

| 任务调度 | celery + Redis Streams | celery 5.x / Redis 7 | 单机规模不上 Kafka（ADR-003 ↔ PM D-004） |
| 采集 | 三层架构：通用 RSS 采集器（feedparser + trafilatura）+ 配置驱动爬虫管线（Fetcher/Discoverer/Extractor 三段式）+ RSSHub + GDELT DOC 2.0 API | - | 源配置化（crawl_config JSONB + adapter_type），600 源 ≠ 600 个爬虫任务（ADR-011 ↔ ADR-008 ↔ PM D-001，选型对比见 3.2）；trafilatura 抽取 F1 93.62（Fundus 基准，调研报告1 §2.3） |
| 无头浏览器 | Playwright + stealth | - | 无 RSS 长尾与反爬站点抓取：stealth、随机 UA、scroll_pages 滚动加载、post_extra_action 声明式点弹窗；借鉴 IIS 反爬栈（调研报告4） |
| 语言识别 | fastText lid.176 | - | 100+ 语言，官方基准准确率 ≥95%；官方仓库已归档，离线分发规避供应链风险（调研报告2 §5） |
| 向量模型 | SiliconFlow bge-m3（云嵌入 API，OpenAI 兼容 /embeddings） | - | 1024 维 + L2 归一化，跨语言统一向量空间，跨国议题对齐硬需求（ADR-005 ↔ PM D-002）；本地 mpnet 分支保留代码不默认使用 |
| 话题聚类 | BERTopic + Agglomerative 硬阈值双策略 | - | BERTopic 增量/在线模式 + Agglomerative cosine 0.25 average linkage 校正（IIS 教训：HDBSCAN 超大簇黑洞，ADR-005） |
| LLM | 讯飞星辰 MaaS（云端 API，OpenAI 兼容 /chat/completions，模型 xophunyuan7bmt，估算） | - | 并发 2 对齐讯飞 QPS 配额；数据经机构批准的出网通道（ADR-004 ↔ PM D-006）；本地 Qwen 分支保留代码不默认使用 |
| 离线翻译 | argos-translate / LibreTranslate | - | 展示层翻译；AGPL 组件以独立服务方式集成不修改源码 |
| 数据库 | PostgreSQL 16 + pgvector 扩展 | 16.x | 主库 + 向量存储一体（选型对比见 3.2，ADR-002） |
| 搜索引擎 | Elasticsearch | 8.x | articles 全文检索、议题/文章搜索 |
| 缓存/队列 | Redis | 7.x | Streams + 去重缓存 + 业务缓存，一举三用 |
| 前端 | React 18 + TypeScript + Apache ECharts | React 18.x | 自研四大专属视图（ADR-007 ↔ PM D-003）；ECharts Apache-2.0 无传染性 |
| 容器编排 | Docker Compose | v2.20+ | 单机私有化唯一交付形态（ADR-001/ADR-010 ↔ PM D-005） |
| Migration | Alembic | - | 与 SQLAlchemy 同生态 |
| 监控 | 内置管理后台（自研面板） | - | 私有化离线场景不依赖外部 APM；采集量/源健康/延迟 P95/错误率/磁盘五类面板 |

> **假定**: 团队为 1 后端 + 1 前端 + 0.5 NLP 顾问（估算，见 `4-开发计划.md`），技术栈优先选单人可维护、成熟的开源组件与可观测的云 API 服务；LLM 与嵌入模型具体规格/价格待供应商合同与基准测试定版。

### 3.2 关键选型对比

#### 数据库选型：PostgreSQL vs MySQL vs MongoDB（IIS 方案）

| 维度 | PostgreSQL 16 | MySQL 8 | MongoDB（IIS 所用） |
|------|-----------|-------|---------|
| 事务支持 | ★★★★★ | ★★★★☆ | ★★★☆☆ |
| JSON 支持（revision_log/follower_sequence 等 JSONB） | ★★★★★（JSONB 可索引） | ★★★★☆ | ★★★★★ |
| 向量检索（pgvector 扩展） | ★★★★☆ | ★☆☆☆☆ | ★★★☆☆（Atlas Search 云端为主） |
| 全文搜索 | ★★★★☆（另有 ES 补强） | ★★★☆☆ | ★★★☆☆ |
| 复杂关联（议题↔文章↔事件↔证据链多表 JOIN） | ★★★★★ | ★★★★☆ | ★★☆☆☆（聚合管道绕路） |
| 单机离线运维成熟度 | ★★★★★ | ★★★★★ | ★★★★☆ |
| 选型结论 | ✅ 选择 | ❌ | ❌ |

**理由**：借鉴来源 IIS（IntelligenceIntegrationSystem）使用 MongoDB，但其数据形态是"文档流"；本平台核心是**关系密集**的领域模型——topics ↔ topic_articles ↔ articles ↔ agenda_events ↔ agenda_event_evidence 多层关联，且 revision_log、follower_sequence、stats_evidence 等字段需要 JSONB 灵活结构 + 可索引查询。PostgreSQL 一库同时满足强事务、JSONB、pgvector 向量检索三件事，单机少一个进程。详细权衡见 ADR-002。

#### 向量存储选型：pgvector vs 独立向量库

| 维度 | pgvector（PG 扩展） | Milvus / Qdrant 独立向量库 | Elasticsearch 向量检索 |
|------|-----------|-------|---------|
| 单机部署复杂度 | ★★★★★（零新增进程） | ★★☆☆☆（新增有状态服务） | ★★★★☆（复用已有 ES） |
| 向量规模适配（~800 万条/年 × 1024 维，估算） | ★★★★☆（IVFFlat/HNSW 够用） | ★★★★★ | ★★★☆☆ |
| 与业务数据 JOIN（向量 ↔ articles/topics 元数据） | ★★★★★（同库 JOIN） | ★★☆☆☆（跨库拼接） | ★★★☆☆ |
| 离线备份一致性 | ★★★★★（随 PG dump） | ★★★☆☆（单独备份） | ★★★★☆（ES 快照） |
| 选型结论 | ✅ 选择 | ❌ | 备选（若 pgvector 性能不达标再迁） |

**理由**：私有化单机部署的第一约束是"少进程、易备份、一键恢复"。向量规模在千万条以内时 pgvector（HNSW 索引）性能足够（估算）；独立向量库引入一个有状态服务，备份/恢复/升级全部翻倍。ES 已承担全文检索，其 dense_vector 为备选降级位。对应 ADR-002。

#### Web 框架选型：FastAPI vs Flask vs Django

| 维度 | FastAPI | Flask | Django |
|------|---------|-------|--------|
| 异步支持（采集回调/ES 并发查询/LLM 流式） | ★★★★★（原生 async） | ★★★☆☆（2.0+ 有限支持） | ★★★☆☆（4.x 部分异步） |
| 请求校验与 OpenAPI 文档 | ★★★★★（Pydantic 自动） | ★★☆☆☆（需插件拼装） | ★★★☆☆（DRF） |
| 与 NLP/LLM 栈同语言复用 | ★★★★★ | ★★★★★ | ★★★★★ |
| 上手与维护（小团队） | ★★★★☆ | ★★★★★ | ★★★☆☆（重） |
| 选型结论 | ✅ 选择 | ❌ | ❌ |

**理由**：NLP worker 与 API 服务共享 Python 数据模型定义（Pydantic schema 复用）；FastAPI 自动生成的 OpenAPI 文档直接作为 `2-详细设计.md` API 契约的可执行校验。Flask 异步生态弱，Django 的 ORM/Admin 重量级组件在模块化单体 + worker 架构中用不上。

#### 前端方案选型：React + ECharts 自研 vs Metabase/Superset

| 维度 | React 18 + ECharts 自研 | Metabase 嵌入 | Superset |
|------|-----------|-------|---------|
| 专属视图能力（全球议程地图/传播链路图/NAS 网络图/时间线） | ★★★★★ | ★☆☆☆☆（查询构建器形态，无链路图） | ★★☆☆☆ |
| 零编程用户适配（核心任务 ≤3 步） | ★★★★★（按画像定制） | ★★★☆☆（查询构建器本身是门槛） | ★★☆☆☆ |
| 红蓝深色视觉规范落地 | ★★★★★ | ★★☆☆☆ | ★★☆☆☆ |
| 许可证（私有化商业分发） | ★★★★★（ECharts Apache-2.0） | ★★☆☆☆（AGPL 不友好） | ★★★★☆（Apache-2.0） |
| 开发成本 | ★★☆☆☆（估算 +6~8 周，PM D-003） | ★★★★★ | ★★★★☆ |
| 选型结论 | ✅ 选择 | ❌（仅 MVP 早期内部数据核查可用） | ❌ |

**理由**：四大专属视图是产品差异化壁垒（PM 决策 D-003），通用 BI 无法实现传播链路图与 NAS 网络图；目标用户零编程基础，BI 的查询构建器交互本身就是使用门槛。对应 ADR-007。

#### 消息队列选型：Redis Streams + celery vs Kafka vs RabbitMQ

| 维度 | Redis Streams + celery | Kafka | RabbitMQ |
|------|-----------|-------|---------|
| 单机私有化适配 | ★★★★★（Redis 本来就要装） | ★☆☆☆☆（JVM 运维重） | ★★★☆☆（多一个中间件） |
| 吞吐适配（百级 QPS 以内，估算） | ★★★★★ | ★★★★★（杀鸡用牛刀） | ★★★★☆ |
| 消费者组/积压回放 | ★★★★☆（Streams 原生） | ★★★★★ | ★★★☆☆ |
| 去重缓存复用 | ★★★★★（同一 Redis） | ★☆☆☆☆ | ★☆☆☆☆ |
| 选型结论 | ✅ 选择 | ❌（日文章量 >500 万再评估，PM D-004 重评估触发器） | ❌ |

**理由**：调研报告2 §8 明确建议中小规模 celery + Redis Streams；单机客户无法接受 Kafka 的资源与运维成本。对应 ADR-003（↔ PM D-004）。

#### 采集架构选型：配置驱动管线 + 通用 RSS 采集器 vs 每源代码插件（IIS A 代反模式）

| 维度 | 三层架构（通用 RSS 采集器 + 配置驱动管线 + 治理告警） | 每源代码插件（IIS A 代模式） | 完全自研采集框架 |
|------|-----------|-------|---------|
| 600 源可扩展性 | ★★★★★（每源一行配置：crawl_config JSONB + adapter_type） | ★☆☆☆☆（每源一个 .py，600 源 = 600 个代码文件） | ★★★★☆ |
| 新增源成本（US-02 自助配源） | ★★★★★（Web 表单 + 试运行预览 + 配置入库，零代码） | ★★☆☆☆（写代码 + 发版部署） | ★★★☆☆ |
| 无 RSS 长尾站点覆盖 | ★★★★☆（ListPageDiscoverer 链接签名聚类，免手写 selector） | ★★★☆☆（可写但逐个定制） | ★★★☆☆（需自研链接发现算法） |
| 治理与运维（重试/防重/告警） | ★★★★★（六态治理状态机 + 防重三层 + 源失败率主动告警） | ★★☆☆☆（重试去重逻辑散落各插件） | ★★★☆☆ |
| 开发成本与许可证风险 | ★★★★☆（复刻 IIS 设计；IntelligenceCrawler 子模块无 LICENSE，不搬代码） | ★★★☆☆（IIS 主仓库 Apache-2.0 可参考） | ★★☆☆☆（估算 +4~6 周） |
| 选型结论 | ✅ 选择 | ❌（600 源规模下的反模式） | ❌ |

**理由**：调研报告4 的核心结论——IIS 任务文件仅覆盖 15 个媒体（12 国，约为 600 源目标的 2.5%），无法直接搬运解决覆盖问题；其价值在架构模式。IIS 自身经历了两代任务模式：A 代（RSS 手写流）每媒体一个 .py，600 源规模下不可扩展，是反模式；B 代（配置驱动流）任务文件仅 17 行壳，逻辑全在配置，"新增无 RSS 媒体 = 调参生成 config + 复制壳，零爬虫代码"。本平台按 B 代方向再前进一步：配置从文件搬进数据库（sources 表 crawl_config JSONB），约 80% 有官方 RSS 的源（估算）由一个通用 RSS 采集器承载，约 20% 无 RSS 长尾（估算）走复刻 IIS IntelligenceCrawler 的三段式配置驱动管线（Fetcher → Discoverer → Extractor，工厂按配置实例化）。许可证上：IIS 主仓库 Apache-2.0，15 个媒体的源 URL、CSS selector、反爬参数可直接复用；IntelligenceCrawler 子模块无 LICENSE，复刻设计、不搬代码。IIS 治理状态机设计照抄，其弱项（只有 pull 监控页、无主动告警）自建补齐。对应 ADR-011（↔ ADR-008 ↔ PM D-001）。

#### LLM 部署选型：本地推理 vs 云端 API

| 维度 | 云端 LLM API（讯飞星辰 MaaS） | 本地 Qwen 推理 | 纯传统 NLP（无 LLM） |
|------|-----------|-------|---------|
| 数据不出境（保密硬约束） | ★★★☆☆（经机构批准的出网通道，仅文本出域） | ★★★★★ | ★★★★★ |
| 议题命名/归并/首发判定质量 | ★★★★★ | ★★★★☆ | ★★☆☆☆ |
| 工程量（提示词覆盖多任务 vs 逐任务建模） | ★★★★★ | ★★★★☆ | ★☆☆☆☆ |
| 硬件成本 | ★★★★★（零本地推理硬件，按量计费） | ★★★☆☆（1×24GB GPU 或 CPU 量化） | ★★★★★ |
| 选型结论 | ✅ 选择（默认 LLM_PROFILE=api） | 保留代码，不默认使用（已删模型权重） | 保留为降级兜底 |

**理由**：云 API 模式免除本地推理 GPU 硬件与运维负担，模型能力与工程效率更优；保密约束通过"仅文本出域 + 机构批准的出网通道"缓解（PM 决策 D-006 的补充决策）。降级链 LLM → c-TF-IDF → 关键词保证 LLM 不可用时主链路（聚类与测量）不中断；本地 Qwen 分支保留代码以备完全离线场景。对应 ADR-004。

#### 聚类策略选型：BERTopic + Agglomerative 双策略 vs 纯 HDBSCAN

| 维度 | BERTopic + Agglomerative 双策略 | 纯 HDBSCAN（IIS 教训） | LDA |
|------|-----------|-------|---------|
| 超大簇黑洞风险 | ★★★★★（硬阈值兜底拆分） | ★☆☆☆☆（IIS 实测超大簇黑洞） | ★★★☆☆ |
| 在线/增量聚类 | ★★★★☆（双阈值 T_event=0.85/T_dup=0.95 + 每小时全局重聚类校正，估算） | ★★☆☆☆ | ★☆☆☆☆ |
| 孤证保留（首日零星报道次日成形，US-16） | ★★★★★（size=1 微簇保留） | ★☆☆☆☆（HDBSCAN 噪声点丢弃） | ★★☆☆☆ |
| 跨语言统一议题空间 | ★★★★★（bge-m3 多语言向量） | ★★★★☆ | ★☆☆☆☆ |
| 选型结论 | ✅ 选择 | ❌ | ❌ |

**理由**：IIS 的核心教训是 HDBSCAN 把噪声点（孤证）丢弃且产生超大簇黑洞——而"首日孤证、次日成形"恰是 US-16 自我纠错的关键场景。双策略：BERTopic 做增量归簇，Agglomerative（cosine 0.25、average linkage，估算）做硬阈值校正与全局重聚类。对应 ADR-005（↔ PM D-002/D-007）。

### 4.1 模块划分

| 模块 | 职责 | 依赖 | 接口形式 |
|------|------|------|---------|
| **collector**（采集） | 三层架构（详见 §4.4）：① 通用 RSS 采集器（feedparser + trafilatura + 治理状态机，承载 ~80% 源，估算，每源一行配置而非每源一个代码文件）；② 配置驱动爬虫管线（Fetcher → Discoverer → Extractor 三段式 + 工厂按配置实例化 + ListPageDiscoverer 链接签名聚类 + Playwright 反爬栈，覆盖无 RSS 长尾 ~20% 源，估算）；③ 采集治理与告警（每 URL 六态治理状态机 PENDING/RUNNING/SUCCESS/TEMP_FAIL/PERM_FAIL/SKIPPED + retry_count/next_run_at + 防重三层 + 源失败率超阈值主动告警）；另含 RSSHub 补源、GDELT DOC 2.0 兜底拉取、URL/标题去重、源健康状态机（active/degraded/failed）、源配置热更新（DB 配置 + 重载信号）、采集延迟度量（published_at→crawled_at） | sources 表（crawl_config/adapter_type）、Redis（去重缓存）、外网出口（global_site_proxy/cn_site_proxy 国内外分级代理） | celery 任务；产出写 Redis Streams `articles.raw`；采集端经 `POST /internal/collect`（token 鉴权）接入中枢 |

### 4.4 collector 采集层设计（三层架构，借鉴 IIS）

设计依据：调研报告4（`docs/pm/_research/调研报告4-IIS采集子系统.md`）。IIS 的任务文件仅覆盖 15 个媒体（12 国），无法直接搬运解决 600 源覆盖；但其"配置即爬虫"架构、治理状态机、ListPageDiscoverer、/collect 解耦设计价值极高——本层**复刻其设计、选择性复用其参数，不搬运其代码**。

```
                        sources 表（每源一行配置：crawl_config JSONB + adapter_type）
                                          │
                    ┌─────────────────────┴───────────────────────┐
                    ▼ adapter_type='rss'                          ▼ adapter_type='pipeline'
        ┌──────────────────────────┐                ┌──────────────────────────────┐
        │ ① 通用 RSS 采集器          │                │ ② 配置驱动爬虫管线（复刻 IIS）  │
        │ （~80% 源，估算）          │                │ （无 RSS 长尾 ~20% 源，估算）  │
        │ feedparser 轮询           │                │ Fetcher(Requests/Playwright) │
        │ → trafilatura 正文        │                │  → Discoverer(RSS/Sitemap/   │
        │ → 治理状态机              │                │    ListPage 签名聚类)         │
        └─────────────┬────────────┘                │  → Extractor(Trafilatura/    │
                      │                             │    Readability/GenericCSS)   │
                      │                             └──────────────┬───────────────┘
                      ▼                                            ▼
        ┌───────────────────────────────────────────────────────────────────────┐
        │ ③ 采集治理与告警（照抄 IIS 治理状态机 + 自建主动告警）                     │
        │ 每 URL 六态：PENDING/RUNNING/SUCCESS/TEMP_FAIL/PERM_FAIL/SKIPPED         │
        │ + retry_count + next_run_at；should_crawl 统一裁决；                     │
        │ TEMP_FAIL ≤3 次转 PERM_FAIL；防重三层（持久去重 / 提交失败内存缓存          │
        │ 下轮重发 / 任务内 URL 过滤）；源失败率超阈值 → alerting 主动告警（US-03）   │
        └───────────────────────────────┬───────────────────────────────────────┘
                                        ▼ POST /internal/collect（token 鉴权）
                                Redis Streams: articles.raw
```

要点：

- **源配置化原则：600 源 ≠ 600 个爬虫任务**。新增源 = sources 表新增一行配置（`adapter_type` 选 `'rss'` 或 `'pipeline'`，`crawl_config` JSONB 承载 feed URL、抓取方式、CSS selector、scroll_pages、post_extra_action 等参数），不是新增代码文件。IIS 实践印证：其 B 代任务文件仅 17 行壳，逻辑全在配置；本平台把配置从文件进一步搬进数据库。DDL 见 `2-详细设计.md` 第二章。
- **种子源清单来源**：awesome-rss-feeds（按国家 OPML）+ Media Cloud 目录 + IIS 15 个媒体任务参数（BBC/VOA/TASS/NHK/DW/France24/RFI/El País/Anadolu/NTV/韩联社/新华网/中新网/半岛/CBC/ABC/Investing——主仓库 Apache-2.0，其源 URL、CSS selector、反爬参数可直接复用）；RSSHub 补长尾。
- **ListPageDiscoverer 链接签名聚类**（无 RSS 站点杀手锏）：对列表页所有 `<a>` 生成结构化路径签名（向上 5 层、剔除 odd/even/active 等噪音类、数字泛化 item-123→item-N），按签名聚类，取链接数 ≥5 的最大簇为文章列表——免手写 selector。算法伪代码见 `2-详细设计.md`。
- **Playwright 反爬栈**：stealth、随机 UA、scroll_pages 滚动加载、post_extra_action 声明式点弹窗（参考 IIS NHK 案例：声明式点"確認しました/次へ"同意弹窗）。
- **许可证注意**：IIS 主仓库 Apache-2.0（任务参数可复用）；**IntelligenceCrawler 子模块无 LICENSE**——复刻设计、不搬代码（许可证分析见 ADR-011）。
- **源配置热更新**：管理界面保存即生效（DB 配置 + 重载信号），不采用 IIS 的 watchdog 文件热重载（其 dev 分支该功能未启用，且文件插件模式不适合 600 源）。
- **新增源自助配置（US-02）**：把 IIS CrawlerPlayground（PyQt 桌面 GUI）理念改为 **Web 表单 + 实时预览 + 配置存 DB**——用户粘贴网址，系统试运行管线并预览提取效果，确认后入库（端点见 `2-详细设计.md` sources 模块）。
- **代理分流**：global_site_proxy / cn_site_proxy 国内外分级（参考 IIS，HTTP/SOCKS5，经部署方批准的边界出口）。
- **采集节奏**：普通源 15 分钟轮询，与 IIS 15 个媒体任务全部 15 分钟周期的实践对齐（调研报告4 §CrawlTasks）。

### 5.1 性能

#### 延迟预算分解（新闻发布 → 平台可见 P95 ≤30min，红线 ≤2h）

| 环节 | P95 预算（估算） | 说明与兜底 |
|------|----------------|-----------|
| 采集轮询等待 | 1–5 min | 重点源 RSS 1–5min 轮询；普通源 15min（15 分钟节奏与 IIS 15 个媒体任务全部 15 分钟周期的实践对齐，调研报告4；走 GDELT 15min 批兜底，最坏 15–30min 仍 ≤ 红线）；GDELT 独立覆盖补漏 |
| 采集→去重→入队 | ≤30 s | URL SHA-256 + 标题近重（Redis），去重缓存命中即弃 |
| 队列等待（Redis Streams） | ≤2 min | 积压 >10,000 持续 10min → 告警并加 worker；拥塞时降级"先入库后聚类"，可见性优先 |
| 正文抽取（trafilatura） | ≤10 s/篇 | 失败 → readability-lxml → 仅存摘要（content_status=partial），不阻塞 |
| 语言识别 + 向量化 + 情感 | ≤5 s/篇 | fastText <1s；云嵌入 API 批量请求（bge-m3 1024 维） |
| 聚类归入（在线增量） | ≤5 s/篇 | 双阈值归入既有议题；新议题走候选池异步处理，不阻塞可见 |
| 写入 PG + ES 索引可见 | ≤1 min | ES refresh_interval 调优（30s，估算）；**至此文章在"最新文章/检索"可见，累计 P95 ≈ 9 min** |
| AgendaSnapshot 刷新 | ≤15 min（固定窗口） | 每 15min 滚动刷新，单次计算 ≤5min；**至此议题排行可见，累计 P95 ≈ 24 min，余量 6 min** |
| LLM 命名/分类/归并 | 议题级异步 ≤5 min | P95 ≤10s/议题（云 API，估算，并发 2 批处理削峰）；不阻塞文章可见与排行 |
| **合计** | **P95 ≤ 24 min（估算），余量 ≥6 min；红线 2h 兜 GDELT 最坏路径** | 逐文章 `pipeline_latency_sample` 埋点度量（published_at→visible_at），>45min 持续 30min 告警 P1，>2h 告警 P0 |

### 5.2 高可用

- **应用层**：Docker Compose restart policy + 健康检查自动重启；api_server/worker 崩溃自愈；docker compose up 冷启动 ≤10 分钟。
- **数据层**：单机单实例（私有化现实约束），PostgreSQL 每日全量 dump + WAL 归档（当日增量 RPO ≤1h）；ES 每日快照；Redis AOF 持久化（队列可重放补采）。
- **灾备**：每日全量备份（PG dump + ES 快照），保留 30 天，AES-256 加密，备份位置可配置（本机/挂载盘）；每月一次恢复演练（US-14）；RTO ≤30 分钟（compose 重启 + 恢复脚本），RPO ≤24h + 增量 ≤1h。
- **采集缺口回补**：GDELT DOC API 支持滚动 3 个月窗口，故障恢复后自动回补缺失数据；新闻数据本身可补采。
- **降级**：三级降级链全部声明式——采集（RSS→RSSHub→GDELT→仅存量自采+缺口提示）、NLP（LLM→c-TF-IDF→关键词；BERTopic→关键词匹配；向量→TF-IDF 粗聚类；fastText→源默认语言）、统计检验（数据 <100 篇拒绝输出结论，硬性规则）；资源告急（CPU>85% 持续 10min）自动下调普通源轮询频率（15→30min），重点源不变。

### 5.4 可扩展性

- **垂直扩容**：采集/NLP worker 无状态，调 celery 并发即可扩吞吐；扩容触发：Redis Streams 积压 >10,000 持续 10min → 加 worker；CPU >70% / 内存 >80% 持续 5min → 告警提示升配。
- **增长预估**：国家 30→50、源 600→1000、文章 2.2 万→15 万篇/天（估算），单机 8C16G + 1TB SSD 可支撑（估算）；磁盘年增 ~300GB（估算）。
- **瓶颈点**：LLM/嵌入云 API 调用时延与配额（并发 2 批处理削峰，下游无本地推理硬件瓶颈）；ES 磁盘 I/O；GDELT API 调用频率。
- **架构演进预留**：消息层抽象（日文章量 >500 万可平滑迁 Kafka，PM D-004 触发器）；应用层无状态部分 V2 可水平复制；向量层可迁独立向量库（pgvector 性能不达标时）。

### 5.5 运维

- **部署**：`docker compose up -d` 单命令起栈；首次启动进入初始化向导（≤10 分钟）；离线环境用离线安装包（镜像 + fastText 语言识别模型 + 离线地图瓦片 + 依赖镜像）；安装前环境自检脚本。
- **升级/回滚**：镜像 tag 版本化（`agendascope:x.y.z`），升级 = 拉新镜像 + Alembic 迁移（停机 ≤10 分钟）；迁移失败自动回滚至上一版本快照（回滚 ≤10 分钟）；高风险功能（NAS 分析、新聚类参数）走 Feature Flag 热开关；迁移脚本前向兼容一个版本。
- **监控**：内置管理后台五类面板（采集量/源健康/延迟 P95/错误率/磁盘）；告警分级：P0（红线突破/覆盖率 <70%）、P1（延迟 >45min、LLM/聚类降级、积压）、P2（源失效）、P3（次日）。
- **日志**：结构化 JSON，trace_id 贯穿全链路，保留 30 天；慢查询、第三方调用失败、降级事件专项埋点（详见 `2-详细设计.md` 第六章）。
- **关键监控指标与告警阈值**：直接采用 PRD 7.2 监控看板（可见延迟 P95 / 活跃源占比 ≥95% / Streams 积压 <2,000 / 采集成功率 ≥98% / 聚类与 LLM 可用率 100% / 议程事件误报率 ≤20% / 议题误并误拆率 ≤5% / 磁盘 <75%，均估算目标）。

- 全部分析、存储、翻译、地图渲染在内网完成；采集通道与 LLM/嵌入云 API 是仅有的出网组件，安装向导"外发连接自检"验证除数据源拉取与模型 API 调用外零外联。
- 无 CDN、无外部字体/地图/统计脚本——全部资源本地化（离线分发硬约束）。
