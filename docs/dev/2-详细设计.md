## 一、API 接口定义

### 约定

- Base URL: `/api/v1`（私有化内网部署，形如 `http://<服务器IP>:8080/api/v1`；启用 TLS 后为 `https://`）
- 认证: Header `Authorization: Bearer <JWT access_token>`；登录/刷新/安装向导接口除外
- 请求格式: `application/json; charset=utf-8`
- 响应格式: `{ "code": 0, "data": {...}, "message": "ok" }`，code=0 成功，code>0 业务错误（见 1.1）
- 分页: `?page=1&page_size=20`（page_size 上限 100），响应 data 内含 `{ "total": N, "page": 1, "page_size": 20, "items": [...] }`
- 时间格式: ISO 8601 UTC，如 `2026-07-24T10:30:00Z`；前端按用户 locale 转时区展示
- 枚举值: 全部小写蛇形（如 `active`、`ctfidf_fallback`）；国家码 ISO 3166-1 alpha-2（如 `US`、`IN`）
- 幂等: POST 创建类接口支持 `Idempotency-Key` 请求头（重复提交返回首次结果）
- 限流响应: HTTP 429 + `Retry-After` 头，data 内含 `retry_after` 秒数

### 1.1 错误码规范

| HTTP Status | code | 含义 | 场景 |
|------------|------|------|------|
| 200 | 0 | 成功 | 正常响应 |
| 400 | 1001 | 参数校验失败 | 缺少必填字段/格式错误/枚举值非法 |
| 400 | 1002 | 非法 URL | 非 http/https 协议或指向内网地址（SSRF 防护，采集相关接口） |
| 401 | 2001 | 未认证 | Token 缺失/过期/签名非法 |
| 401 | 2003 | 凭据错误 | 登录用户名或密码错误 |
| 403 | 2002 | 无权限 | 角色/权限不足（如注册用户访问议程溯源） |
| 403 | 2004 | 账号被禁用 | users.status != active |
| 404 | 3001 | 资源不存在 | ID 查不到数据 |
| 409 | 4001 | 资源冲突 | 唯一性约束冲突（如 feed_url 已存在、重复源请求） |
| 422 | 4002 | 业务规则限制 | 状态机不允许的流转（如对 confirmed 事件重复确认、对 archived 议题归并） |
| 422 | 4003 | 配额超限 | 预警规则数/自定义源数/报告导出并发超上限 |
| 422 | 4004 | 数据不足 | 统计检验样本量 <100 篇、时间窗内无重叠报道（拒绝输出误导性结论） |
| 429 | 5001 | 请求过于频繁 | 触发限流 |
| 500 | 9001 | 服务器内部错误 | 未知异常 |
| 503 | 9002 | 依赖服务降级 | LLM/聚类/ES 不可用且接口无降级路径（有降级路径的接口正常返回并在 data 中标注降级） |

### 1.2 通用响应结构

```json
// 成功
{ "code": 0, "data": { "id": "..." }, "message": "ok" }

// 失败
{ "code": 2001, "data": null, "message": "Token 已过期，请重新登录" }

// 参数校验失败（带字段级明细）
{ "code": 1001, "data": { "fields": { "feed_url": "不是合法的 URL" } }, "message": "参数校验失败" }

// 降级模式响应（正常返回，调用方据 degraded 字段提示用户）
{ "code": 0, "data": { "degraded": true, "degrade_reason": "llm_unavailable", "items": [] }, "message": "ok" }
```

### 1.3 角色与权限（RBAC）

| 角色 | 说明 | 关键权限边界 |
|------|------|-------------|
| `guest` | 游客（仅演示页样例数据，无需登录） | 仅 `GET /demo/*` |
| `registered` | 注册用户 | 限 3 国看板、近 7 天时间线、报告导出 ≤5 次/月（估算，可配） |
| `authorized` | 授权用户（私有化机构内被授权使用者，分析师主体） | 全部 30 国、议程溯源/事件/人物监测、预警规则 ≤50 条/人（估算）、报告导出不限 |
| `admin` | 管理员（机构 IT/系统管理） | authorized 全部权限 + 源库管理/用户管理/系统监控/备份/许可证/审计日志 |

> **假定**: 角色枚举命名（guest/registered/authorized/admin）为本设计对 PM 权限矩阵（游客/注册用户/授权用户/管理员）的技术化映射，实现时可调整命名但保持四档语义。

下文每个端点 `Auth` 列标注最低所需角色。

#### POST /auth/refresh — 刷新 Token

```
POST /api/v1/auth/refresh
Content-Type: application/json

Request:  { "refresh_token": "dGhpcyBp..." }   // string, 必填

Response 200:
{ "code": 0, "data": { "access_token": "eyJhbG...", "refresh_token": "bmV3...", "expires_in": 7200 }, "message": "ok" }
// refresh_token 一次性轮换: 旧 refresh_token 立即失效并写入 Redis 黑名单; 旧 token 重放 → 401 并使该用户全部会话失效(防盗用)

限流: 同一用户 30 次/分钟
```

### 1.13 模块：内部接口（internal，采集端 → 中枢）

> 借鉴 IIS 的 /collect 解耦设计（ADR-011）：采集端（collector worker，含通用 RSS 采集器与配置驱动爬虫管线）不直接写库/写队列，统一按 CollectedData 式载荷 POST 到中枢接入端点——任何采集方式皆可接入，中枢统一做鉴权、校验、幂等去重与入队。
> 该接口**不走 /api/v1 前缀、不对用户开放**：仅部署内网采集端可达（网络层隔离），鉴权用独立内部 token（与 JWT 用户体系分离）。

#### POST /internal/collect — 采集数据接入

```
POST /internal/collect
Authorization: Bearer <collector_internal_token>   // 部署时注入的静态内部 token; 非法→401(code=2001)
Content-Type: application/json

Request (CollectedData 式载荷):
{
  "uuid": "5f8c2a1d-...",                  // string, 必填, 采集端生成的数据 UUID(中枢幂等去重键)
  "source_id": "7c9e6679-...",             // uuid, 必填
  "job_id": "9f8e...",                     // uuid, 可选, 关联 collection_jobs(回写治理状态机六态)
  "adapter_type": "pipeline",              // enum, 必填, rss/pipeline
  "url": "https://example-news.ng/news/12345",  // string, 必填
  "title": "...",                          // string, 必填
  "content": "...",                        // string, 必填, ≥10 字符(不足拒收, 对齐 IIS CollectedData 校验)
  "informant": "Example News - Latest",    // string, 必填, 来源标识(媒体名/feed 名/栏目名)
  "authors": ["..."],                      // array<string>, 可选
  "pub_time": "2026-07-24T05:30:00Z"       // datetime, 可选; 缺省按 crawled 处理(articles.time_source='crawled')
}

Response 200:
{ "code": 0, "data": { "uuid": "5f8c2a1d-...", "accepted": true, "duplicate": false }, "message": "ok" }
// 中枢处理: 校验 → uuid/url_hash 幂等去重(防重①持久去重; 重复→duplicate=true 幂等返回) → 写采集去重指纹(Redis dedup:url:{hash})
//   → XADD raw:articles(后续 extractor/NLP 流程不变) → 回写 collection_jobs 治理状态(SUCCESS/TEMP_FAIL)
// 采集端配合: 提交失败(网络/5xx)时数据入本地内存缓存, 下一轮重发(防重②); 任务内 URL 缓存过滤(防重③)——三层防重照抄 IIS 设计

Response 400 (code=1001): 字段缺失 / content <10 字符 / uuid 格式非法
Response 401 (code=2001): 内部 token 缺失或非法
限流: 采集端令牌桶 600 次/分钟(估算, 与 ~600 源峰值对齐)
```

### 2.2 数据库参数

- **数据库**: PostgreSQL 16（主库，含 pgvector 扩展存向量，避免独立向量库进程——单机部署简化）
- **字符集**: UTF-8；**排序规则**: `C.UTF-8`（多语言混合排序，不做本地化 collation）
- **时区**: UTC（全部 `TIMESTAMPTZ`，应用层转时区）
- **必备扩展**: `pgcrypto`（gen_random_uuid）、`vector`（pgvector）
- **检索副本**: articles 全文 + topics 摘要同步入 Elasticsearch 8（结构化查询走 PostgreSQL，全文检索走 ES）
- **行数估算依据**: articles ~2.2 万条/天、topic_articles ~3.3 万条/天（估算，与 PRD 5.2 一致）

### 2.5 DDL — collection_jobs 表

```sql
CREATE TABLE collection_jobs (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    source_id       UUID         NOT NULL REFERENCES sources(id),
    channel         VARCHAR(10)  NOT NULL
                    CHECK (channel IN ('rss','rsshub','gdelt')),
    scheduled_at    TIMESTAMPTZ  NOT NULL,               -- 计划轮询时间
    started_at      TIMESTAMPTZ,
    finished_at     TIMESTAMPTZ,
    status          VARCHAR(15)  NOT NULL DEFAULT 'PENDING'
                    CHECK (status IN ('PENDING','RUNNING','SUCCESS','TEMP_FAIL','PERM_FAIL','SKIPPED')),  -- 治理状态机六态(照抄 IIS 设计, 大写为例外命名, 见 COMMENT)
    retry_count     INT          NOT NULL DEFAULT 0,     -- 已重试次数; TEMP_FAIL 重试 ≤3 次, 超限转 PERM_FAIL
    next_run_at     TIMESTAMPTZ,                         -- TEMP_FAIL 下次重试时间(退避重试); should_crawl 统一裁决点据此调度
    http_status     SMALLINT,
    articles_found  INT          NOT NULL DEFAULT 0,     -- feed 中发现条目数
    articles_new    INT          NOT NULL DEFAULT 0,     -- 去重后新入库数
    error           TEXT,                                -- 失败原因(feed 结构变更/超时/SSRF 拦截等)
    latency_stats   JSONB,                               -- {published_min, published_max, avg_delay_min} 本轮延迟采样
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);
```

### 2.17 数据库变更管理

- **Migration 工具**: Alembic（Python 技术栈原生）；本文全部 DDL 可直接落入初始 migration `0001_init.py`
- **建表顺序**: 文档按业务模块叙述，migration 内须按外键依赖拓扑排序执行：`users / sources / topics / persons_orgs` → `articles`(FK→sources,topics 无关） → `collection_jobs / topic_articles / agenda_snapshots / agenda_events`(FK→topics,persons_orgs,sources,users) → `agenda_event_evidence / alert_rules` → `alerts / report_exports / audit_logs`（文档 2.10 agenda_events 对 2.12 persons_orgs 的前向引用由此消解）
- **命名规范**: `alembic revision --autogenerate -m "add_xxx"`，版本号使用 Alembic 默认 rev id + 描述
- **回滚策略**: 每个 migration 必须实现 `downgrade()`；升级前自动全量备份（pg_dump），迁移失败自动回滚至上一版本快照（对应 PRD 7.3，回滚 ≤10 分钟）
- **变更原则**:
  1. 新增列必须有 DEFAULT 或允许 NULL（避免锁表，articles/topic_articles 大表尤其注意）
  2. 删除列先标记 deprecated 注释 → 下一个版本再真删除
  3. 大表（articles/topic_articles/collection_jobs）加索引一律 `CREATE INDEX CONCURRENTLY`
  4. 枚举变更（新增 status/lifecycle_state 取值）以 CHECK 约束替换方式分两步：先放宽写入，再迁移数据，最后收紧
  5. pgvector 索引参数（m/ef_construction）变更须离线重建并在维护窗口执行

**异常/降级分支汇总**（与 PRD 4.2 异常流程、8.5 失败降级一致）：

| 环节 | 异常 | 处理 |
|------|------|------|
| collector | 单 URL/单轮抓取失败（治理状态机） | status→TEMP_FAIL，retry_count+1 并按 next_run_at 退避重试；重试 ≤3 次仍失败→PERM_FAIL 不再调度；should_crawl 统一裁决，去重命中→SKIPPED |
| collector | 源失败率超阈值（TEMP_FAIL/PERM_FAIL 占比） | 触发**主动告警**对接 alerting 模块与 US-03（IIS 仅 pull 监控页，主动告警为自建），见 6.3 |
| collector | 源连续 3 次轮询失败 | status→degraded，切 RSSHub 补源/GDELT 兜底，管理员告警；>24h→failed，触发覆盖率缺口检查 |
| collector | 短时 >20% 源同时失败（估算） | 判定出口网络故障，全局告警，不逐源变更状态 |
| collector | GDELT 不可达 | 自采链路独立运行，覆盖缺口黄灯提示；恢复后回补 3 个月窗口 |
| Redis Streams | nlp 积压 >10,000 条持续 10min | 自动扩 worker 并发 + 降级"先入库后聚类"（可见性红线优先于聚类完整性），积压 >2,000 即监控告警 |
| extractor | trafilatura + readability 均失败 | content_status=partial，标题+摘要向量入管线，不阻塞入库 |
| nlp_pipeline | BERTopic 不可用 | cluster_method=keyword_fallback 关键词匹配粗聚类 + P1 告警，恢复后回填重聚类 |
| llm_service | 调用超时率 >20% / API 不可用 | 降级 c-TF-IDF 关键词标签（naming_method=ctfidf_fallback）+ P1 告警；首发表述判定降级 media_time_fallback，置信度降一级 |
| llm_service | 终审不可用 | 事件跳过终审直接进人工复核队列，不自动告警，恢复后补审 |
| agenda_engine | 统计检验样本 <100 篇 | 拒绝输出检验结论（硬性规则），事件判定用其余证据并降置信度 |
| agenda_engine | 检验计算超时 >5min | 跳过当次刷新保留上一版结果，连续 3 次失败告警 |

**可见性红线保障**：文章写入 PostgreSQL 并设 `visible_at` 的时刻即"平台可见"考核点（延迟 = published_at → visible_at）；聚类/LLM 命名均不阻塞 visible_at 的设置——先可见、后补标签。

## 四、数据结构与算法

### 4.1 核心数据结构

#### EchoNode（回声消除折叠节点）— 用途： 跨国跟随链路与首发源判定的算法基础（借鉴 IIS DynamicGraphEngine）

```
Structure: EchoNode (内存结构, 落库为 topic_articles + articles.canonical_id 组)
┌─────────────────────────────────────────────────────────────┐
│ node_id: UUID            ← 节点标识(映射到议题内报道组)        │
│ canonical_article_id: UUID ← 组内主记录(最早 TIME_PUB)        │
│ related_docs: [            ← 折叠进来的跟风报道(保留全部来源!)  │
│   { article_id, source_id, country_code, published_at,      │
│     similarity, fold_rule }  ← fold_rule: same_day/within_3d │
│ ]                                                           │
│ countries: Set<char(2)>    ← 涉及国家(跟随链路的边)            │
│ earliest_pub: TIMESTAMPTZ  ← 节点内最早发布时间(首发锚点)       │
│ centroid: vector(1024)     ← 节点向量中心(时间衰减加权池化)     │
└─────────────────────────────────────────────────────────────┘
Methods:
  - absorb(article): bool — 若相似度达折叠阈值则吸入 related_docs 并更新 centroid/countries
  - origin(): Article — 返回 earliest_pub 对应文章(首发候选)
```

**选择理由**：
- **为什么不直接丢弃转载（常规去重）**: 跟风报道的数量与国家分布本身就是"议程跟随"的证据，丢弃即丢失跟随链路；折叠保留来源（related_docs）使显著性权重与跨国序列都可计算（IIS 核心经验）。
- **为什么不用 HDBSCAN 输出的簇直接做节点**: HDBSCAN 存在超大簇黑洞、实体引力过载、孤证被当噪声三个实战教训（调研报告3）；Agglomerative 硬距离阈值可保证簇内任意点距离受控，孤证保留为 size=1 微簇。

#### TopicDossier（议题档案）— 用途： 次日归并的比对对象（topic_id 复用）

```
Structure: TopicDossier (落库为 topics 行 + centroid)
┌─────────────────────────────────────────────────────────────┐
│ topic_id: UUID           ← 复用关键: 归并后新证据挂到旧议题    │
│ centroid: vector(1024)   ← 时间衰减加权池化的议题中心          │
│ keywords: [str]          ← c-TF-IDF top 词(降级匹配/可解释)   │
│ country_scope: [char(2)] ← 涉及国家                           │
│ lifecycle_state: enum    ← nascent/forming/confirmed/evolving/archived
│ no_merge_with: [UUID]    ← 误并回滚名单(归并比对前先行排除)    │
│ last_seen_at: TIMESTAMPTZ ← 活跃判定(7 天无新报道→消亡,估算)   │
└─────────────────────────────────────────────────────────────┘
Methods:
  - similarity(candidate_vec): float — cosine(centroid, candidate_vec)
  - absorb_microcluster(micro): void — 并入孤证微簇, 更新质心/国家/last_seen_at
```

### 4.2 关键算法伪代码

#### 算法 1：回声消除折叠（Echo Cancellation Folding）

```
输入: 议题候选报道集 D = {article}, 每篇含 embedding v, published_at t, country c, source s
参数: FOLD_SAME_DAY = 0.65   (同日折叠阈值, 余弦相似度)
      FOLD_3DAY     = 0.85   (3日内折叠阈值——跨天报道需更高相似度才判跟风)
输出: 节点集 N = {EchoNode}, 全部来源保留于 related_docs

function echo_fold(D):
    sort D by published_at asc                    // 时间序, 最早者优先成为 canonical
    N ← []
    for a in D:
        best ← argmax_{n in N} cosine(a.v, n.centroid)
        sim  ← cosine(a.v, best.centroid) if best else 0
        Δt   ← a.t - best.earliest_pub if best else ∞
        threshold ← (Δt ≤ 1 day) ? FOLD_SAME_DAY
                  : (Δt ≤ 3 day) ? FOLD_3DAY : None
        if best and threshold and sim ≥ threshold:
            best.related_docs.append({a, similarity: sim,
                                      fold_rule: same_day|within_3d})
            best.countries.add(a.c)
            // 主记录不换: canonical 永远是节点内最早 TIME_PUB
            best.centroid ← time_decay_pool(best.centroid, a.v, Δt)  // 时间衰减加权, 非 mean pooling
            mark a.is_duplicate = true, a.canonical_id = best.canonical_article_id  // 落库
        else:
            N.append(new EchoNode(canonical=a))   // 含孤证: size=1 微簇必须保留(议题萌芽)
    return N

复杂度: O(|D|·|N|) 朴素比对; 用 pgvector HNSW 近似近邻降为 O(|D|·log|N|)（估算）
注意: 折叠只影响"节点归属", 所有报道照常入库、照常计入显著性权重——来源永不丢弃
```

#### 算法 2：在线增量归簇（双阈值事件驱动）

```
输入: 新文章向量 v, 既有议题中心集 T(活跃议题, 含质心)
参数: T_event = 0.85  (归簇阈值, 估算), T_dup = 0.95  (判重阈值, 估算)
输出: 文章归属结果

function online_assign(v, article):
    if exists a' in recent_articles with cosine(v, a'.v) ≥ T_dup:
        return duplicate_of(a')                // 直接判转载, 走回声消除折叠
    best_topic ← argmax_{t in T} cosine(v, t.centroid)   // HNSW 近邻检索
    if cosine(v, best_topic.centroid) ≥ T_event:
        assign article → best_topic (weight=cosine)
        best_topic.centroid ← time_decay_pool(...)       // 增量更新质心
        best_topic.last_seen_at ← now()
        if best_topic.lifecycle_state == 'nascent':      // 孤证获得同伴
            best_topic.lifecycle_state ← 'forming'
    else:
        create micro_cluster(size=1, lifecycle_state='nascent')  // 孤证保留, 等待次日证据
    // 每小时全局重聚类校正(估算): 离线 Agglomerative 硬阈值(cosine 0.25, average linkage)
    // 对近 24h 窗重算, 修正纯在线误差累积; 校正期间前端读上一版快照并标注"校正中"
```

#### 算法 3：次日自动归并（Next-day Auto Merge, topic_id 复用）

```
输入: 昨日至今的新议题/微簇集 C, 历史活跃议题档案集 Dossiers(含归档前 30 天,估算)
参数: MERGE_SIM = 0.85 (跨语言向量比对阈值, 估算)
输出: 归并映射 merge_map, 新议题集 new_topics

function nextday_merge(C, Dossiers):
    load no_merge_pairs ← ∪ topics.no_merge_with      // 误并回滚名单先行加载
    merge_map ← {}, new_topics ← []
    for c in C (按 first_seen_at 升序):                // 老议题优先被并入目标
        candidates ← HNSW_knn(c.centroid, Dossiers, k=5)
        target ← argmax_{d in candidates} cosine(c.centroid, d.centroid)
        sim ← cosine(c.centroid, target.centroid)
        if sim ≥ MERGE_SIM and (c.id, target.id) ∉ no_merge_pairs:
            // 人工否决过的议题对永不自动归并
            merge_map[c.id] ← target.id               // topic_id 复用!
            migrate topic_articles: c → target (assign_method='merge')
            target.centroid ← time_decay_pool(target.centroid, c.centroid, w=|c|)
            target.country_scope ← union, target.last_seen_at ← now()
            target.lifecycle_state ← advance(target)  // nascent→forming→confirmed
            c.merged_into ← target.id, c.lifecycle_state ← 'evolving'
            append c.revision_log {field:'merged_into', after:target.id,
                                   trigger:{'sim':sim}, actor:'machine'}
        else:
            new_topics.append(c)                      // 开新议题(新 topic_id)
    if merge_map 非空: 触发受影响议题的"增量重估"(见算法 4)
    return merge_map, new_topics

// 配套消亡机制(超越 IIS: 补 split 与衰减关闭):
function lifecycle_sweeper():  // 每小时(估算)
    for t in active_topics:
        if now() - t.last_seen_at > 7 days(估算): t.lifecycle_state ← 'archived'   // 消亡
        // 误拆自愈: 归并环节发现 A、B 同源(同日被拆), 下一轮自动再合并
        // 误并回滚: 人工 POST /topics/{id}/split → 恢复双方 topic_id 与文章归属,
        //           写入 no_merge_with 与 revision_log(actor='human')
```

#### 算法 4：首发源判定与增量重估（Origin Detection + Re-estimation）

```
输入: 议题 T 的 EchoNode 集 N(算法 1 输出), persons_orgs 首发表述记录 U
输出: AgendaEvent 创建/更新(含 revision_log)

function detect_origin(T):
    nodes ← echo_fold(T.articles)                        // 算法 1
    media_origin ← argmin_{n in nodes} n.earliest_pub     // 节点内最早 TIME_PUB
    person_origin ← llm_first_utterance(T, U)             // LLM 判定"首次提出", 须输出 evidence_quote
    // LLM 不可用→detection_method=media_time_fallback, 仅媒体时间锚点, 置信度降一级
    origin ← earlier_of(media_origin, person_origin, tolerance=2d)  // 人物首发通常早于媒体(估算容差)
    followers ← group_by_country(nodes, exclude=origin.country)
              .map(c → {country: c, first_media, lag_hours: first_pub(c) - origin.at})
              .sort by lag_hours
    evidence ← { xcorr(T, origin.country, followers, lag 0..14d),   // 时滞互相关
                 granger(origin_series → follower_series),           // p<0.05 方向一致
                 qap(network) }                                      // 样本<100 篇→拒绝输出(硬性规则)
    if origin.confidence ≥ 阈值 and |followers| ≥ 3 国(14天窗口,可配,估算)
       and (xcorr or granger 显著) and T.lifecycle_state ∈ (forming, confirmed):
        event ← upsert AgendaEvent(status='suspected', origin, followers, evidence)
        review ← llm_final_review(event)                // 终审审查官 1-10 分
        if review.score < 5: event.status 维持 'watching' 并记录 REJECTED(负例积累)
        else: 触发 alerting(见 3.3)
    return event

function reestimate(T, trigger):        // 增量重估: 新证据(更早报道/新来源/归并)触发
    old ← snapshot(T.origin_fields, T.confidence, event.status)
    new ← detect_origin(T)
    for field where old[field] ≠ new[field]:
        if field ∈ T.human_locked_fields: continue      // 人工否决优先, 机器不推翻
        append revision_log {field, before: old[field], after: new[field],
                             trigger_evidence: trigger, actor: 'machine',
                             model, prompt_version}
        event.status ← 'revised'                        // 前端标注"该判定已于 X 时修正"
    // 修正风暴保护: 单议题 24h 内修正 >5 次(估算)→冻结自动修正, 转人工复核队列
    if count_revisions_24h(T) > 5: freeze_auto_revision(T), enqueue_human_review(T)
```

#### 算法 5：动态高频实体黑名单（Dynamic Entity Blacklist）

```
输入: 近 30 天 articles 的 NER 实体日频(LOCATION/GEOGRAPHY/PEOPLE/ORG)
参数: TOP_K = 50 (估算), 窗口 30 天, 刷新周期 24h
输出: Redis Set `entity:blacklist`(供聚类/关联图/归并比对过滤)

function refresh_entity_blacklist():     // 每日定时(估算)
    freq ← 统计近 30 天实体日频 Σ
    blacklist ← top_k(freq, 50)          // 如大国名、名人等超高频实体
    Redis.SET `entity:blacklist` = blacklist (TTL 48h, 刷新失败保旧值)
    // 用途(防超级节点污染, IIS 经验):
    // ① 聚类特征加权: 黑名单实体在 c-TF-IDF 与关联图边权中降权/剔除
    // ② 议题归并比对: 不因共享黑名单实体而提高相似度(仅看语义向量)
    // ③ 实体日频仍作议题萌芽/升温信号——黑名单只防"虚假关联", 不丢弃"趋势信号"

复杂度: 30 天 × 8 万篇/天(估算) 的实体计数, 每日批处理 O(总实体出现次数), 单机分钟级可完成(估算)
```

#### 算法 6：ListPageDiscoverer 链接签名聚类（无 RSS 站点文章列表发现）

> 复刻 IIS IntelligenceCrawler 的设计（ADR-011）：**子模块无 LICENSE，复刻思路、不搬代码**。服务于 `adapter_type='pipeline'` 的无 RSS 长尾源（~20%，估算），免手写 CSS selector；RSS/Sitemap 可发现的站点优先用对应 Discoverer，ListPage 为兜底。

```
输入: 列表页 HTML(栏目页 URL, 取自 sources.crawl_config.entry_points)
参数: PATH_DEPTH = 5   (DOM 祖先链向上回溯层数)
      MIN_CLUSTER = 5  (文章列表簇最小链接数, 估算)
输出: 文章链接集 L(绝对化、去重、同站过滤后)

function discover_articles(list_page_html, base_url):
    links ← extract all <a> in page, 仅保留与 base_url 同域链接
    for a in links:
        path ← a 的 DOM 祖先链向上取 PATH_DEPTH 层, 每层记 (tag + class)
        path ← 剔除噪音类: odd/even/active/hover/selected 等状态类与工具类(图标/纯样式类)
        path ← 数字泛化: class/id 中数字串 → 'N'   // item-123 → item-N, page-3 → page-N
        signatures[a.href] ← join(path)            // "结构化路径签名", 如 div.content>ul>li.item-N>a
    clusters ← group_by(signatures)                // 同签名链接聚为一簇
    article_cluster ← argmax_{c in clusters, |c| ≥ MIN_CLUSTER} |c|   // 链接数 ≥5 的最大簇即文章列表
    if article_cluster 不存在:
        return fallback(SitemapDiscoverer) 或标记配置待人工调整(经 POST /sources/crawl-preview 预览确认)
    L ← normalize_and_dedup(article_cluster.hrefs)  // 相对转绝对、去锚点、去重
    return L

复杂度: O(链接数 × PATH_DEPTH), 单页毫秒级(估算)
注意: 签名聚类只解决"发现"; 正文提取走 Extractor 链(Trafilatura→Readability→GenericCSS 兜底),
      与 RSS 路径共用治理状态机(should_crawl 六态裁决)与 POST /internal/collect 接入
```

## 五、缓存策略

### 5.1 缓存架构

```
┌─────────────────────────────────────────────────────────────┐
│ L1: 应用内缓存 (api_server 进程内, cachetools TTLCache)        │
│     TTL=60s, 容量=5000, LRU —— 仅超高频只读小对象(覆盖率汇总)   │
│ ─────────────────────────────────────────────────────────── │
│ L2: Redis 7 (与 Streams 同实例, 逻辑库分离 db0=缓存/db1=队列)   │
│     TTL 按数据类型 30s-30min, 主动失效优先于 TTL               │
│ ─────────────────────────────────────────────────────────── │
│ L3: PostgreSQL 16 (结构化) / Elasticsearch 8 (全文)            │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 缓存策略清单

| 数据 | 缓存位置 | TTL | 更新策略 | 失效策略 | Key 模式 |
|------|---------|-----|---------|---------|---------|
| 逐国覆盖率汇总 | L1+L2 | 60s / 300s | 查询时缓存 | TTL + 源状态变更 Pub/Sub 主动失效 | `coverage:all` / `coverage:{cc}` |
| 议题排行（国家×日期） | L2 | 900s | 查询时缓存 | TTL + snapshot 刷新（15min）主动失效 | `topics:rank:{cc}:{date}` |
| 议题时间线 | L2 | 900s | 查询时缓存 | TTL + snapshot 刷新主动失效 | `timeline:{topic}:{cc}:{gran}` |
| 传播链路图 | L2 | 1800s | 查询时缓存 | TTL + 事件更新/revision 主动失效 | `chain:{event_id}` |
| 系统概览（admin） | L2 | 30s | 查询时缓存 | TTL | `admin:overview` |
| 用户会话/配额 | L2 | 随 token | 登录写入 | 登出/吊销删除 | `session:{user_id}` |
| 实体黑名单 | L2 | 48h | 每日批刷新 | TTL（刷新失败保旧值） | `entity:blacklist` |
| 采集去重指纹 | L2 | 72h | 采集时写入 | TTL | `dedup:url:{hash}` / `dedup:title:{hash}` |
| 重聚类校正快照 | L2 | 至下次校正 | 校正完成写入 | 校正完成替换（读旧版不阻塞） | `cluster:snapshot:latest` |

### 5.3 缓存穿透/击穿/雪崩防护

| 风险 | 本系统场景 | 方案 |
|------|-----------|------|
| 穿透 | 检索不存在的 topic_id/event_id | 空值缓存（`null` 标记，TTL=60s）；ID 格式先行校验（UUID v4）拦截明显非法请求 |
| 击穿 | 每小时 snapshot 刷新瞬间，热点 `topics:rank:*` 同时 miss | 互斥锁 `SET lock:{key} NX EX 10`：抢到锁的 worker 重建，其余请求短暂等待后重试；热点 key 采用"逻辑过期"（value 内嵌过期时间，过期后异步刷新、先返旧值） |
| 雪崩 | 15min 对齐的大量排行 key 同时到期 | TTL 加随机偏移 ±20%（如 900s → 720-1080s）；L1 60s 兜底；snapshot 刷新采用"先写新版本再失效旧 key"而非先删后算 |
| 队列/缓存共实例风险 | Redis 单实例承载 Streams + 缓存 | 逻辑库分离 + `maxmemory-policy`：缓存 db 用 `allkeys-lru`，队列 db 用 `noeviction`（防任务被驱逐）；内存水位 >80% 告警 |

## 六、日志与监控

### 6.1 结构化日志规范

```json
{
  "timestamp": "2026-07-24T06:30:00.123Z",
  "level": "INFO",
  "trace_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "article_id": "b3d4e5f6-...",
  "service": "nlp_pipeline",
  "module": "embedding",
  "event": "article_embedded",
  "duration_ms": 42,
  "message": "文章向量化完成"
}
```

- **trace_id 贯穿全链路**：采集（XADD 时注入消息头）→ 抽取 → NLP → LLM → 入库 → 议程判定，每篇文章可回溯完整处理轨迹（PRD 6.5 可维护性要求）；Redis Streams 消息字段携带 trace_id 逐跳传递。
- **级别约定**：DEBUG（开发）/ INFO（正常业务事件）/ WARN（降级生效、重试、慢查询）/ ERROR（失败、异常栈）。
- **敏感控制**：日志不记录密码/Token/正文全文（正文只记 article_id 与长度）；审计日志独立存 audit_logs 表（只增不改），与应用日志分离。
- **存储**：本机 JSON Lines 文件 + logrotate（保留 30 天，估算）；管理后台提供日志查看页（US-14），无需额外装 Grafana/ELK。

### 6.2 关键埋点

| 事件 | 级别 | 关键字段 |
|------|------|---------|

## 七、安全设计细则

### 7.1 认证流程

```
[用户] → [POST /auth/login] → [校验 username+password(bcrypt cost=12)]
                                    │
                 ┌──────────────────┼───────────────────────┐
                 ▼                  ▼                       ▼
        [失败计数+1, ≥5 锁 15min] [管理员且开 MFA→校验 TOTP] [成功]
                                                     │
                                    [签发 JWT access(2h) + refresh(12h, 一次性轮换)]
                                                     │
                                    [每次请求中间件验证: 签名/有效期/Redis 黑名单]
                                                     │
                                          ┌─────────┴─────────┐
                                       [有效]               [过期]
                                          │                    │
                                          ▼                    ▼
                                    [注入 User+Role]    [401 → 走 /auth/refresh]
                                                                 │
                                            ┌────────────────────┤
                                         [refresh 有效]      [refresh 重放(旧 token)]
                                            │                    │
                                            ▼                    ▼
                                    [签发新对, 旧 refresh 吊销] [全部会话强制失效 + 安全告警]
```

### 7.2 授权模型（RBAC 权限矩阵）

```
资源/操作:                guest  registered  authorized  admin
演示看板(样例数据)            ✅       ✅          ✅        ✅
实时看板(国家数)              ❌    ≤3 国(估算)   30 国全部   ✅
时间线跨度                   ❌      近 7 天      全历史      ✅
议程溯源/事件/链路/修正历史     ❌       ❌          ✅        ✅
人物机构监测(US-15)           ❌       ❌          ✅        ✅
预警规则                     ❌       ❌      ≤50 条/人(估算)  ✅
报告导出                     ❌   ≤5 次/月(估算)    不限       ✅
事件确认/排除/否决自动修正      ❌       ❌          ✅        ✅
议题重命名/误并拆分           ❌       ❌          ✅        ✅
请求新增源                   ❌       ✅          ✅        ✅
源库管理/审核/覆盖率维护        ❌       ❌          ❌        ✅
用户管理/系统监控/备份/许可证   ❌       ❌          ❌        ✅
审计日志查看                  ❌       ❌          ❌        ✅
```

- 接口级鉴权：FastAPI 依赖注入 `require_role("authorized")`，每个端点声明最低角色（见第一章各端点 Auth 行）。
- 数据级约束：registered 的国家白名单与时间窗限制在 Service 层强制（不仅前端隐藏）。
- 越权访问一律 403 + 写审计日志（result=denied）。

### 7.3 输入校验与注入防护

| 类别 | 规则 | 实现位置 |
|------|------|---------|
| 参数校验 | Pydantic v2 模型全量声明类型/范围/枚举（country_code、UUID v4、时间跨度 ≤90 天等） | Controller 层 |
| SQL 注入 | SQLAlchemy ORM + 参数化查询，禁止字符串拼接 SQL；ES 查询用官方客户端 DSL | Repository 层 |
| XSS | API 纯 JSON 输出；前端 React 默认转义，富文本（报告/议题摘要）白名单渲染 | 前端 + 报告渲染层 |
| CSRF | JWT 走 Authorization 头（非 Cookie），天然免疫；若启用 Cookie 会话则加 SameSite=Strict + CSRF Token | api_server 中间件 |
| SSRF（采集面） | 用户提交 URL（sources/requests、webhook_url、自定义源）强制校验：仅 http/https、DNS 解析后拒绝 RFC1918/loopback/link-local 地址、禁止重定向到内网（code=1002） | collector/api_server 共用 UrlGuard |
| 限流 | 登录 10 次/分钟/IP；通用 API 300 次/分钟/用户（估算）；导出/备份等重操作单独配额；Redis 令牌桶实现 | api_server 中间件 |
| 密码策略 | ≥10 字符含大小写+数字；bcrypt cost=12；管理员首登强制改密；MFA TOTP（管理员可选） | auth 模块 |
| 传输加密 | TLS 1.3 + HSTS；内网部署允许 HTTP 但安装向导明确提示风险（PRD 6.2） | 反向代理（Caddy/Nginx 容器） |
| 数据保密 | 全部业务数据存用户内网；LLM 与嵌入经云 API（讯飞/SiliconFlow，仅发送待处理文本，不落库）——离线翻译、离线地图瓦片仍本地；导出与机密查询全量审计 | 部署形态 + audit_logs |
| 离线完整性 | 离线安装包（镜像+模型权重+地图瓦片）签名校验，安装向导逐组件哈希验证（防供应链篡改） | 安装器 |

> **假定**: 反向代理选型（Caddy 或 Nginx）、JWT 具体有效期（access 2h / refresh 12h）、各项限流数值（10/300 次等）为本设计在 PM 约束（会话超时 12h、登录 10 次/分钟、API 300 次/分钟，PRD 6.2/2-需求分析 5.3）下的具体化，实现时可经配置调整。
