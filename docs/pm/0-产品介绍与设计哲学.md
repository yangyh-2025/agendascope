## 第一部分：我们在解决什么问题

### 1. 开场白：一个问题，一个承诺

**如果你在国家安全机关负责国际舆情研判，或者在国际关系研究院研究跨国传播，你一定问过这三个问题：**

1. 今天全球主流媒体在报道什么？——**这是媒体议程。**
2. 这个议题是谁先提出来的？——**这是议程设置的起点。**
3. 哪些国家的媒体在跟随、隔了多久？这是一次自然传播，还是一次有组织的议程设置？——**这是议程设置的行为本身。**

市面上的工具，没有一个能同时回答这三个问题：

- **商业舆情平台**（Meltwater、Brandwatch、Talkwalker）价格高企（$10k–50k/年），以社交媒体聆听为主，不提供议程设置理论层面的测量，而且是纯 SaaS——数据托管在厂商云端，安全保密场景根本无法使用。
- **免费数据库**（GDELT、Media Cloud）只有原始数据与 API，需要 SQL 与编程能力才能分析，业务专家用不了。
- **国内政务舆情厂商**（蚁坊、清博等）以国内舆情为主，海外媒体覆盖弱，没有跨国议程溯源能力。
- **开源舆情项目**（TrendRadar 等）面向中文热搜与技术用户，既无全球媒体覆盖口径，也无理论化的显著性测量。

结果是：**最需要议程溯源能力的一群人，反而在用 Excel 和人工采样做跨国议程研判。**

**我们的承诺**：AgendaScope 观澜是一个私有化部署在您自有服务器/内网中的全球议程设置监控平台。它把议程设置理论三层框架（客体显著性 → 属性议程设置 → 网络议程设置 NAS）作为分析内核，实时监控 108 个经济体主流新闻媒体，在新闻发布后 2 小时红线内（P95 ≤ 30 分钟）将各国媒体议程转化为可交互的地图、时间线与议题网络图；并在此之上识别"议程设置"行为——当某国（媒体、官员、重要人士、智库、国际组织）率先提出议题、随后多国媒体跟随报道时，平台自动识别首发源、跟随国序列与时间差，呈现完整传播链路证据链，判定为议程设置事件并告警。

**监控范围**：108 国 = G20 全部 20 成员 + 全球南方大幅补足（85 国全球南方标记）+ 欧洲/拉美/中亚/非洲/中东补齐，覆盖全球主要经济体与全球南方典型国家。底层存储 ISO 3166-1 alpha-2 国家码，前端统一展示中文名。

**零编程基础的业务专家，可以像看天气预报一样使用它。**

### 2. 为什么这件事重要

议程设置是传播学最稳健的发现之一。1968 年 Chapel Hill 研究中，媒体议程与公众议程的 Spearman 相关系数高达约 0.97（McCombs & Shaw 1972）——**媒体告诉你"想什么"，在很大程度上决定了你想什么。**

今天的国际舆论场，议程设置博弈持续升温。一个典型模式反复出现：某国官员或媒体率先提出一个涉华议题，随后多国媒体在短时间内跟随报道，形成国际舆论压力。国家安全机关与国际关系研究机构，需要的是**第一时间识别"这是一次议程设置"**，并固定完整证据链支持研判与上报。

但我们今天看到的现实是：

| 场景 | 现有工具的实际表现 |
|------|-------------------|
| 识别"谁先提出的" | 靠人工经验事后归因，缺少首发源判定与证据引用 |
| 识别"哪些国家在跟随" | 靠人工跨国采样，缺少完整序列与时滞测量 |
| 识别"是不是有组织的议程设置" | 缺少议程设置行为的自动判定与统计佐证 |
| 固定证据链 | 缺少留痕、可回滚、可审计的判定修正体系 |
| 数据安全 | 商业 SaaS 数据出境不合规，无法进内网 |

**观澜把这条路压缩到"一次内网 Docker Compose 部署 + 10 分钟配置看板"。**

### 3. 一句话价值主张

> **私有化部署的全球舆情与议程设置行为监控平台——输入零代码，输出论文级的议程设置三层分析与跨国议程溯源证据链。**

核心差异化（详见第五部分）：

1. **议程设置行为识别与议程溯源（差异化核心）**：市面唯一能自动识别"这是一次议程设置"的产品——识别议题首发源（国家/媒体/人物）、跟随报道的国家序列与时间差、传播链路图，自动判定议程设置事件并告警，呈现完整证据链。
2. **自我纠错的议程演化追踪**：议题生命周期状态机 + 次日自动归并 + 增量重估判定修正 + 人工否决优先，全程留痕。
3. **70% 覆盖率口径**：每国主流媒体不是"随手选几家"，而是按可审计的操作化口径（维基百科 + ABYZ + Media Cloud + Similarweb 交集）合计受众覆盖率 ≥70%，逐国标注置信度。
4. **云端 LLM 智能**：议题分类、命名、归并、摘要、首发表述判定等 NLP 环节调用云端大模型 API，数据不出域、仅文本经批准出网通道出域推理；不可用时自动降级。
5. **零编程可用性与安全合规交付**：核心任务 ≤3 步、首次看板配置 ≤10 分钟、Docker Compose 一键私有化部署。

### 4.1 一个典型的研判故事（"新疆棉"式案例）

让我们用国际舆论场反复出现的一类模式，走一遍观澜的完整研判链路。这类模式是：**某国官员/媒体率先提出一个涉华议题 → 多国媒体在短时间内跟随报道 → 涉华负面议程在国际舆论场扩散**。

**第 0 天 23:00** — 一家美国媒体发布报道，首次使用一个针对中国新疆棉产业的定性表述。

- 采集层在 P95 ≤ 30 分钟内抓到这篇报道（RSS 高频轮询或 GDELT 兜底），正文抽取、语言识别、跨语言向量嵌入完成。
- 在线归簇判断这是一篇"孤证"，但语义向量独特，保留为 `size=1` 的 `nascent`（萌芽）微簇。
- 云端 LLM 为该微簇生成临时名称与分类。此刻它只是全球无数萌芽议题中的一个，没有任何异常。

**第 1 天 06:00** — 欧洲、东南亚、拉美多家媒体开始跟进报道同一话题。

- 跟进报道与萌芽微簇跨语言向量比对 ≥0.85，归入同一议题节点（`topic_id` 复用）。
- 议题状态从 `nascent` 推进到 `forming`（形成中），覆盖国家从 1 国扩展到多国。
- 议程引擎对该活跃议题启动完整检测链路：
  - **首发锚点判定**：议题簇内最早 `published_at` 锁定为那篇美国媒体报道，判定首发国=美国、首发媒体明确。
  - **LLM 首发表述判定**：从首发报道中抽取原文子串作为 `evidence_quote`，判定首发表述。
  - **跟随国序列**：各国首篇报道按 `lag_hours` 升序排列——欧洲某国 +4 小时、东南亚某国 +9 小时、拉美某国 +16 小时。
  - **统计佐证**：样本量 ≥100 后，XCorr/Granger/QAP 检验首发国与跟随国报道曲线的关系。
  - **事件判定**：首发源明确 + ≥3 国 14 天内跟随 + 统计显著 + 议题活跃 → 判定为 `suspected`（疑似）议程设置事件。

**第 1 天 06:10** — 分析师打开观澜。

- 全球总览页：该国在地图上显著高亮（报道量着色），健康度 TOP 列表可点击下钻。
- 议题列表按显著性排序，这个议题进入前列，卡片带"议程事件"标签。
- 进入议题详情页 → 关联议程事件卡：世界地图流向动画（美国红色高亮"首发"，欧洲/东南亚/拉美蓝色散点，红色箭头标注时滞小时数）、跟随序列表格、统计检验结果卡、终审结论。
- **分析师 10 分钟内拿到完整证据链**：首发源、首发表述原文引用、跟随国序列、时滞、统计显著性——全部可点击、可追溯、可导出。

**第 2 天** — 新证据出现：一篇更早的报道被发现。

- 增量重估触发：更早报道改变首发锚点判定 → `revision_log` 写入修正条目（actor='machine'，含模型与触发证据），前端标注"该判定已于 X 时修正"。
- 若某国通讯社实际是转载而非原创首发，相关字段被修正，`origin_confidence` 可能降级为 `low`，进入"首发源待核实"队列，不自动告警。
- 分析师在**修正历史**页看到全部修正流，可选择**人工确认**事件、**否决**某条修正（需填原因）、或**排除**（标记误报）。

**第 7 天** — 议题进入 `evolving`（演化），后续报道趋缓，7 天无新报道后自动 `archived`（归档，保留可查）。

这个故事的每一个环节——从孤证萌芽到归档——都不是"关键词命中"，而是**议程设置理论的完整测量链在实时数据上的工业化落地**。而最关键的是：**首发源、跟随序列、时滞、统计佐证、每一次修正，全部留痕可查。**这正是研判可信度的根基。

### 4.3 为什么是现在：技术成熟、数据就位、需求上升

观澜不是一个"应该存在但太早"的产品。以下是为什么 2026 年是它的正确时机：

**① 技术成熟度：一个工程师能搭起过去一个 NLP 团队的管线**

- 跨语言嵌入云端 API（SiliconFlow bge-m3，1024 维）让"把不同语言的报道映射到同一语义空间"变成一行 API 调用。
- BERTopic（7.8k★，含在线/增量模式）让在线主题聚类成为成熟工程组件。
- 云端大模型 API（如讯飞星辰 MaaS，OpenAI 兼容）让议题分类/命名/归并/首发表述判定等 NLP 环节直接交给 LLM。

三年前搭这套管线需要一个 NLP 团队，今天是一个工程师的工作量。

**② 免费数据基础设施就位：边际数据成本趋近于零**

- GDELT 每 15 分钟更新、100+ 语言、65 种语言实时机翻，完全免费。
- RSSHub 为无 RSS 的媒体补源。
- 全球媒体监控的边际数据成本已趋近于零——这支撑了"57 国全面监控"的产品形态。

**③ 学术范式转向：方法论需求与工具供给的剪刀差扩大**

- 2025 年 *Communication and Change* 出版"AI 时代重访议程设置"特刊，计算议程设置研究进入高峰期。
- 但研究者普遍缺乏工程能力——方法论需求旺盛，工具供给缺失。观澜把这个剪刀差变成产品机会。

**④ 安全需求上升：议程设置博弈成为刚需**

- 国际舆论场的议程设置博弈持续升温，"某国率先提出涉华议题 → 多国媒体跟随"的模式反复出现。
- 国家安全机关与国际关系研究机构对"第一时间识别议程设置行为并固定证据链"的需求成为刚需，而现有工具无一可用。

**⑤ 竞品空档：窗口期存在但会关闭**

- 商业平台向社媒与消费者智能集中（Brandwatch 83 种语言但以社媒为主）且为纯 SaaS。
- 国内政务舆情厂商海外覆盖弱。
- 无人把"议程设置理论 + 议程溯源"做成可私有化部署的产品；开源舆情项目集中在中文热搜。

> **结论**：技术、数据、需求、竞品空档四个条件同时满足，观澜正是为填补这个真空而设计。

## 第二部分：产品能力全景

### 5. 从数据到研判：一条完整的产品管线

观澜不是一堆功能的拼凑，而是一条**从原始新闻到议程设置研判**的完整管线。理解这条管线，就理解了整个产品。

```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│  采集层    │ → │  理解层    │ → │  议程层    │ → │  研判层    │ → │  呈现层    │
│ 全球媒体   │   │ 语言识别   │   │ 议题聚类   │   │ 首发源判定 │   │ 地图/时间线 │
│ RSS/GDELT │   │ 跨语言向量 │   │ 生命周期   │   │ 跟随国序列 │   │ 传播链路图 │
│ 正文抽取   │   │ 云端 LLM   │   │ 自我纠错   │   │ 事件判定   │   │ 预警/报告   │
└──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
```

- **采集层**：57 国主流媒体 RSS 高频轮询 + GDELT 兜底 + RSSHub 补源 + 正文抽取；源健康监控与失效自愈。
- **理解层**：fastText 语言识别（176 种语言）→ 跨语言向量嵌入（bge-m3，1024 维）→ 云端大模型 LLM（议题命名/分类/摘要）。
- **议程层**：跨语言向量聚类（BERTopic 在线增量 + 重聚类校正）→ 议题生命周期状态机 → 回声消除折叠 → 次日自动归并 → 分裂回滚。
- **研判层**：媒体首发锚点判定 → LLM 首发表述判定 → 跟随国序列计算 → 统计佐证（XCorr/Granger/QAP）→ 议程设置事件判定 → LLM 终审。
- **呈现层**：全球议程地图、议程时间线、跨国传播流向图、议题显著性排行、预警推送、一键报告导出。

### 6.2 关键交互：议程事件详情页的三层信息

以**议程事件详情页**（`/events/:id`）为例，它体现了观澜"给证据，也给证据的边界"的设计理念——三层信息递进：

| 层级 | 内容 | 回答的问题 |
|------|------|-----------|
| **第一层：结论** | 事件状态标签、首发国（红色高亮）、首发时间、首发类型、首发媒体、检测方式、跟随国数、判定轮次 | "这是一次议程设置吗？谁发起的？" |
| **第二层：证据** | 世界地图流向动画（首发→跟随，箭头标注时滞）、跟随序列表格、首发原文引用 | "证据是什么？谁在跟随、隔了多久？" |
| **第三层：边界** | 统计检验卡（xcorr/Granger/QAP 的 p 值 + 样本量 + "统计关联≠因果"提示）、终审结论、修正留痕 | "这个结论有多可靠？哪些需要人工复核？" |

一个分析师从第一层快速判断"要不要看"，从第二层拿证据链，从第三层判断"结论的置信边界在哪"。**每一层都服务一个决策，不浪费任何一次点击。**

### 6.3 关键交互：议题详情页的自我纠错中心

**议题详情页**（`/topics/:id`）是"自我纠错"哲学的集中体现：

| 区域 | 内容 | 设计意图 |
|------|------|---------|
| 议题信息卡 | 名称、分类、生命周期标签、覆盖国家、首次/最近出现、24h 报道量、关键词 | 议题"现在是什么" |
| 修正记录（可展开） | revision_log 列表：字段/前后值/actor/时间 | 议题"怎么变成现在这样" |
| 关联议程事件 | 内嵌事件卡：首发源/跟随序列/流向图/终审 | 议题"是不是议程设置" |
| 报道趋势 | 近 7 天报道量折线图 | 议题"正在怎么变" |
| 相关文章 | 标题/摘录/来源/国家/时间 | 议题"证据是什么" |
| 合并建议 | 相似议题 + 相似度，人工确认 | 议题"是否该合并" |
| 已并入的源议题 | 被并入的源议题 + 误并回滚按钮 | 议题"从哪里来，能否拆回去" |

**"误并回滚（拆分）"是自我纠错的最强表达**：如果系统把两个议题误并了，分析师一键拆分，双方进入 `no_merge_with` 名单防再误并，全程 revision_log 留痕。**机器会错，但人能纠正，且纠正本身也是留痕的证据。**

### 7. 核心能力逐个说明

#### 7.1 全球媒体源管理与采集

**一句话**：108 国、每国 ≥70% 受众覆盖率、可审计的媒体清单 + 高频轮询 + 失效自愈。

- **覆盖口径**：监控国家清单是**单一事实源**（`backend/app/core/countries.py`，108 国：G20 全部 20 成员 + 全球南方大幅补足 + 欧洲/拉美/中亚/非洲/中东补齐），全系统（地图/议题/安装向导/GDELT/种子源）从它派生，杜绝散落硬编码。底层存储 ISO 3166-1 alpha-2 两位国家码，前端展示中文名。
- **媒体清单**：124 个媒体源（每国 ≥1 个代表源，大国多源），来自维基百科各国报纸列表 + ABYZ News Links + Media Cloud Directory + awesome-rss-feeds + Similarweb 流量排名取交集，逐国标注覆盖率估算置信度。
- **采集策略**：重点源 RSS 高频轮询（1–5 分钟）+ GDELT 兜底（15 分钟更新，刚好满足 2 小时红线内的兜底延迟）+ RSSHub 为无 RSS 的媒体补源 + trafilatura 正文抽取（抽取基准 F1 93.62）。
- **源健康监控**：每个源有 `active / degraded / failed` 三态健康状态机，成功/失败连续判定自动恢复/降级；`failed` 源连续 2 次成功自动恢复 `active`（2026-08 修复的历史 bug）。
- **付费墙反爬**：借鉴 bypass-paywalls 思路——Playwright route 拦截付费脚本域名、bot UA 伪装按源配置、Google Cache 兜底。
- **自助配源**：业务专家粘贴媒体 URL → 试运行抓取样例核对 → 确认入库（需 admin 角色），无需懂任何技术配置。

#### 7.2 议程分析引擎（议题聚类与命名）

**一句话**：跨语言、可纠错、带方法学留痕的议题提取与标注。

- **语言识别**：fastText 语言识别模型（176 种语言），本地运行、无 API 依赖。
- **跨语言向量**：云端嵌入（SiliconFlow bge-m3，1024 维），不同语言报道映射到同一向量空间，**"法国媒体的『新疆棉』"与"美国媒体的『Xinjiang cotton』"能聚到同一议题**。
- **议题聚类**：BERTopic（UMAP+HDBSCAN+c-TF-IDF）主线 + Agglomerative 硬阈值（cosine 0.25，average linkage）双策略并行评估，单簇占比 >80% 触发超大簇黑洞护栏回落 Agglomerative；在线增量双阈值归簇（T_event=0.85 归簇 / T_dup=0.95 判重），孤证保留为 size=1 nascent 微簇；每小时全局重聚类校正（近 24h 窗）+ Redis 快照发布（校正期间读侧读上一版并标注"校正中"）。
- **议题命名/分类/摘要**：由云端大模型 LLM 完成，prompt 内嵌 JSON Schema 强约束 + pydantic 校验，带版本号管理（只增不改），每次判定写 `llm_judgements` 表（模型名 + prompt_version + 输入/输出快照 + 耗时）。
- **降级链**：LLM 不可用 → c-TF-IDF 关键词标签兜底 + P1 告警；聚类不可用 → 关键词匹配粗聚类降级；恢复后自动回填降级期议题。

#### 7.3 议题生命周期与自我纠错

**一句话**：议题像生物一样"生长"，也像档案一样"留痕"。

- **生命周期状态机**：`萌芽（nascent）→ 形成中（forming）→ 已确认（confirmed）→ 演化（evolving）→ 消亡（archived）` 五态完整版；连续 7 天无新报道自动归档（保留可查）；人工锁定字段议题不自动消亡。
- **回声消除折叠**：同日 cosine ≥0.65 / 3 日内 ≥0.85 折叠为同一议题节点，全部来源保留 related_docs，canonical 永远是最早 TIME_PUB，时间衰减加权质心。
- **次日自动归并**：candidate nascent 微簇 vs 历史活跃议题跨语言向量比对 ≥0.85 并入旧议题，topic_id 复用 + 推进 lifecycle_state；加载 no_merge_with 名单先行排除；人工锁定 `merged_into` 字段的源议题不自动归并。解决"今天只有零星报道、明天才成形"的议程滞后问题。
- **议题分裂与误并回滚**：恢复双方 topic_id 与文章归属；双方写入 no_merge_with 防再误并；revision_log 留痕。
- **合并建议**：对相似度高但未达自动归并阈值的议题，给出"合并建议"供人工确认（系统不会自动合并）。

**为什么"议题演化"是产品而不是后台机制**：对分析师而言，"这个议题昨天是 X、今天变成了 X'、我能否追溯它怎么变过来的"直接决定研判结论。观澜把议题演化做成用户可见的一等公民：

- **议题详情页**完整展示：生命周期标签、覆盖国家、首次出现/最近活跃、24h 报道量与媒体数、关键词、分类。
- **合并建议卡**：相似议题 + 相似度百分比，人工确认是否归并（系统绝不自动合并未确认项）。
- **已并入的源议题卡**：展示每个被并入的源议题（原名/摘要/覆盖/首次出现），并支持"误并回滚（拆分）"一键操作——拆分后双方进入 `no_merge_with` 名单，防止再次误并。
- **修正记录**：议题级 `revision_log` 可展开查看，每条含字段、前后值、actor（人工/机器）、修正时间。

**自我纠错体系全景**：

| 机制 | 触发条件 | 用户可见效果 | 留痕 |
|------|---------|-------------|------|
| 生命周期推进 | 证据积累（报道数/跨时长/跟随国） | 议题卡片状态标签变化 | lifecycle 字段 revision |
| 次日自动归并 | 跨语言向量 ≥0.85 | "已合并至其他议题"重定向 | merged_into 字段 revision |
| 增量重估 | 更早报道/新来源出现 | 首发源字段变化 + 前端"已修正"标注 | revision_log（actor=machine） |
| 置信度升降 | 满足/失去升级条件 | 事件状态 watching/suspected/confirmed 变化 | confidence revision |
| 修正风暴保护 | 24h 修正 >5 次 | 自动修正冻结，转人工 | 冻结记录 |
| 人工确认/否决 | 分析师操作 | 事件 confirmed / 修正 rejected | audit_logs + revision_log |
| 误并回滚 | 分析师操作 | 双方议题归属恢复 | revision_log（actor=human） |

#### 7.4 议程溯源与议程设置事件识别（差异化核心）

**一句话**：自动回答"这是不是一次议程设置、谁发起的、哪些国家在跟随、隔了多久"。

完整检测链路（由事件检测 worker 周期驱动，对活跃议题全链路检测）：

1. **回声折叠**：把多国报道折叠到同一议题节点。
2. **实体登记**：jieba 中文 NER + 英文大写规则，登记人物/机构/政府/智库实体。
3. **媒体首发锚点判定**：议题簇内最早 published_at UTC；同秒并列通讯社原文优先（media_type/agency/wire 双通道）；time_source='crawled' 低置信"首发源待核实"不自动告警。
4. **LLM 首发表述判定**：候选全文+历史表述 ≤4000 token；evidence_quote 强制原文子串；无依据判定丢弃进人工队列；不可用回落 media_time_fallback。
5. **跟随国序列计算**：各国首篇 lag_hours 升序；14 天窗口；仅原创节点。
6. **统计佐证计算**：XCorr lag 0-14 + Granger + QAP；样本量 <100 硬性拒绝"数据量不足"；降级不抛异常。
7. **事件判定**：满足条件（首发源明确 + ≥3 国 14 天内跟随 + 统计显著 + 议题活跃）→ AgendaEvent 状态机 `watching → suspected → confirmed`。
8. **LLM 终审审查官**：对 suspected 事件评逻辑连贯性 1-10 分；<5 自动降 watching 不自动告警；≥5 维持；不可用跳过直进人工复核队列。

**事件状态机**：`watching / suspected / confirmed / dismissed / revised / archived` 六态。判定条件的核心约束：**upsert 不重置已 confirmed/archived 事件**——人工结论机器不推翻。

**首发源判定的三种类型**：

| 类型 | 说明 | 前端标签 |
|------|------|---------|
| 媒体首发（media） | 议题簇内最早媒体 | "媒体首发" |
| 人物首发（person） | 官员/重要人士/智库首发表述 | "人物首发" |
| 政府/机构首发（gov/org/official） | 官方/机构声明 | "政府/机构/官方首发" |
| 社交媒体首发（social） | 社媒首发（V2.0 深化） | "社交媒体首发" |

**统计佐证的三重检验**（详情页"统计检验结果"卡）：

| 检验 | 它回答什么 | 前端展示 |
|------|-----------|---------|
| 时滞互相关（xcorr） | 首发国与跟随国报道曲线是否领先/滞后 | 最佳时滞天数 + r 值 + p 值 |
| 格兰杰因果（Granger） | 一国报道曲线能否预测另一国曲线 | 方向 + p 值 |
| QAP 相关 | 议题网络结构是否相似 | r 值 + p 值 |

**前端呈现**：世界地图流向动画（首发国红色高亮 + 跟随国蓝色散点 + 红色箭头标注时滞小时数）+ 跟随序列表格（国家/首发媒体/时滞）+ 统计检验结果卡 + 终审结论（评分/结论/推理/担忧项）。

**统计检验的严谨性**：前端明确提示"**统计关联≠因果**——检验结果仅反映报道曲线的统计相关性，不构成因果证据"。这是产品设计哲学的重要体现：**给出证据，也给出证据的边界。**

#### 7.5 人物/机构监测

**一句话**：跟踪"谁在发起议题"，而不只是"哪些媒体在报道"。

- 别名表精确匹配人物/机构实体；同名歧义 confidence 衰减 + needs_review 进人工队列。
- 关键人物、智库与国际组织的首次发声信号列表：新表述（原文+中文）、首发时间、跟进媒体数、关联议题、置信度。
- 动态高频实体黑名单：近 30 天 Top-50 实体写 Redis，聚类/归并比对前过滤（避免被高频刷屏词污染议题）。

**为什么"人物监测"与"媒体监测"分开**：议程设置的发起者不只是媒体——**官员的讲话、智库的报告、国际组织的声明**常常是议题的真正起点，媒体只是放大器。观澜把"人物首发 → 媒体扩散"的链路单独建模（`first_utterance.py`），让分析师能区分：

| 发起类型 | 示例 | 观澜的呈现 |
|---------|------|-----------|
| 人物首发 | 某国官员提出一个新表述 | 人物监测页"发起信号"卡，含原文引用 + 跟进媒体数 |
| 智库首发 | 某智库发布报告提出概念 | 同上，实体类型=智库 |
| 国际组织首发 | 某国际组织声明 | 同上，实体类型=国际组织 |
| 政府首发 | 某国官方声明 | 同上，实体类型=政府机构 |
| 媒体首发 | 某媒体原创报道 | 议题详情页"媒体首发" |

**实体库的工程实现**（`entity_repo.py`）：

- **别名表精确匹配**：同一人物的不同称谓（"泽连斯基" / "Zelensky" / "Volodymyr Zelensky"）映射到同一实体。
- **同名歧义处理**：不同国家的同名人物，confidence 衰减 + `needs_review` 进人工队列，避免误归并。
- **动态黑名单联动**：近 30 天 Top-50 高频实体写 Redis Set（TTL 48h），聚类/归并比对前过滤——防止"特朗普""中国"这类刷屏词把不相关议题黏在一起。
- **黑名单容错**：刷新失败保旧值不抛错（优化非正确性依赖）。

#### 7.6 预警与订阅

**一句话**：把"该关注的信号"推到正确的人面前。

- **预警规则配置**：基于议题、国家与阈值规则的三条件 AND 叠加条件构建器（增长幅度 growth_rate / 报道量 TOP-N / 负面占比 neg_ratio）。
- **通知通道**：站内 / 邮件 / Webhook（企业微信/钉钉/飞书）。
- **预警调度**：15min 周期规则评估 + 通知退避重试执行者（webhook 终态降级邮件并停用通道）+ 订阅日报/周报推送 + 报告导出队列。
- **站内预警中心**：列表 / 标记已读 / 全部已读。
- **订阅管理**：创建/删除/列表 + 免登录 token 一键退订。

**预警规则的三条件构建器**（前端 `AlertRulesPage` + `alertConditions.ts`）：

| 条件类型 | 规则含义 | 示例 |
|---------|---------|------|
| 报道量增幅（growth_rate） | 某议题报道量较基线增幅 ≥ X% | "某国涉华议题报道量增幅 ≥ 50%" |
| 显著性 Top N（top_n） | 某议题显著性进入该国/全局前 N | "议题显著性进入前 10" |
| 负面占比（neg_ratio） | 某议题负面报道占比 ≥ X% | "负面占比 ≥ 30%" |

三条件可 **AND 叠加**（最多 3 个），叠加后生成一句话规则描述（"报道量增幅 ≥ 50% 且 显著性进入前 10"）。规则可启停、删除、显示最近触发时间。

**预警的降级与容错**：

- **退避重试**：通知失败退避重试，webhook 终态降级为邮件，并停用该通道避免反复失败。
- **SMTP 可配**：邮件通道经环境变量注入，未配置不阻塞其他功能。
- **订阅退订**：免登录 token 一键退订，尊重用户对信息流的掌控。

#### 7.7 报告与导出

**一句话**：从发现到成稿，30 分钟。

- **三模板导出**：议题深度报告 / 跨国对比简报 / 周期监测周报。
- **格式**：PDF 与 Word（docx）。
- **异步任务**：创建导出任务 → 排队/生成/完成状态轮询 → 下载。
- **水印与口径声明**：报告含水印"由 AgendaScope 观澜生成 + 数据口径声明"；不含全文，仅标题与摘录（版权友好）；时间窗上限 90 天。

**三个报告模板**：

| 模板 | 适合谁 | 内容 |
|------|-------|------|
| 议题深度报告（topic_deep） | 陈国栋/李思远 | 选定议题的完整深度报告：生命周期、显著性时间线、传播链路、相关文章（标题与摘录）、方法学留痕 |
| 跨国对比简报（compare_brief） | 张建国 | 2–4 国近 N 天报道量对比、首位议题差异、覆盖差异，供决策简报 |
| 周期监测周报（periodic_weekly） | 王晓彤 | 周期性监测周报，覆盖关注国与重点议题的摘要 |

**报告的合规设计**：

- **版权友好**：不含全文，仅标题与摘录——既满足研判需求，又规避新闻版权风险。
- **口径可审计**：水印 + 数据口径声明，任何拿到报告的人都知道数据从哪来、覆盖口径是什么。
- **异步不阻塞**：生成在后台任务队列执行，前端轮询状态，用户可继续其他工作。

#### 7.8 系统管理与安全

**一句话**：私有化部署的完整治理闭环。

- **用户管理**：多用户、角色（admin/普通）、会话自动刷新（access_token 过期拦截 401 → 刷新 → 重试，单飞防并发重复刷新）。
- **审计日志**：时间/actor/action 过滤分页查询与 CSV 导出（admin）。
- **日志查看**：在线日志查看（admin）。
- **许可与诊断**：许可状态与系统诊断（admin）。
- **安装向导**：首次安装初始化向导（`/setup`），10 分钟完成看板配置。

**安装向导的 5 步**（`SetupPage`）：

| 步骤 | 内容 | 说明 |
|------|------|------|
| 1. 环境自检 | CPU/内存/磁盘/Docker/外网连通性 | 前端确认步；Docker 不可用阻止部署 |
| 2. 基础配置 | 系统名称 | 落库 |
| 3. 监控范围 | 勾选监控国家（默认 30 国全选） | 未勾选国家的媒体源将停用 |
| 4. 管理员账号 | 用户名 + 密码（强密码策略） | 至少 10 位，含大写/小写/数字 |

**系统管理 5 个面板**（`SystemPage`）：

| 面板 | 功能 |
|------|------|
| 系统概览（overview） | 系统运行状态与核心指标 |
| 用户管理（users） | 用户列表/角色/启停 |

## 第三部分：设计哲学

> 这一部分是本文档的灵魂。观澜不是"又一个舆情平台"，而是**一套关于"如何把学术方法做成可信产品"的设计主张**。以下每一条哲学，都能在产品中找到具体对应。

### 8. 第一性原理：理论即产品

**主张**：议程设置理论不只是产品的"灵感"，而是产品的**分析内核与默认视图**。

大多数舆情产品是"关键词命中 + 情感打分"的聚合器。观澜把传播学半个世纪的学术积累——McCombs & Shaw 的客体显著性（第一层）、属性议程设置（第二层）、Guo & McCombs 的网络议程设置 NAS（第三层）——直接做成了产品功能：

| 理论层 | 学术方法 | 产品功能 |
|--------|---------|---------|
| 第一层：客体显著性 | 显著性测量（media attention） | 议题聚类 + 显著性排行 + 时间线 |
| 第二层：属性议程设置 | 实质属性 + 情感属性 | 议题分类 + 摘要（实质属性）；负面占比（情感属性） |
| 第三层：网络议程设置 NAS | 议题-属性关联网络显著性转移 | 议题网络图（跨国传播流向） |
| 议程溯源 | 时滞互相关 + Granger 因果 + QAP/MRQAP + intermedia agenda setting | 首发源判定 + 跟随国序列 + 统计佐证卡 |

**为什么重要**：因为"议程设置"这个词在商业产品里已经被滥用成营销话术。观澜把可引用的学术方法做成可点击的产品功能，**让"议程设置识别"从口号变成可审计的测量**。这是竞品（无论高价 SaaS 还是国内厂商）短期无法复制的方法论壁垒——复制需要"传播学方法论 × NLP 工程"的复合知识，属于人才护城河。

**在代码中的体现**：`backend/app/agenda_engine/` 下的 `origin.py`（首发锚点判定）、`stats_evidence.py`（XCorr/Granger/QAP）、`final_review.py`（LLM 终审）、`snapshot.py`（显著性快照）——每一个文件都对应一个可写进论文的方法。

### 9. 第二性原理：覆盖即信用

**主张**：数据质量的可审计性，比数据量更重要。

"主流媒体"是一个模糊概念。观澜把它操作化为**逐国可审计的清单**：维基百科各国报纸列表 + ABYZ News Links + Media Cloud Directory + awesome-rss-feeds + Similarweb 流量排名取交集，得到**合计受众覆盖率 ≥70%** 的媒体集合，并逐国标注覆盖率置信度（高/中/低）。

- **单一事实源**：国家清单集中在 `backend/app/core/countries.py`，全系统派生，杜绝"地图上是一个版本、议题里是另一个版本"的分裂。
- **置信度标注**：前端地图 tooltip、总览页徽章、国家下钻抽屉，处处显示覆盖率置信度。置信度低的国，平台明示"数据覆盖不足"徽章，而不是用旧数据冒充。
- **降级可见**：任何一个环节降级（LLM/聚类/翻译/快照/覆盖），界面用明确的降级徽章标注，而不是默默吞掉。

**为什么重要**：对国安机关与研究者来说，"这份结论的数据基础是否可信、能否引用"是比"有没有结论"更优先的问题。**可审计的覆盖口径，是机构采购与研究引用的信任基础。**当口径本身成为被引用标准后，它还是品牌的护城河。

**在代码中的体现**：`DegradedBadge` 组件定义了 6 类降级徽章（LLM 降级/聚类降级/跨语言匹配不可用/首发源待核实/快照校正中/数据覆盖不足），每一类都有明确的展示文案与 tooltip 原因。**产品把"我知道自己在降级"当成一种功能。**

### 10. 第三性原理：机器会犯错，所以要让纠错成为产品

**主张**：实时流上的聚类与 LLM 判定**必然出错**。与其假装完美，不如把"纠错"做成一等公民。

这是观澜最反直觉也最重要的设计决策。它的逻辑链条：

1. **错误是概率必然**：跨语言聚类、LLM 命名、首发源判定在实时流上必然出错——今天只有零星报道、明天才成形，或某国通讯社转载了别国新闻却被判为首发。
2. **一次误判会摧毁一切**：如果首发源判错了，"新疆棉"类关键案例的证据链就建立在错误首发源上。错误不可怕，**不可纠正的错误才可怕。**
3. **纠错必须随证据自动发生**：等人工补录，实时监测价值归零且人力不可扩展。

于是观澜设计了一套完整的**自我纠错体系**：

| 机制 | 说明 | 用户可见效果 |
|------|------|-------------|
| **议题生命周期状态机** | 萌芽→形成中→已确认→演化→消亡 | 议题卡片的生命周期标签，随证据推进 |
| **次日自动归并** | 新议题先与历史议题跨语言比对，≥0.85 并入旧议题（topic_id 复用） | "该议题已合并至其他议题"重定向 |
| **增量重估与判定修正** | 新证据出现自动重跑首发源判定，变化写 revision_log | 前端标注"该判定已于 X 时修正" |
| **置信度自动升降** | watching→suspected→confirmed 自动升级；降 low 撤销 | 事件状态标签随证据变化 |
| **修正风暴保护** | 24h 修正 >5 次冻结自动修正转人工 | 防止机器在争议事件上反复横跳 |
| **人工确认/否决优先** | 人工可确认事件、否决某条修正、回滚合并 | 修正历史页的确认/否决/回滚操作 |
| **人工锁定字段** | 人工锁定字段机器不推翻 | 防止机器推翻人工结论 |

**核心原则**：**人工校正优先级高于机器；机器不推翻已确认/已归档的人工结论。**

**在代码中的体现**：`revision.py` 的 `append_revision`（actor='machine'/'human'，含 model/prompt_version/trigger_evidence）、`confidence.py` 的修正风暴保护、`api/routes/agenda_events.py` 的人工确认/否决 API。前端"修正历史"页把这条原则做成了完整的交互：查看修正流、人工确认、否决某条修正（需填原因）、排除误报。

**为什么重要**：**一个会自我纠错的系统，比一个假装完美的系统更可信。** 对分析师而言，能看到"机器曾经判错、后来如何修正、我能否否决"，比看到一个静态结论有用得多——这是研判可信度的根基。

### 11. 第四性原理：不撒谎的降级

**主张**：系统任何一环不可用时，宁可降级+明示，也不伪造或默默吞掉。

观澜有一套贯穿全栈的降级哲学：

| 环节 | 不可用时 | 降级行为 | 界面表现 |
|------|---------|---------|---------|
| 云端 LLM | API 不可用/超时率>20% | c-TF-IDF 关键词标签兜底 + P1 告警 + 恢复后回填 | "LLM 降级中"徽章，标签带 `ctfidf_fallback` 留痕 |
| 聚类引擎 | BERTopic 不可用 | 关键词匹配粗聚类降级 + 告警 + 恢复后回填 | "聚类降级中"徽章 |
| 跨语言匹配 | 向量模型不可用 | 跨国匹配暂停，界面展示原文 | "跨语言匹配暂不可用"徽章 |
| 首发源判定 | time_source='crawled' 低置信 | 标注"首发源待核实"进人工队列，不自动告警 | "首发源待核实"徽章 |
| 快照 | 重聚类校正中 | 读侧读上一版 + 标注"校正中" | "快照校正中"徽章 |
| 覆盖率 | 置信度<70% | 明示"数据覆盖不足" | "数据覆盖不足"徽章 |
| 统计检验 | 样本量<100 | 硬性拒绝"数据量不足"，不下显著性结论 | "数据量不足"提示 |
| 情感分析 | 尚未接入（Phase 4） | sentiment 留 NULL 不伪造 | 空缺而非编造 |

**三条铁律**：

1. **不伪造**：LLM 降级时摘要留空，不用模板话术充数；sentiment 未接入就留 NULL，不编造情绪值。
2. **不沉默**：任何降级都在界面上可见、可解释（徽章 + tooltip 原因），并写 P1 告警。
3. **可恢复**：降级期间的数据在恢复后自动回填重算，`backfill_degraded_topics()` 对降级期议题回填重命名/分类/摘要并写 revision_log。

**为什么重要**：舆情研判的产出可能进入上报材料或研究报告。**一份标注了"此处数据覆盖不足"的报告，比一份伪造了完整性的报告更有价值。**"诚实"在别的产品里是道德选项，在观澜里是数据架构。

### 12. 第五性原理：零编程，但不降智

**主张**：面向零编程业务专家，但绝不把产品做成"玩具"——学术严谨性一分不减，只把复杂度藏在工程里。

- **学术级分析，小白级操作**：核心任务 ≤3 步、首次看板配置 ≤10 分钟；但底层跑的是论文级的统计检验（XCorr/Granger/QAP/MRQAP）。
- **方法可追溯可引用**：每个议题名称、分类、摘要、判定都带方法来源与留痕（llm_judgements 表、prompt 版本、revision_log），研究者可在论文/报告中引用。
- **给证据，也给证据的边界**：统计检验结果卡下方永远有"统计关联≠因果"的提示——这既是对用户的诚实，也是学术规范。
- **不替代判断，而是武装判断**：人工确认/否决/回滚操作是产品的一等公民，机器产出只是"建议+证据链"，最终决策权在人。

**在代码中的体现**：`llm_judgements` 表每次判定写模型名+prompt_version+输入/输出快照；`final_review` 字段留 score/verdict/model/prompt_version/reasoning/concerns；`rerun_judgements()` 支持换 prompt 后历史判定批量重跑对比。**这些"方法学保险"全部对用户可见（详情页可查）。**

### 13. 第六性原理：私有化即合规

**主张**：私有化不是部署选项，而是产品形态本身。

- **唯一交付形态**：私有化部署（Docker Compose 一键）——**无 SaaS 形态**。数据不出域、离线内网、等保合规是国家安全机关与涉密研究机构的不可谈判前置条件。
- **云端 LLM/嵌入的合规路径**：LLM 与嵌入经**机构批准的出网通道**走云端 API——**数据不出域，仅文本出域推理**。这是"要 LLM 能力"与"要数据安全"之间的唯一合规平衡点。
- **本地保留**：语言识别（fastText lid.176.bin）本地运行，无 API 依赖。
- **支持离线部署**：离线地图瓦片或内网地图服务、无外部依赖的安装包。
- **审计闭环**：审计日志、许可与诊断、用户与角色管理，构成私有化治理闭环。

**在代码中的体现**：`LLM_`/`NLP_EMBEDDING_` 前缀环境变量集中配置云 API；`run.py` 的 `doctor` 环境预检；部署镜像瘦身（本地模型 2.1GB → 126MB，仅保留语言识别）。

### 13.1 诚实的工程权衡：每条哲学背后的取舍

设计哲学不是免费午餐。每一条背后都有真实的工程权衡——我们把它们摊开，因为**知道"放弃了什么"比"得到了什么"更能体现成熟度**。

| 哲学 | 我们得到了什么 | 我们放弃了什么 | 为什么值得 |
|------|--------------|--------------|-----------|
| 理论即产品 | 方法论壁垒、可引用、可审计 | 上手复杂度（统计检验对零编程用户是负担） | 用"可展开"结构化解——默认只给结论，统计卡可展开 |
| 覆盖即信用 | 逐国可审计口径 | 初始媒体源数量有限（57 国 57 源起步） | 用"自助配源"化解——业务专家可随时补充 |
| 纠错即产品 | 研判可信度、人工掌控 | 额外工程成本（revision_log/回滚/风暴保护） | 一次误判可能摧毁整个证据链，纠错成本远低于误判成本 |
| 不撒谎的降级 | 长期信任、结论置信边界 | 降级期功能不完整 | 研判产出可能进上报材料，假数据比没数据更危险 |
| 零编程不降智 | 锁定业务专家用户群 | 前端开发成本高（四态/动画/空状态） | 10 分钟上手是采购决策的临门一脚 |
| 私有化即合规 | 唯一能进内网的产品形态 | 放弃 SaaS 的规模效应 | 目标客户的数据不出域是硬门槛，SaaS 根本进不来 |

**两条更深的取舍**：

1. **云端 LLM 的合规权衡**：为了要 LLM 能力（命名/分类/摘要/判定），我们接受"仅文本出域推理"。为了保数据安全，我们放弃"在本地跑大模型"。这背后是：**本地 LLM 在可预见的资源约束下无法达到云端模型的命名/摘要质量，而"仅文本出域"恰好是国家安全场景可接受的唯一边界。** 这是两害相权取其轻的清醒选择，不是妥协。

2. **自动归并 vs 人工控制的权衡**：自动归并（≥0.85 向量相似）省去人工，但有误并风险。我们放弃了"完全自动化"（可能误并），也放弃了"完全人工"（不可扩展），选择**"自动归并 + 可拆分回滚 + 合并建议人工确认"**的中间态——机器做粗活，人做判断，两边都不失。

### 14. 设计哲学总结：五根支柱

| 支柱 | 一句话 | 用户可感知的表现 |
|------|-------|-----------------|
| **理论即产品** | 学术方法是产品的分析内核 | 显著性/传播链路/统计佐证是默认视图，可引用 |
| **覆盖即信用** | 数据质量可审计比数据量重要 | 逐国覆盖率置信度、媒体清单单一事实源 |
| **纠错即产品** | 机器会犯错，纠错体系是一等公民 | 修正历史页、人工确认/否决、回滚 |
| **不撒谎的降级** | 宁可降级+明示，也不伪造 | 6 类降级徽章、P1 告警、恢复后回填 |
| **零编程不降智** | 操作简单，方法严谨不减 | 10 分钟上手 + 论文级方法与留痕 |

### 14.1 设计哲学之间的关系：一张相互支撑的网络

这五根支柱不是孤立的五条标语，而是一张**相互支撑的约束网络**。它们彼此加强、彼此校验：

```
              覆盖即信用（数据可信）
                    │
      ┌─────────────┼─────────────┐
      │             │             │
  理论即产品      纠错即产品    不撒谎的降级
 （方法可信）   （结论可信）   （过程可信）
      │             │             │
      └─────────────┼─────────────┘
                    │
              零编程不降智
            （可信度向用户交付）
```

- **理论即产品**支撑**覆盖即信用**：只有测量方法可引用，覆盖口径才值得标注置信度。反过来，只有覆盖可审计，理论测量才有数据基础。
- **纠错即产品**依赖**不撒谎的降级**：一个系统敢承认"我可能判错了"，它才愿意把修正过程完整暴露给用户。反过来，只有纠错体系完善，系统才敢承认降级而不必担心整体可信度崩塌。
- **不撒谎的降级**支撑**覆盖即信用**：置信度低的国"宁缺毋滥"地标注，而不是用旧数据冒充——这正是"覆盖即信用"在运行时的体现。
- **零编程不降智**是四个可信度支柱的用户界面：把"方法可信、结论可信、过程可信、数据可信"完整地呈现给零编程用户，同时不降低学术严谨性。

**换一个角度看，这五根支柱其实是同一个问题的五个侧面：信任。**

> 对国安机关与研究者来说，一个工具最大的价值不是"给了答案"，而是"**答案可以信任、可以审计、可以引用**"。五根支柱从数据、方法、结论、过程、交付五个维度，共同构建这层信任。

### 14.2 我们刻意不做的事（反模式）

设计哲学不仅有"要做什么"，也有"坚决不做什么"。观澜有一份明确的反模式清单：

| 反模式 | 我们为什么不做 | 我们怎么做 |
|--------|---------------|-----------|
| **伪造完整性** | 降级时用模板话术填摘要、未接入的情绪值填 0，短期好看、长期失信 | 摘要留空不伪造，sentiment 留 NULL，明示降级徽章 |
| **隐藏纠错** | 机器判错了悄悄改，用户看到的是"从未出错的完美系统" | 每次修正写 revision_log，前端标注修正时间与触发证据 |
| **术语堆砌** | 把"NAS/QAP/Granger"当营销词甩给零编程用户 | 术语只出现在可展开的技术细节与报告附录，主界面用业务语言 |
| **数据过载** | 把 57 国全部数据一次性铺给用户，制造"很强大"的错觉 | 默认视图只给显著性与健康度，深钻才展开细节 |
| **一次性正确** | 认为判定一次就对，不设计纠错 | 把"错误是概率必然"当设计前提，纠错体系与首次识别同版本交付 |
| **用广度稀释深度** | 一口气扩到 60+ 国、接入社媒全量，NLP 质量与覆盖率置信度还没验证 | 57 国范围内先验证质量，60+ 国按用户需求投票驱动 |

### 14.3 每一个哲学如何成为一行代码

| 哲学 | 在代码中的落点 |
|------|---------------|
| 理论即产品 | `backend/app/agenda_engine/` 的 `origin.py` / `stats_evidence.py` / `final_review.py` / `snapshot.py` |
| 覆盖即信用 | `backend/app/core/countries.py` 单一事实源；前端 `DegradedBadge` 的 `coverage_low` |
| 纠错即产品 | `revision.py` 的 `append_revision`；`confidence.py` 的修正风暴保护；`agenda_events.py` 人工确认/否决 API |

### 14.4 常见疑问：这些哲学会不会牺牲产品力？

**疑问：降级徽章会不会吓跑用户？**
不会。降级徽章只出现在真正降级的环节，正常时界面完全干净。而且对研判用户来说，"这里降级了"比"这里看起来完美"更有用——它告诉你**结论的置信边界在哪**。一个分析师宁可看到一个"数据覆盖不足"的徽章并据此调整研判力度，也不愿基于一份伪装完整的数据给出错误结论。

**疑问：把纠错全程暴露给用户，会不会显得产品不成熟？**
恰恰相反。纠错体系的存在证明产品**知道自己会错**，并有完整的机制应对。这是成熟度的标志——就像飞机有故障处理手册，不是飞机不成熟，而是它把风险纳入了设计。反观那些"看起来永远正确"的产品，一旦被用户发现一次误判，信任会瞬间崩塌。

**疑问：学术方法做进产品，会不会太重、零编程用户用不了？**
不会。学术方法在**后端**跑，零编程用户看到的是**地图、时间线、传播链路图**这些直观视图。统计检验结果、方法论留痕是"可展开"的深度层——业务专家可以只看结论，研究者可以钻到方法。**复杂度藏在工程里，简单暴露给用户，严谨保留在留痕里。**

### 14.5 设计哲学收束：观澜相信什么

走到这里，我们把五根支柱收束成一句产品的自我认知：

> **观澜相信：在舆情研判这个领域，可信比炫目更重要，可纠错比永远正确更重要，可审计比覆盖所有更重要，能进内网比功能更多更重要。**

这不是一句口号，而是刻在架构里的判断：

- **可信比炫目**：降级徽章不炫目，但让人可信；统计卡不炫目，但让结论可信。
- **可纠错比永远正确**：我们承认机器会错，所以把纠错做成产品功能——这比假装完美更成熟。
- **可审计比覆盖所有**：57 国 ≥70% 可审计口径，胜过"号称覆盖全球"的不可验证承诺。
- **能进内网比功能更多**：私有化形态是目标客户的硬门槛，进得去内网，功能才有意义。

**为什么这对客户重要**：当你在采购评估中比较舆情平台时，你真正在问的不是"谁功能多"，而是"**谁的结论我敢引用、敢上报、敢写进报告**"。观澜的每一根哲学支柱，都在回答这个问题。

### 16.1 管线即 Worker：九个异步管线的分工

观澜的核心管线由**九个独立 worker 进程**协作完成。它们各自职责单一、独立调度、单任务失败不阻塞其他任务——这是"管线可靠"的工程基础。

| Worker | 职责 | 调度 |
|--------|------|------|
| `collector.worker` | 采集调度：重点源 RSS 高频轮询 + GDELT 兜底 | 周期调度 |
| `nlp_worker` | 语言识别 → 向量化 → ES 同步 → 延迟埋点 | 消费 nlp 队列 |
| `cluster_worker` | 在线归簇（消费 nlp:embedded）+ 每小时重聚类校正 | 周期 + 消费队列 |
| `naming_worker` | 待命名议题 → LLM 命名/分类/摘要回填 | 轮询 + LLMTaskQueue |
| `agenda_worker` | 次日归并 / 消亡扫描 / 实体黑名单刷新（三任务独立调度，启动即首轮全触发） | 60min/60min/24h |
| `snapshot_worker` | 国家×议题显著性快照 15min 刷新 | 15min |
| `detection_worker` | 活跃议题全链路检测（首发锚点/跟随序列/统计佐证/事件判定/终审） | 周期 |
| `alerting_worker` | 预警规则评估 / 通知退避重试 / 订阅推送 / 报告导出队列 | 15min |

**为什么要拆成 9 个 worker**：

1. **故障隔离**：一个 worker 崩了（如 LLM 依赖挂了），其他 8 个照常运行，采集不中断。
2. **独立伸缩**：LLM 密集的 `naming_worker` 可单独限流（`LLM_MAX_CONCURRENCY=2`），采集密集的 `collector.worker` 独立吞吐。
3. **语义边界**：每个 worker 对应管线上的一层（采集/理解/议程/研判/呈现），职责清晰，新算法可替换单层而不动全链路。

### 16.2 聚类引擎的工程细节

观澜的聚类引擎（`backend/app/clustering/`）是"议题从哪来"的核心，值得展开：

**双策略并行评估**：

| 策略 | 原理 | 适用 |
|------|------|------|
| BERTopic 主线 | UMAP 降维 + HDBSCAN 聚类 + c-TF-IDF 主题提取 | 高维语义结构清晰时 |
| Agglomerative 硬阈值 | cosine 0.25，average linkage | BERTopic 失效/超大簇时 |

**超大簇黑洞护栏**：单簇占比 >80% 触发回落——防止某国语言"黑洞"把大量议题吸进一个簇。

**在线增量双阈值归簇**：

| 阈值 | 用途 | 效果 |
|------|------|------|
| T_event=0.85 | 归簇（并入既有议题） | 跟进报道并入议题 |
| T_dup=0.95 | 判重（判定重复） | 重复报道不新建议题 |
| 孤证 | 都不满足 | 保留为 size=1 nascent 微簇 |

**每小时重聚类校正**：

- 对近 24h 窗口做全局重聚类，修正在线归簇的漂移。
- 校正期间读侧读上一版快照并标注"校正中"（降级徽章 `snapshot_outdated`）。
- 校正完成发布 Redis 快照，前端自动刷新。

**聚类降级链**：双策略均不可用 → 关键词匹配粗聚类降级（`cluster_method=keyword_fallback`）+ P1 告警 + 恢复后回填。

### 16.3 LLM 服务的工程细节

观澜的 LLM 服务（`backend/app/llm/`）承担命名/分类/摘要/首发表述判定/终审五个职责，全部走云端 API（讯飞星辰 MaaS，OpenAI 兼容）：

**结构化输出与校验**：

- prompt 内嵌 JSON Schema 强约束 + pydantic 校验，解析失败重试 1 次后单点降级。
- 未引入 outlines/约束解码——因为输出 schema 极简（命名/分类/摘要字段），不值得引入解码库的复杂度。

**异步批处理**：

- `LLMTaskQueue`（asyncio 队列 + 小窗口聚批 + 独立线程推理）。
- 主链路投递即返回，不阻塞采集——**LLM 慢不影响采集快**。

**并发限制**：

- `LLM_MAX_CONCURRENCY`（默认 2）线程信号量，跨命名/检测/终审/首发表述统一限流，对齐外部 API QPS/并发配额。

**降级链**：

- 调用失败/超时率 >20%（滑窗）或 API 不可用 → c-TF-IDF 关键词标签兜底（`naming_method=ctfidf_fallback`，分类归「其他」，摘要留空不伪造）+ P1 告警（1h 防抖）+ WARN 日志。
- 恢复后 `backfill_degraded_topics()` 对降级期议题回填重命名/分类/摘要并写 revision_log。
- worker 每轮做恢复探针（真实推理验证），恢复后自动回填。

**prompt 版本管理**：

- 命名/分类/摘要模板带版本号（`app/llm/prompts.py` 注册表，只增不改）。
- 每次判定写 `llm_judgements` 表（模型名 + prompt_version + 输入/输出快照 + 耗时）。
- `rerun_judgements()` 支持换 prompt 后历史判定批量重跑对比——**这支撑了"方法学可演进、历史可复核"**。

### 16.4 快照引擎

`snapshot.py` + `snapshot_worker` 每 15 分钟刷新国家×议题显著性：

- **计算内容**：显著性得分/排名/top_attributes/network_metrics。
- **幂等写库**：UPSERT，UK country×topic×window×granularity——重复刷新不产生脏数据。
- **超时保护**：单次 ≤5 分钟超时保留上版；连续 3 次失败写 alerts P1 告警。
- **不伪造**：sentiment 留 NULL 不伪造（Phase 4 情感分析接入后回填）——这是"不撒谎的降级"在快照层的体现。

### 16.5 数据层与持久化

| 组件 | 用途 | 关键点 |
|------|------|--------|
| PostgreSQL + pgvector | 文章/议题/事件/实体持久化 + 向量检索 | `vector(1024)` 存储 bge-m3 嵌入 |
| Redis | 在线归簇、实体黑名单、快照发布、任务队列 | 黑名单 TTL 48h；快照 UPSERT |
| Elasticsearch | 相关文章全文检索 | 全文检索不可用时降级为基础匹配（`snapshot_outdated` 徽章） |
| alembic | 数据库迁移 | 14 张核心表；`0009_embedding_dim_1024` 把向量从 768 升到 1024 |

### 16.6 采集层的实时性如何保证

**P95 ≤ 30 分钟 / 红线 ≤ 2 小时**的实时性承诺，靠三层保障：

1. **RSS 高频轮询**：重点源 1–5 分钟轮询一次，多数新闻在发布后几分钟内被采集。
2. **GDELT 兜底**：每 15 分钟更新一次，为 RSS 未覆盖的媒体提供兜底，刚好满足 2 小时红线。
3. **RSSHub 补源**：无 RSS 的媒体通过 RSSHub 聚合器补源。

**延迟埋点**：`nlp_worker` 对每篇新闻从发布到平台可见的延迟做埋点，支撑 P95 指标的可度量性与持续优化。若某国违约率 >1%，对该国增加 sitemap 爬虫或商业 API 补充源。

### 17. 降级与自愈架构

- **LLM 降级链**：调用失败/超时率 >20%（滑窗）或 API 不可用 → c-TF-IDF 关键词标签兜底 + P1 告警（1h 防抖）+ WARN 日志；恢复后 `backfill_degraded_topics()` 回填。
- **聚类降级链**：双策略（BERTopic + Agglomerative）均不可用时 → 关键词匹配粗聚类降级（`cluster_method=keyword_fallback` + P1 告警 + 恢复后回填）。
- **源健康状态机**：`failed/degraded` 连续 2 次成功均恢复 `active`；单任务失败不阻塞其他任务。
- **快照容错**：单次 ≤5min 超时保留上版；连续 3 次失败写 P1 告警。
- **事件检测容错**：LLM 降级时整轮回落 `media_time_fallback` 并写 P1 告警。
- **预警通知退避**：webhook 终态降级邮件并停用通道。

### 18. 数据安全与合规架构

- **数据不出域**：私有化部署，数据留在自有服务器/内网。
- **仅文本出域推理**：LLM 与嵌入经机构批准出网通道，只发送待推理文本，不发送用户账户/配置/全文数据库。
- **本地模型最小化**：仅保留 fastText 语言识别（无 API 替代），LLM/嵌入全部云端化（镜像瘦身）。
- **审计日志**：时间/actor/action 完整审计，CSV 导出。
- **角色与权限**：admin/普通用户两级，敏感操作（新增源/系统管理）需 admin。
- **会话安全**：access_token 过期自动刷新（单飞防并发），刷新失败清空会话跳登录页。

### 18.1 合规的三个层次

| 层次 | 要求 | 观澜的对应 |
|------|------|-----------|
| **数据不出域** | 数据留在机构自有服务器/内网 | 私有化 Docker Compose 部署，无 SaaS |
| **仅文本出域推理** | LLM/嵌入调用经机构批准的出网通道，仅文本出域 | `LLM_`/`NLP_EMBEDDING_` 环境变量集中配置；`run.py doctor` 预检 |
| **审计闭环** | 涉密场景的保密审计日志 | 审计日志面板 + CSV 导出；用户/角色管理；许可与诊断 |

**关键边界**：观澜调用云端 LLM 时，**只发送待推理的文本片段**（命名/分类/摘要所需的最小文本），不发送用户账户信息、系统配置、全文数据库。这个边界是"要 LLM 能力"与"要数据安全"的唯一合规平衡点，也是与纯 SaaS 竞品的决定性错位。

### 18.2 部署形态与资源要求

| 形态 | 说明 | 资源 |
|------|------|------|
| 单机 Docker Compose | 全栈起一个容器组 | db/redis/es/rsshub/backend + 8 worker |
| 私有化内网 | 离线地图瓦片/内网地图服务、无外部依赖安装包 | 同上，隔离网络 |
| 涉密内网 | 等保 2.0 三级配套文档、保密审计日志、专属实施 | 同上，涉密适配 |

**云 API 模式下的资源优势**：本地模型目录从 2.1GB 降至 126MB（仅保留语言识别），运行内存从本地 LLM 的约 4.9GB 降至约 2.5GB，镜像从 11.2GB 瘦身至 4.7GB（torch 改 CPU-only wheel）。**云端化不仅是合规需求，也大幅降低了私有化部署的资源门槛。**

### 20.1 逐个竞品：他们为什么追不上

**Meltwater / Brandwatch / Talkwalker（商业 SaaS）**

- **没动机**：他们的付费客户是 PR 团队与品牌方，要的是"品牌提及量、社媒情绪、竞品监测"，不是"谁在设置国际议程"。为安全与研究细分投入议程溯源研发，对其营收没有意义。
- **进不了内网**：纯 SaaS 形态，数据托管在厂商云端。国家安全机关的"数据不出域"硬要求直接排除——这不是价格问题，是合规门槛。
- **没有理论能力**：议程设置三层分析（NAS/Granger/QAP）需要"传播学方法论 × NLP 工程"的复合人才，商业团队不养这种配置。

**GDELT / Media Cloud（免费学术数据）**

- **没有产品化**：只给原始数据与 API，不提供"谁是首发源、跟随序列、时滞、传播链路"的判定。他们的价值定位是数据基础设施，不是研判产品。
- **误差未清洗**：GDELT 自动抽取存在转写/翻译/实体识别误差（官方与学界均提示）。观澜在此基础上做清洗、建模与产品化。
- **定位不冲突**：GDELT 是观澜的兜底数据源，Media Cloud 是覆盖率口径的输入之一——**他们不是对手，是队友。**

**蚁坊 / 清博（国内舆情厂商）**

- **覆盖短板**：以国内舆情为主，全球主流媒体覆盖弱——没有 57 国 ≥70% 的可审计口径。
- **无理论框架**：面向舆情处置（预警、简报），没有议程设置理论分析框架与跨国议程溯源。
- **出海能力弱**：国际关系研究需要的全球南方语言（印地语、印尼语、斯瓦希里语等）覆盖不足。

**TrendRadar（开源中文热搜）**

- **场景错位**：面向中文热搜/社媒，无全球主流媒体体系，无理论分析层。
- **许可证限制**：GPL-3.0 决定其代码不可直接并入商业发行版，仅作架构参考。

> **共同点**：所有竞品都缺"议程溯源 × 自我纠错 × 私有化内网"这个组合。这个组合需要**理论能力 + 工程能力 + 合规交付能力**三者的交叉——这正是观澜的护城河所在。

### 21. 护城河

1. **议程溯源与议程设置理论分析引擎**：首发源判定、跟随国序列与时滞测量、传播链路图与议程设置事件自动判定，加上完整计算测量链（时滞互相关 + Granger + QAP/MRQAP + intermedia agenda setting）。商业竞品没有动机为安全与研究细分投入该研发，开源项目没有理论能力与产品化能力同时具备的团队。
2. **70% 覆盖率口径**：逐国可审计媒体清单是持续运营出来的数据资产，各商业平台均不公开逐国覆盖统计。口径本身成为被引用标准后，形成品牌护城河。
3. **安全合规交付能力**：私有化内网部署、数据不出域、审计日志——把 SaaS 竞品与绝大多数国内舆情厂商挡在门外，且随测评资质与标杆案例积累持续加深。
4. **零编程可用性**：把学术级分析的门槛降到零，直接锁定被 GDELT/Media Cloud 拒之门外的业务专家用户群。

**护城河如何随时间加深**：

| 护城河 | 今天 | 12 个月后 | 3 年后 |
|--------|------|-----------|--------|
| 议程溯源引擎 | 首发源/跟随序列/时滞/统计佐证 | 历史案例回放准确率 ≥80%，判定更准 | 大规模历史案例库 + 判定方法论成为事实标准 |
| 覆盖率口径 | 57 国清单 + 置信度 | 60+ 国，置信度提升 | 口径被学术引用，成为行业基准 |
| 合规交付 | Docker + 审计日志 | 等保配套文档 + 更多部署案例 | 测评资质 + 标杆案例 |
| 零编程可用性 | 10 分钟配置 | 模板库 + 用户口碑 | 体验复利 + 社区沉淀 |

### 22. 竞争定位声明

> "Unlike Meltwater / Talkwalker（高价 SaaS 舆情平台）、GDELT / Media Cloud（免费但需要编程的数据源）与蚁坊/清博（国内舆情厂商），AgendaScope 观澜把议程设置行为识别——首发源判定、跟随国序列、时滞测量与传播链路证据链——连同议程设置理论三层分析引擎，做成私有化内网部署、零代码可用的产品，这意味着国家安全机关与国际关系研究机构的业务专家都能在 2 小时延迟红线内，亲眼看到谁在为世界设置议程。"

### 23. 与自我纠错相关的竞品差异（为什么我们独此一家）

我们观察到一个重要事实：**竞品要么不做判定（所以无需纠错），要么做了判定但拒绝承认会错。**

- GDELT/Media Cloud：只给数据与检索，不给判定，自然无需纠错——但也没有产品化价值。
- 商业 SaaS：给关键词与情感面板，判定维度浅（不涉及首发源、跟随国序列这类高风险的因果判定），自然不易暴露错误——但也无法回答"谁在设置议程"。
- 国内舆情厂商：以国内处置为主，判定维度不涉及跨国议程溯源。

**只有做议程溯源（高风险判定）的产品，才需要完整的纠错体系；也只有把纠错体系做成一等公民的产品，才敢做议程溯源。** 观澜的"议程溯源 × 自我纠错"组合，是市场独此一家的品类定义。

## 第六部分：数据可信度、评测与开放性

> 这一部分回答一个对客户最关键的问题：**观澜声称的能力，凭什么可信？** 我们把数据质量承诺、评测方法与开放性一次性讲清楚。

### 24. 质量承诺：我们承诺什么，不承诺什么

| 指标 | 承诺 | 验证方法 |
|------|------|---------|
| 实时性 | 新闻发布→平台可见 P95 ≤ 30 分钟，红线 ≤ 2 小时 | Alpha 期对 57 国重点源 2 周延迟实测打点 |
| 覆盖率 | 每国主流媒体合计受众覆盖率 ≥70% | 逐国按操作化流程产出清单，2 名领域专家评审 |
| 议题可解释性 | 聚类与 LLM 命名结果可解释性 ≥4/5（估算目标） | Beta 期 10 名研究者人工评估 |
| 议程溯源准确率 | 议程设置事件识别准确率 ≥80%（估算目标） | Beta 期"新疆棉"等历史案例回放验证 |
| 自我纠错正确率 | 次日归并正确率 ≥90%、首发判定修正留痕率 100%（估算目标） | Beta 期构造"首日孤证→次日多国跟进"案例集回放 |
| 可用性 | 首次看板配置 ≤10 分钟，核心任务 ≤3 步 | Beta 期 20 名目标画像用户可用性测试 |
| 系统可用性 | 99.5% | 私有化部署监控 |

**我们刻意不承诺的**：

- **不承诺**"100% 正确判定"——实时流上的聚类与判定必然有误差，这是科学现实。我们承诺的是**误差可见、可追溯、可纠错**。
- **不承诺**"完全覆盖全球"——我们承诺 57 国 ≥70% 可审计口径，60+ 国按用户需求驱动扩展，不追求广度稀释深度。
- **不承诺**"因果证据"——统计检验只报告相关性，"统计关联≠因果"是每个检验卡的默认提示。

### 25. 评测方法：回放验证与专家评审

观澜的质量主张不是"自我感觉良好"，而是有明确评测方法：

#### 25.1 历史案例回放

用已经发生、已有公认结论的历史案例，回放观澜的判定链路，验证"机器能否复现人类专家的研判"：

| 案例类型 | 回放方法 | 通过标准 |
|---------|---------|---------|
| "新疆棉"类跨国扩散 | 回放首发源判定、跟随国序列、时滞测量 | 首发源/序列/时滞与公认结论一致 |
| "首日孤证→次日多国跟进" | 回放次日自动归并、议题成形 | 次日归并正确率 ≥90%（估算） |
| 议题误并/误拆 | 构造相近议题对，回放归并/分裂 | 误并/误拆率可控（估算） |
| 首发源误判 | 构造"通讯社转载却被判首发"案例 | 修正留痕率 100%，低置信进人工队列 |

#### 25.2 专家评审

### 26. 方法学开放性：让"结论怎么来的"可以复核

观澜的"开放性"不是开源代码，而是**方法学透明**——任何结论都可以回答"怎么来的、依据什么、何时判定、用什么模型"。这是比开源代码对客户更有价值的开放：

| 透明度维度 | 用户能看到什么 | 支撑机制 |
|-----------|--------------|---------|
| 判定来源 | 首发源判定的依据（最早时间戳/通讯社优先/LLM 表述引用） | 议题详情页 + 事件详情页字段 |
| 模型与版本 | 每条判定用的什么模型、什么 prompt 版本 | `llm_judgements` 表 + `final_review` 字段 |
| 修正历史 | 每次修正的前后值、actor、触发证据、时间 | `revision_log` + 修正历史页 |
| 统计依据 | 每个检验的 p 值、方向、样本量 | 统计检验结果卡 |
| 数据基础 | 每个国家的媒体清单与覆盖率置信度 | 总览页 + 地图 tooltip |
| 降级状态 | 每一环是否在降级、降级到什么口径 | 6 类降级徽章 + P1 告警 |

**学术引用友好**：研究者可以把观澜的方法学留痕写进论文的"研究方法"一节——`llm_judgements` 表记录了模型名、prompt 版本、输入/输出快照、耗时，`rerun_judgements()` 支持换 prompt 后历史判定批量重跑对比。**这支撑了"方法学可演进、历史可复核"**——研究者可以证明"我们的结论是在某模型、某版本下得出的，且可以复现"。

### 31.1 部署场景对比

| 场景 | 形态 | 出网 | 适用 | 关键配置 |
|------|------|------|------|---------|
| 标准私有化 | Docker Compose 单机 | 允许出网（云端 LLM/嵌入） | 高校/研究院/智库 | `LLM_`/`NLP_EMBEDDING_` 环境变量 |
| 受限内网 | Docker Compose + 内网镜像 | 仅经批准出网通道 | 涉密内网 | 代理配置；离线地图瓦片 |
| 完全离线 | 无外部依赖安装包 | 禁止出网 | 高保密场景 | 本地 fastText 语言识别；LLM 降级 c-TF-IDF；离线地图 |

**三种场景的取舍**：

- **标准私有化**：功能最全（云端 LLM 命名/分类/摘要/判定），需机构批准出网通道。
- **受限内网**：折中——数据不出域、仅文本经批准通道出域推理，保留云端 LLM 能力。
- **完全离线**：最安全（零出网），但 LLM 降级为关键词标签兜底，命名/摘要质量下降。

**关键原则**：无论哪种场景，**采集、聚类、判定、纠错、看板核心功能都完整可用**——降级的是"锦上添花"的 LLM 文本质量，不是核心研判链路。

### 37. 数据资产属于谁

一个常被忽视的问题：**用了观澜之后，数据到底是谁的？**

- **出域最小化**：仅文本出域推理，且只发送推理所需的最小文本，不传账户/配置/全文库。
- **可导出**：报告（PDF/Word）、数据（CSV）、审计（CSV）均可导出，机构随时可以带走自己的数据。
- **可退订**：订阅免登录 token 一键退订，用户对信息流有完全掌控。

这不仅是合规要求，也是信任基础：**机构花了钱和时间运营出来的数据资产，永远属于机构。**

## 附录

### A. 常见问题（FAQ）

**Q1：观澜是 SaaS 还是私有化部署？**
观澜**只有私有化部署形态，无 SaaS**。数据留在机构自有服务器/内网，这是国家安全机关与涉密研究机构的不可谈判前置条件。

**Q2：云端 LLM/嵌入调用，数据会出境吗？**
**数据不出域，仅文本出域推理**。观澜经机构批准的出网通道调用云端 API，只发送命名/分类/摘要/判定所需的最小文本片段，不发送用户账户、系统配置、全文数据库。机构可自行决定是否批准出网通道；不批准时降级为本地兜底（c-TF-IDF 关键词标签），并保持完整功能。

**Q3：需要编程能力吗？**
**不需要**。目标用户就是零编程基础的业务专家（分析师/研究员）。核心任务 ≤3 步、首次看板配置 ≤10 分钟、Docker Compose 一键部署。

**Q4：为什么有"降级徽章"？系统是不是不稳定？**
恰恰相反。降级徽章是**诚实的设计**：系统任何一环不可用时，宁可降级+明示，也不伪造数据。对研判用户来说，"这里降级了"比"这里看起来完美"更有用——它告诉你结论的置信边界在哪。降级期间数据恢复后自动回填重算。

**Q5：为什么机器判定的结论还能被修正？**
因为实时流上的聚类与判定**必然有误差**。观澜把纠错做成一等公民：每次修正写 revision_log，前端标注修正时间与触发证据，分析师可人工确认/否决/回滚。**一个会自我纠错的系统，比一个假装完美的系统更可信。**

**Q6：覆盖 57 国的"≥70% 覆盖率"是什么口径？**
每国主流媒体按可审计的操作化流程（维基百科 + ABYZ + Media Cloud + awesome-rss-feeds + Similarweb 交集）估算合计受众覆盖率，逐国标注置信度。这是学术上可辩护、业务上可审计的独家口径。

**Q7：实时性怎么保证？**
重点源 RSS 高频轮询（1–5 分钟）+ GDELT 兜底（15 分钟更新）+ RSSHub 补源。新闻发布到平台可见 P95 ≤ 30 分钟，红线 ≤ 2 小时，延迟有埋点可度量。

**Q8：报告会包含全文吗？会不会有版权问题？**
**不含全文**，仅标题与摘录，并含水印"由 AgendaScope 观澜生成 + 数据口径声明"。既满足研判需求，又规避新闻版权风险。

**Q9：数据是谁的？**
**机构的**。所有数据存储在机构自有服务器/内网，可导出（PDF/Word/CSV/审计），机构随时可以带走自己的数据资产。

**Q10：支持哪些通知通道？**
站内 / 邮件 / Webhook（企业微信/钉钉/飞书）。预警规则支持三条件 AND 叠加，通知失败自动退避重试。

**Q11：我的机构有一家媒体想加入监控，怎么加？**
自助配源：粘贴媒体 URL → 试运行抓取样例核对 → 确认入库（需 admin）。无需懂任何技术配置。

**Q12：和商业舆情平台（Meltwater 等）比，观澜的优势在哪？**
①议程溯源与议程设置行为识别（竞品没有）；②议程设置理论三层分析（竞品没有）；③57 国 ≥70% 可审计覆盖率口径（竞品不公开逐国统计）；④私有化内网部署、数据不出域（竞品纯 SaaS 进不了内网）；⑤价格约为竞品的 1/3–1/10。

**Q13：和免费的 GDELT/Media Cloud 比呢？**
它们只有原始数据与 API，需要编程能力才能分析；观澜提供产品化的分析看板、议程溯源、预警与报告，目标用户是零编程业务专家。

**Q14：观澜会接入社交媒体数据吗？**
当前**刻意不做**社交媒体全量监控。V2.0 将接入公众议程数据（社媒/搜索趋势作为公众议程代理，与媒体议程做时滞互相关与 Granger 因果）。

**Q15：如何保证数据不被误用？**
角色权限分级（敏感操作需 admin）+ 完整审计日志（时间/actor/action，CSV 导出）+ 数据所有权明确属于机构 + 人工确认/否决优先于机器。

### B. 术语表

| 术语 | 定义 |
|------|------|
| **议程设置（Agenda Setting）** | 媒体通过报道显著性影响公众对议题重要性的判断（McCombs & Shaw） |
| **客体显著性（第一层）** | 媒体决定"公众想什么"——议题在媒体议程中的显著性测量 |
| **属性议程设置（第二层）** | 媒体影响"公众怎么想"——议题属性的显著性（实质属性+情感属性） |
| **网络议程设置 NAS（第三层）** | 议题-属性关联网络的显著性转移（Guo & McCombs） |
| **议程溯源** | 识别议程设置的发起者（国家/媒体/人物）与跨国传播路径 |
| **首发源（Origin）** | 议题簇内最早发布的媒体/人物/国家 |
| **跟随国序列（Follower Sequence）** | 各国首篇报道按时间差升序的序列 |
| **时滞（Lag）** | 某国首篇报道与首发源的时间差（小时） |
| **XCorr** | 时滞互相关，检测两条报道曲线的领先/滞后关系 |
| **Granger 因果** | 统计检验一国报道曲线能否预测另一国曲线 |
| **QAP/MRQAP** | 网络相关分析，检验议题网络结构的相似性 |
| **intermedia agenda setting** | 媒体间议程设置——某媒体议程影响其他媒体议程 |
| **显著性与显著性分数** | 议题在特定国家/时间窗的报道权重 |
| **生命周期状态机** | 萌芽→形成中→已确认→演化→消亡 五态 |
| **回声消除** | 把多国对同一议题的重复报道折叠到同一节点，保留来源但不重复计数 |
| **孤证微簇（nascent）** | size=1 的萌芽议题，仅有单一来源报道 |
| **次日归并** | 新议题与历史议题跨语言比对后并入（topic_id 复用） |
| **revision_log** | 判定修正留痕（字段/前后值/actor/触发证据） |
| **llm_judgements** | LLM 判定留痕表（模型名+prompt 版本+输入/输出快照+耗时） |
| **no_merge_with** | 不可合并名单——防止误并/拆分的议题对再次合并 |
| **fastText** | 本地运行的语言识别模型（176 种语言，无 API 依赖） |
| **bge-m3** | 云端跨语言嵌入模型（SiliconFlow，1024 维），把不同语言映射到同一向量空间 |
| **BERTopic** | 主题聚类算法（UMAP+HDBSCAN+c-TF-IDF），观澜聚类主线 |
| **c-TF-IDF** | 关键词标签兜底方法（LLM 不可用时给议题命名） |
| **70% 覆盖率口径** | 每国主流媒体合计受众覆盖率 ≥70% 的可审计操作化定义 |
| **DegradedBadge** | 前端降级徽章组件，明示 6 类降级状态 |
| **P95 ≤ 30 分钟** | 新闻发布到平台可见的第 95 百分位延迟 ≤30 分钟 |
| **快照（Snapshot）** | 国家×议题显著性 15 分钟刷新一次的实时视图 |
| **修正风暴保护** | 24h 修正 >5 次自动冻结机器修正，转人工处置 |

### C. 方法论可信度：这些数字怎么来的

- **覆盖率**：57 国逐国按"维基百科 + ABYZ + Media Cloud + awesome-rss-feeds + Similarweb 交集"操作化估算，逐国标注置信度。
- **首发源判定**：议题簇内最早 published_at UTC，通讯社/机构双通道并列优先；低置信标注"待核实"。
- **跟随序列**：14 天窗口、仅原创节点、各国首篇 lag_hours 升序。
- **统计佐证**：样本量 ≥100 才下显著性结论；"统计关联≠因果"为默认提示。
- **LLM 判定**：每次判定写 llm_judgements 表（模型名+prompt 版本+输入/输出快照+耗时），可重跑对比。

### C.1 局限性坦诚声明

一份可信的产品介绍，也应该坦诚边界。观澜当前已知的局限性与应对：

| 局限性 | 坦诚说明 | 我们的应对 |
|--------|---------|-----------|
| 媒体源数量 | 每国 1 个代表源起步（57 国 57 源），非全覆盖 | 自助配源 + 国别扩展按需驱动；≥70% 覆盖率口径可审计 |
| 情感分析 | 第二层情感属性深化（Phase 4）未完全交付 | sentiment 留 NULL 不伪造；负面占比已有基础版 |
| 公众议程 | 社媒/搜索趋势未接入（V2.0） | 明确 out of scope，不假装有 |
| 判定误差 | 实时流上聚类/判定必然有误差 | 纠错体系 + 人工否决优先 |
| 统计解释 | 统计关联≠因果 | 每个检验卡默认提示 |
| LLM 依赖 | 云端 LLM 不可用时命名/摘要质量下降 | 降级链 + 恢复后回填 |

**为什么写这些**：因为"观澜相信可信比炫目更重要"（见 14.5）——如果连自己的局限性都不坦诚，凭什么让客户相信我们对数据的标注是诚实的？

### F. 数据流完整示例：一篇多语种报道如何聚合

为了把"跨语言聚合"讲透，我们用一个具体例子展示一篇非英语报道如何进入议题：

**场景**：某巴西葡语媒体发布一篇关于"亚马孙雨林国际协议"的报道。

| 阶段 | 发生了什么 | 技术 |
|------|-----------|------|
| 1. 采集 | RSS 轮询抓到该葡语报道 URL | collector |
| 2. 正文抽取 | trafilatura 抽取正文 | trafilatura |
| 3. 语言识别 | fastText 识别为 `pt`（葡萄牙语） | fastText |
| 4. 向量化 | 云嵌入把葡语正文转为 1024 维向量 | bge-m3 API |
| 5. 归簇 | 与同日西班牙语/英语的"亚马孙协议"报道 cosine ≥0.85，归入同一议题 | 在线归簇 |
| 6. LLM 命名 | 云端 LLM 为议题生成可读名称与分类（含多语输入） | 讯飞星辰 |
| 7. 议题更新 | 议题覆盖国家 +1（巴西），报道数 +1，显著性更新 | 议题生命周期 |
| 8. 快照刷新 | 下一轮快照把"巴西 × 该议题"显著性写入 | snapshot |
| 9. 呈现 | 分析师在全球总览点巴西，看到该议题进入 Top | 前端地图 |

**关键点**：第 4 步的跨语言向量是"法国媒体的『新疆棉』与日本媒体的『Xinjiang cotton』能聚到同一议题"的工程基础。**语言不通，但语义向量同空间**——这正是跨语言议程分析区别于单语言舆情产品的核心能力。
