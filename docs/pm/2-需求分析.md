## 第一部分：需求分析汇总

### 一、业务需求

> **核心问题**: 产品要帮企业实现什么商业目标？为什么要做？值不值得做？

**为什么做**：全球媒体情报市场被 Meltwater（约 $15,000/年起）、Brandwatch（年合同约 $10,000–15,000 起，第三方采购中位 ~$50,000/年）、Talkwalker（中位约 $27,000/年）等高价 SaaS 占据（来源：调研报告1，[syncly 三方对比](https://syncly.app/blog/brandwatch-vs-meltwater-vs-talkwalker)、[CheckThat Brandwatch 定价](https://checkthat.ai/brands/brandwatch/pricing)、[CheckThat Talkwalker 定价](https://checkthat.ai/brands/talkwalker/pricing)）；免费端只有 GDELT、Media Cloud 这类无产品化界面的数据基础设施。中间存在巨大空档：**没有任何产品把议程设置理论（客体显著性 → 属性议程设置 → 网络议程设置 NAS）做成零技术门槛的实时监控产品**。对国家安全机关与国际关系/国际政治/国家安全研究机构而言，更关键的是识别"议程设置"行为本身——某国（媒体、官员、重要人士、智库、国际组织）率先提出一个议题，随后多国媒体跟随报道——目前没有任何工具能自动识别此类事件并给出首发源、跟随国序列与时滞的完整证据链。同时 RSS + GDELT（15 分钟更新、100+ 语言、免费，来源：[GDELT 官网](https://www.gdeltproject.org/)）+ BERTopic + 云端 LLM API（讯飞星辰 MaaS）技术栈已经成熟，使私有化 Docker Compose 部署的实时全球媒体议程监控在成本上首次可行——LLM 与嵌入经机构批准的出网通道调用云端 API，数据不出域、仅文本出域推理。

**值不值得做**：私有化部署授权（一次性授权 + 年度维保）客单价可达 ¥5–20 万（估算，参照国内舆情厂商清博/识微/蚁坊"数千至数十万元/年"的报价档位，来源：调研报告1），首年即可覆盖小团队研发成本（估算）。**产品无 SaaS 形态**：安全保密场景 SaaS 不适用，全部以私有化交付（LLM 与嵌入经机构批准的出网通道调用云端 API，仅文本出域推理；含离线地图瓦片、无外部依赖的安装包）。

#### 2.4 用户期望体验

- **"啊哈时刻"**：用户第一次打开全球议程地图，看到"此刻 57 国主流媒体分别在炒什么议题"；更进一步，当平台把某议题标记为"疑似议程设置事件"并展示首发源与跟随国传播链路时——第一次感受到"谁在设置全球议程"清晰可见。
- **最小满意体验**：打开看板 → 选一个国家 → 看到今日 Top 议题及其显著性曲线 → 导出/记下结论。3 步以内完成。
- **最高频场景**：
  1. 每日晨间：查看全球议程地图 + 关注国的议题排行 + 隔夜议程设置事件告警（陈国栋、王晓彤）；
  2. 每周研究：选定"国家×议题"，查看显著性时间线与传播链路并导出数据/报告（李思远）；
  3. 事件突发：某国官员/媒体提出新涉华表述，确认是否构成议程设置、首发源是谁、哪些国家媒体在跟随（陈国栋、张建国）。

| 温数据 | 90 天 | PostgreSQL/ES（HDD 或同盘冷索引） | 偶尔（时间线拉长） | 正常查询，ES 索引只读冻结 |

| 过期 | >1 年 | 归档/删除 | - | 按机构数据政策与版权合规处理（默认只保留元数据与聚合快照，删除全文） |

#### 4.6 数据质量要求

#### 5.5 可扩展性

- **架构**: Docker Compose 单机多容器（采集 worker、NLP worker、Web、PostgreSQL、ES、Redis 分容器）；采集与 NLP worker 支持单容器内并发调参扩容，应用层无状态部分可水平复制（V2 再考虑）。
- **扩容触发**: 容器 CPU > 70% / Memory > 80% 持续 5 分钟 → 管理后台提示调整 worker 并发或升配。
- **预估增长**: 国家数 57 → 100（估算）、源数 1100 → 2000（估算）、文章量 15 万 → 30 万篇/天（估算），单机 8C16G + 1TB SSD 可支撑（估算）；无 GPU 硬件要求（云端 API 无需本地推理卡）。
- **瓶颈点**: 云端 LLM API 并发配额（讯飞星辰并发 2，信号量限流）；NLP worker 的嵌入 API 调用频率（SiliconFlow RPM 2000/TPM 500000）；ES 磁盘占用；GDELT DOC API 调用频率。

#### 5.6 可维护性

- **日志**: 结构化 JSON，trace_id 贯穿 采集→抽取→NLP→LLM→入库 全链路；每篇文章可回溯完整处理轨迹。
- **监控**: 管理后台内置 采集量/源健康/延迟分布/错误率/磁盘 五类面板，无需额外装 Grafana。
- **部署**: `docker compose up -d` 单命令起栈；首次启动进入初始化向导；无外网环境使用私有化安装包（镜像 + 离线地图瓦片），LLM/嵌入经机构批准出网通道后调用云端 API（机构不批准云通道时提供本地推理兜底镜像）。
- **升级/回滚**: 镜像版本化，`compose pull + up` 升级；数据库迁移失败自动回滚至上一版本快照，回滚 ≤10 分钟（估算）。
- **配置**: 全部经 `config.yml` + 环境变量，与代码分离；源库配置支持后台热更新（新增源不重启）。

### Epic 1: 全球媒体源管理与采集

#### US-01 [P0]: 浏览媒体源库与覆盖率

**用户故事**: 作为一名研究员（李思远），我希望查看每个国家纳入监控的主流媒体清单及其合计受众覆盖率与置信度，以便判断"该国媒体议程"这一结论的数据基础是否可信、能否在论文/研判报告中引用。

**关联画像**: 李思远（P0）、陈国栋（P0）、张建国（P1）

**验收标准**:

| AC# | Given | When | Then |
|-----|-------|------|------|
| AC1 | 用户已登录且源库已完成 57 国初始化 | 进入"媒体源库"页并选择国家"印度" | 展示该国全部源列表（名称、类型、采集方式、状态、受众覆盖率估算值），顶部显示合计覆盖率 ≥70% 与置信度（high/medium/low） |
| AC2 | 用户在某国源列表页 | 点击"覆盖率口径说明" | 展示估算方法：维基百科各国报纸列表 + ABYZ News Links + Media Cloud Directory + awesome-rss-feeds 清单 + Similarweb 流量排名取交集（来源：调研报告1 §2.4），并标注该置信度含义 |
| AC3 | 某国合计覆盖率因源失效降至 70% 以下 | 用户打开该国源列表页 | 页面顶部出现"覆盖率缺口"警示条，显示当前合计覆盖率与受影响源 |

**异常场景**:
- 源库初始化未完成（部署后首批导入中）：页面显示导入进度，禁止导出"覆盖率证明"类内容
- 覆盖率参考数据源（如 Similarweb）不可用：置信度自动降一级展示，并标注"流量数据缺失"

**边界条件**:
- 一国仅 1 家媒体即满足 ≥70%（高度集中的媒体市场）：正常展示，并在口径说明中提示"单一源集中度风险"
- 覆盖率估算值为 0（新加入源未评估）：展示为"待评估"，不计入合计，不阻断列表展示
- 源数量极大国（如美国 >50 个候选源）：分页展示，每页 20 条，支持按状态/覆盖率排序

#### US-02 [P1]: 请求新增媒体源

**用户故事**: 作为一名研究助理（王晓彤），我希望提交一个未被收录的媒体源 URL 请求加入监控，以便把我工作中发现的重要媒体纳入平台，而不需要懂任何技术配置。

**关联画像**: 王晓彤（P2）、陈国栋（P0）

**验收标准**:

| AC# | Given | When | Then |
|-----|-------|------|------|
| AC1 | 注册用户/授权用户已登录 | 在源库页点击"请求新增源"，粘贴 URL 并选择国家 | 系统自动探测：存在原生 RSS → 直接给出"可接入"反馈；无原生 RSS → 尝试 RSSHub 路由匹配并反馈结果；提交成功进入审核队列 |
| AC2 | 管理员在后台审核队列 | 审核通过该请求 | 源进入 active 状态并参与下一轮采集；提交者收到通知 |
| AC3 | 提交的 URL 已存在于源库 | 用户提交 | 提示"该源已在监控中"并展示其状态，不创建重复请求 |

**异常场景**:
- URL 无法访问/超时：提示"无法访问该站点"，允许用户修改后重试，不进入审核队列
- 探测发现站点需要登录或有付费墙：标记"受限源"，提示仅可采集公开摘要，由用户确认后再提交
- 审核驳回：通知提交者并附驳回原因（如"非新闻媒体""重复"）

**边界条件**:
- 同一用户每日提交上限 10 条（估算），超限提示次日再试
- URL 为非 http/https 协议或内网地址：直接拒绝（SSRF 防护）
- 该源所属国家不在已部署的 57 国内：允许提交但标注"扩展国家候选"，不立即接入

#### US-03 [P0]: 源健康监控与失效自愈

**用户故事**: 作为一名管理员，我希望系统自动监控每个源的采集健康状态并在失效时自动降级与告警，以便平台 7×24 无人值守运行时媒体覆盖不出现静默缺口。

**关联画像**: 管理员（机构 IT）、张建国（P1，关注可审计性）

**验收标准**:

| AC# | Given | When | Then |
|-----|-------|------|------|
| AC1 | 某 RSS 源正常采集 | 系统按 poll_interval（重点源 60–300 秒）轮询 | 每次轮询记录成功/失败、新文章数、published_at→ingested_at 延迟 |
| AC2 | 某源连续 3 次轮询失败（估算阈值） | 系统判定 | 源状态 active → degraded，自动尝试 RSSHub 替代路由；同时用 GDELT 数据对该媒体/国家兜底；向管理员发送告警 |
| AC3 | degraded 源连续失败超过 24 小时（估算） | 系统判定 | 状态 → disabled，移出合计覆盖率计算，触发"覆盖率缺口"检查（该国合计 <70% 时升级告警级别） |
| AC4 | degraded 源恢复可用 | 连续 3 次轮询成功 | 状态自动恢复 active，告警自动关闭，后台保留完整状态变更历史 |

**源状态机**:

```
            连续3次失败            连续3次成功
┌────────┐ ──────────> ┌──────────┐ ──────────> ┌────────┐
│ active │             │ degraded │             │ active │
└────────┘ <────────── └────┬─────┘             └────────┘
                            │ 连续失败 >24h
                     ┌──────▼──────┐
                     │  disabled   │ ──人工修复/重新验证──> active
                     └─────────────┘
```

**异常场景**:
- RSSHub 实例不可用：降级链跳到 GDELT 兜底，告警中注明"RSSHub 通道失效"
- GDELT 亦不可达：标记该国"仅靠存量自采"，在看板显著位置提示数据缺口时段
- 告警通道（邮件/Webhook）发送失败：后台记录未送达告警并重试 3 次，界面常驻未读告警标记

**边界条件**:
- 源返回 200 但内容连续为空（feed 结构变更）：判定为"解析失败"计入失败次数，而非"无新文章"
- 短时间内大规模源同时失败（>20%，估算）：判定为平台侧网络问题而非源失效，触发"出口网络故障"全局告警，不逐个变更源状态
- GDELT 兜底文章无法精确归属到具体媒体时：计入该国覆盖但不冒充该源产出，数据标记 `via=gdelt`

### Epic 2: 议程分析引擎：话题聚类、议程溯源与显著性测量

#### US-04 [P0]: 话题聚类、LLM 议题命名与议题显著性排行

**用户故事**: 作为一名研究员（李思远），我希望系统自动把各国新闻聚成议题、由大模型为议题生成可读名称并完成主题分类与重复议题归并，同时计算显著性排行，以便获得第一层议程设置（客体显著性，媒体决定"想什么"）的量化测量结果，议题名称一看就懂、方法可追溯可引用。

**关联画像**: 李思远（P0）、陈国栋（P0）

**验收标准**:

| AC# | Given | When | Then |
|-----|-------|------|------|
| AC1 | NLP 管线运行中（fastText lid.176 语言识别 → SiliconFlow bge-m3 向量（1024 维）→ BERTopic 增量聚类 → 云端 LLM API（讯飞星辰）命名/分类/归并，来源：调研报告2 §4；决策 D-006） | 新文章入库 | 文章被归入既有议题或触发新议题生成；跨语言同义议题归入同一议题（跨语言向量空间） |
| AC2 | 新议题形成（报道量达到候选阈值） | LLM 处理该议题 | 生成人类可读议题名称（如"新疆棉争议"而非关键词堆叠）与主题分类（政治/经济/军事/科技/社会等，估算分类体系），并自动归并重复议题；命名与分类结果可人工修正，修正记录反哺后续判定 |
| AC3 | 用户选择国家与日期 | 查看"议题排行" | 展示该国当日 Top-20 议题（估算），每个议题含：LLM 生成的议题名称、显著性分数、报道量、涉及媒体数、环比变化、代表文章 |
| AC4 | 用户点击某议题的"显著性说明" | 查看分数解释 | 展示显著性计算口径（议题报道量、涉及媒体数及其覆盖率加权的归一化分数）与原始数据，可下钻到文章列表 |

**异常场景**:
- LLM 服务不可用：自动降级为 BERTopic c-TF-IDF 关键词标签作为议题名，看板标注"降级模式：议题名为关键词标签"；聚类不可用时降级为关键词匹配（详见 3-产品需求.md 第八章 AI 专项设计，决策 D-006），恢复后自动回切
- LLM 命名明显不当（事实性错误/表述失当）：提供"修正"入口，修正后该议题立即更新并记录审计日志
- 某语言向量质量不达标（预评估黑名单语言）：该语言文章走关键词匹配通道并标注
- 当日某国采集量为 0（全网源失效）：排行页显示"数据缺失"而非空排行，并关联源健康状态

**边界条件**:
- 新议题只有 1 篇文章：进入"候选议题"池，报道量 ≥3 篇或涉及 ≥2 家媒体（估算阈值）后进入正式排行
- 突发大事件导致单议题占比 >50%：正常展示，排行页提供"排除该议题"开关以观察长尾议程
- 议题合并/分裂（增量聚类演化 + LLM 归并）：保留演化关系与归并理由记录，时间线上可回溯

**用户故事**: 作为一名国际舆情分析师（陈国栋），我希望看到每个议题下报道的情感属性分布（正面/中性/负面）及其随时间变化，以便实现第二层议程设置分析（属性议程设置——媒体影响"怎么想"，来源：调研报告1 §1.2），回答"某国媒体以什么基调报道涉华议题"。

#### US-06 [P0]: 议程溯源与跨国传播链路

**用户故事**: 作为一名国际舆情分析师（陈国栋），我希望平台自动识别每个跨国议题的首发源（国家/媒体/人物）、跟随报道的国家序列与时间差，生成传播链路图，并在满足判定条件时自动标记"议程设置事件"并告警，以便第一时间回答"这是不是一次议程设置、谁发起的、哪些国家在跟随"，并获得完整证据链。

> 典型案例：某国官员/媒体率先提出"新疆棉"议题 → 多国媒体在随后数天跟随报道 → 平台识别首发源、跟随国序列与时滞，判定为议程设置事件并告警。

**关联画像**: 陈国栋（P0）、李思远（P0）、张建国（P1）

**底层测量方法**: 网络议程设置（NAS，Guo & McCombs，来源：[Nature HSSC 2025](https://www.nature.com/articles/s41599-025-04472-0)）、时滞互相关、Granger 因果检验、QAP/MRQAP（来源：调研报告1 §1.2/§1.3）；首发表述判定由云端 LLM API 辅助完成（决策 D-006）。

**验收标准**:

| AC# | Given | When | Then |
|-----|-------|------|------|
| AC1 | 某议题在多国媒体出现 | 系统按小时滚动计算（估算频率） | 输出该议题首发源判定（国家/媒体/人物，附首发表述原文与发布时间）、跟随报道国家序列、各国相对首发的时滞（天/小时） |
| AC2 | 用户打开议题"传播链路"页 | 查看链路图 | 展示 首发源 → 各国媒体 的传播链路图（节点=国家/媒体，边=跟随关系与时滞），支持按时间回放扩散过程 |
| AC3 | 议题满足议程设置判定条件（首发源明确 + ≥3 国媒体在时滞窗口内跟随 + 时滞方向一致性经时滞互相关/Granger 检验支持，阈值可配，估算） | 系统判定 | 自动生成 AgendaEvent（状态：疑似），向订阅用户告警；事件卡片含判定依据、置信度与完整证据链 |
| AC4 | 分析师复核疑似事件 | 点击"确认/排除" | 状态流转（疑似 → 确认/排除）并记录操作人与时间（审计日志）；确认事件进入"议程设置事件库"可检索 |
| AC5 | 研究员（李思远）需要方法论输出 | 选定议题与媒体组，运行"引领分析" | 输出时滞互相关曲线（lag 0–14 天）、Granger 检验 p 值表与 QAP 结果，附"如何解读"的非技术语言说明，可保存为含参数/时间窗/数据版本的可复现快照 |

**传播链路图原型**:

```
                ┌──────────────────────┐
                │ 首发源: X国 官方媒体    │  T0 (03-12)
                │ 人物: X国 官员 讲话     │  T0-2d
                └──────────┬───────────┘
        ┌──────────────────┼──────────────────┐
        ▼ +0.5d            ▼ +1.2d             ▼ +2.8d
  ┌────────────┐    ┌────────────┐     ┌────────────┐
  │ Y国 媒体群  │    │ Z国 媒体群  │     │ W国 媒体群  │
  │ 12 篇/5 家  │    │ 27 篇/9 家  │     │ 8 篇/4 家   │
  └────────────┘    └────────────┘     └────────────┘
  判定: 首发明确 + ≥3 国跟随 + 时滞方向一致 → 议程设置事件(疑似) → 告警
```

**议程设置事件状态机**:

```
┌────────┐  满足判定条件   ┌────────┐   分析师确认    ┌────────┐
│ 监测中  │ ─────────────> │  疑似   │ ─────────────> │  确认   │
└────────┘                └───┬────┘                 └────────┘
                              │ 分析师排除 / 证据不足超时(14天,估算)
                       ┌──────▼─────┐
                       │    排除     │ (保留记录,可重开)
                       └────────────┘
```

**异常场景**:
- 首发源无法判定（多源几乎同时首发，时滞 <6 小时，估算）：事件标注"首发源存疑"，列出并列候选源，不强行判定
- LLM 不可用：首发表述判定降级为规则匹配（官方讲话稿源 + 关键词/模板），事件判定照常进行但置信度降一级并标注"降级模式"（决策 D-006）
- 时间窗内数据量不足（<100 篇，估算）：拒绝运行引领分析并提示所需最小样本量与建议时间窗
- Granger 检验前提不满足（序列非平稳且差分后仍不满足）：展示检验失败原因，不输出误导性 p 值；事件判定改用其余证据并降低置信度
- 计算超时（>60s，估算）：转后台任务，完成后通知用户

**边界条件**:
- 链路涉及国家 >20 个：链路图默认按报道量 Top-N 聚合展示（N 可调），完整序列可导出（CSV）
- 两媒体时间窗内重叠报道为 0：提示"无重叠议题，无法计算"，而非输出零相关
- 议题合并/分裂：事件与链路记录随议题演化关系迁移，保留历史快照
- 同一议题出现多轮议程设置（不同首发源）：生成多个 AgendaEvent，按轮次编号

#### US-16 [P0]: 议程演化与自我纠错

**用户故事**: 作为一名国际舆情分析师（陈国栋），我希望平台对识别结果随证据积累自动更新与修正——新议题次日自动归并到历史议题、首发源误判自动纠正、置信度自动升降，且每次修正全程留痕可审计、我可人工否决——以便"今天只有零星报道、明天才成形"的议程不被漏判，首发误判与议题误并/误拆不沉淀为错误结论。

> 与 US-06 的边界：US-06 管"识别一次议程设置"（首发源 + 跟随序列 + 时滞的一次性判定与告警）；US-16 管"识别结果的持续演化与纠错"（议题生命周期、次日归并、增量重估、置信度自动升降、修正留痕）。US-06 的判定输出是 US-16 增量重估与修正的对象。

**关联画像**: 陈国栋（P0）、李思远（P0）、张建国（P1）

**核心机制**（与 `1-产品全景.md`、`3-产品需求.md`、`4-运营计划.md` 表述一致，决策 D-007）:
- **议题生命周期状态机**：萌芽（孤证微簇）→ 形成中 → 已确认 → 演化（合并/分裂）→ 消亡（连续 N 天无新报道自动归档，N=7 估算）
- **次日自动归并**：新议题先与历史议题做跨语言向量比对，相似（≥0.85 估算）则并入旧议题（topic_id 复用），否则开新议题——解决"今天没形成的议程明天成形"的滞后问题
- **增量重估与判定修正**：新证据（更早报道、新来源）出现时自动重跑首发源判定；判定变化时自动更新并写入**修正历史（revision_log）**，前端标注"该判定已于 X 时修正"；AgendaEvent 置信度随证据自动升级（观察中→疑似→确认）或撤销
- **全程留痕**：每次自动修正记录修正前/后值、触发证据、模型与 prompt 版本；分析师可人工确认/否决（人工校正优先级高于机器）
- **参考实现**：开源项目 IntelligenceIntegrationSystem（Apache-2.0，380★，[GitHub](https://github.com/SleepySoft/IntelligenceIntegrationSystem)，调研报告3）的主题档案合并（topic_id 复用）与在线增量聚类设计；其合并/分裂回写未完成（writeback 为 TODO），本平台需自行落地并超越（增加分裂与消亡机制）

**议题生命周期状态机**:

```
┌────────┐  报道量/来源数达标   ┌────────┐  跨库验证通过   ┌────────┐
│  萌芽   │ ────────────────> │ 形成中  │ ────────────> │ 已确认  │
│(孤证微簇)│ <── 证据不足回退 ── └────┬───┘               └───┬────┘
└────────┘                        │                        │
                                  ▼ 相似议题出现(≥0.85,估算)  ▼
                            ┌──────────────────────────────────┐
                            │   演化(合并/分裂): topic_id 复用   │
                            │   或被 merged_into 指向存活议题     │
                            └────────────────┬─────────────────┘
                                             │ 连续 N 天无新报道(N=7,估算)
                                      ┌──────▼─────┐
                                      │    消亡     │ 自动归档;新证据可复活并留痕
                                      └────────────┘
```

**验收标准**:

| AC# | Given | When | Then |
|-----|-------|------|------|
| AC1（次日自动归并） | 某议题首日仅有零星报道（孤证保留为 size=1 微簇，生命周期=萌芽，不丢弃） | 次日多国媒体跟进报道进入在线增量聚类（双阈值 T_event=0.85 归簇 / T_dup=0.95 判重，估算） | 新议题先与历史议题做跨语言向量比对：相似度 ≥0.85（估算）则并入旧议题（topic_id 复用）并记录演化关系与归并理由，否则开新议题；时间线上可回溯完整演化链 |
| AC2（首发判定自动修正+留痕） | 某 AgendaEvent 首发源已判定为媒体 A | 新证据（更早报道或新来源）出现 | 系统自动重跑首发源判定；判定变化时自动更新结论并写入 revision_log（修正前/后值、触发证据、模型与 prompt 版本），前端该事件标注"该判定已于 X 时修正"，旧值可查证不删除 |
| AC3（置信度自动升降） | 某 AgendaEvent 处于"观察中"状态 | 证据积累满足升级条件（跟随国数/时滞一致性增强），或出现反证 | 置信度自动升级（观察中→疑似→确认）或撤销/降级；每次状态变化写入 revision_log 并在事件卡片上展示当前置信度与变化轨迹 |
| AC4（人工否决优先） | 系统已执行自动归并或自动判定修正 | 分析师点击"确认"或"否决" | 人工校正优先级高于机器：否决立即回滚该次自动修正（恢复原值）并锁定对应判定不再被自动修改（除非人工解锁）；全部操作记录操作人与时间，入审计日志 |
| AC5（消亡与归档） | 某议题连续 7 天（N=7，估算）无新报道 | 系统每日生命周期扫描 | 议题自动转入"消亡"状态并归档，看板默认不再展示但可检索；归档后出现新证据时可"复活"（回到形成中）并留痕 |

**异常场景**:
- 误并回滚：系统将两个不同议题误并 → 分析师否决后一键拆分回滚，两议题恢复原 topic_id、各自时间线与关联 AgendaEvent 自动迁移还原，revision_log 记录拆分原因与触发证据；误并样本作为负例积累用于优化归并阈值
- 重聚类期间读旧版：每小时全局重聚类校正（估算）执行期间，看板读取上一稳定版议题快照并标注"校正中"，不暴露中间态数据；校正完成后原子切换至新版本
- LLM 不可用：增量重估与 LLM 终审暂停，议题演化仅依赖向量聚类通道继续，期间修正标注"降级模式"，LLM 恢复后自动补跑复核并记录（决策 D-006）
- 修正风暴（单位时间自动修正次数超过阈值，估算）：触发质量告警，自动修正暂停并转入人工确认队列，防止阈值失效导致大面积误改

**边界条件**:
- 多次合并链（A→B→C）：演化关系全链可溯，merged_into 始终指向最终存活议题，中间节点保留历史快照
- 高频实体干扰归并：动态高频实体黑名单（每 24h 统计近 30 天 Top-50 高频实体，如大国名、名人，估算）过滤超级节点，防止虚假关联造成误并
- 人工否决与自动修正同时发生：以人工操作时间戳优先，冲突时保留人工结论并向分析师提示冲突记录
- 议题消亡后再次复活：归档议题被新证据复活时保留原 topic_id 与完整历史，lifecycle_state 回到"形成中"并写入 revision_log
- 孤证长期不增长：萌芽微簇超过 30 天（估算）无新增报道且无归并对象，自动归档为"未成形议题"，不计入排行但可检索

**异常场景**:
