## 第一章: 需求背景与目标

### 1.1 需求背景

议程设置理论（Agenda-Setting Theory）是传播学最稳健的理论之一：1968 年 Chapel Hill 研究中，媒体议题强调度与选民议题重要性排序的 Spearman 相关系数高达约 **0.97**（McCombs & Shaw, 1972, *Public Opinion Quarterly* 36(2): 176–187）。理论已从第一层"客体显著性"（媒体决定"想什么"）发展到第二层"属性议程设置"（影响"怎么想"，含实质属性与情感属性）和第三层"网络议程设置 NAS"（Guo & McCombs 提出的议题-属性关联网络显著性转移）。计算传播学已给出成熟的测量方法：BERTopic 话题建模、时滞互相关、Granger 因果检验、QAP/MRQAP 网络相关分析、媒体间议程设置（intermedia agenda setting，如 Guo & Vargo 2017 *Journal of Communication* 67(4): 499–520 的跨国新闻流大数据研究）。

然而，"把这套方法做成一个能 7×24 运行的产品"目前存在明显空档：

- **商业舆情平台贵且不学术**：Meltwater 约 $15,000/年起，Brandwatch/Talkwalker 年合同约 $10,000–50,000（第三方采购数据中位 ~$27,000–50,000/年），且其分析停留在声量/情感层面，没有议程设置三层测量框架（来源：[syncly 三方对比](https://syncly.app/blog/brandwatch-vs-meltwater-vs-talkwalker)、[CheckThat Talkwalker 定价](https://checkthat.ai/brands/talkwalker/pricing)）。
- **免费学术工具不实时、无产品形态**：GDELT 免费、100+ 语言、每 15 分钟更新，但只是原始数据库；Media Cloud 免费但偏学术查询界面，二者均无面向小白用户的议程分析看板（来源：[GDELT 官网](https://www.gdeltproject.org/)）。
- **开源舆情项目有热度但不对口**：TrendRadar（60.9k★）聚合中文热榜、BettaFish（41.8k★）做多 Agent 中文舆情、worldmonitor（72.7k★）做全球情报仪表盘，但均不覆盖"57 国主流媒体 ≥70% 覆盖率 + 议程设置三层测量"这一组合（star 数为 2026-07-24 GitHub API 实测）。
- **目标用户没有技术能力自建**：国家安全机关舆情分析人员、国际关系/国际政治/国家安全研究机构人员普遍零编程基础，无法自行组装 feedparser + BERTopic + Elasticsearch 的技术栈。

### 1.3 用户价值

不是"给用户一个爬虫工具"，而是给用户三个可交付的结果：

1. **看得见的全球舆情动向**：打开看板即见 57 国主流媒体此刻在"想什么"（第一层）、如何定性这些议题（第二层）、议题之间如何关联（第三层 NAS 网络），无需写一行代码。
2. **可识别的议程设置行为（差异化核心）**：识别某国（媒体、官员、重要人士、智库、国际组织）率先提出一个议题、随后多国媒体跟随报道的"议程设置事件"，自动呈现首发源、跟随国序列与时滞的完整证据链并告警（典型示例：某国官员/媒体率先提出"新疆棉"议题 → 多国媒体跟随报道 → 平台判定为议程设置事件）。
3. **可引用的测量与不遗漏的预警**：显著性排名、时滞互相关、Granger 因果、QAP/MRQAP 的计算结果可直接导出，嵌入简报、研究报告或论文的方法论附录；指定议题在指定国家显著性突变时自动推送，把"每天刷几十个新闻网站"的人工劳动降为 0。

## 第二章: 范围定义

### 2.1 In Scope（V1.0 全量范围，交付节奏分两期）

> 交付节奏与 `1-产品全景.md` 路线图一致：**MVP（V0.1）** = US-01、US-03、US-04、US-06、US-07、US-08、US-12、US-13、US-16（P0）；**V0.2** = US-02、US-05、US-09、US-10、US-11、US-14、US-15（P1/P2）。以下为本 PRD 覆盖的完整功能范围。

- **监控范围**：57 国 = G20 全部成员（20 国）+ 全球南方代表性经济体（40 国），共 57 国（东亚/东南亚/南亚/中东/欧洲/北美/拉美/大洋洲/非洲/中亚全覆盖）。
- **媒体覆盖**：每国主流新闻媒体合计受众覆盖率 ≥70%（操作化口径：维基百科各国报纸列表 + ABYZ News Links + Media Cloud Directory（25,000+ 源）+ awesome-rss-feeds 清单 + Similarweb 流量排名取交集，逐国标注覆盖率估算置信度）。
- **实时采集**：重点源 RSS 1–5 分钟高频轮询 + GDELT（15 分钟更新）兜底 + RSSHub 补源 + trafilatura 正文抽取（readability-lxml 降级兜底）；新闻发布 → 平台可见 P95 ≤ 30 分钟，红线 ≤ 2 小时。
- **议程分析引擎**：媒体议程的三层测量——第一层议题显著性排名；第二层实质/情感属性分析；第三层 NAS 议题网络 + 时滞互相关 + Granger 因果 + QAP/MRQAP + 媒体间议程设置（国家间媒体谁引领谁）。
- **LLM 议题管线（云端 API）**：大模型负责议题命名、主题分类、重复议题归并、议题摘要与"首发表述"判定，简化传统 NLP 工程；LLM 全部走云端 API（讯飞星辰 MaaS，OpenAI 兼容 `/chat/completions`，生产并发上限 2），数据不出域、仅文本出域推理；仅当机构不批准云通道时启用本地 Qwen 分支作为极端降级兜底（决策 D-006）。
- **议程溯源与议程设置事件识别（差异化核心，US-06）**：识别议题首发源（国家/媒体/人物）、跟随报道的国家序列与时间差、传播链路图，自动判定"议程设置事件"并告警。
- **关键人物与机构议题发起监测（US-15）**：跟踪外国官员、重要政治人物、智库、国际组织首次提出的新表述/新议题，标注"人物首发 → 媒体扩散"链路。
- **议程演化与自我纠错（US-16）**：议题生命周期状态机（萌芽→形成中→已确认→演化→消亡）、次日自动归并（新议题与历史议题跨语言向量比对，相似则并入旧议题复用 topic_id）、增量重估与首发判定自动修正（revision_log 全程留痕可审计）、AgendaEvent 置信度随证据自动升降、人工否决优先于机器判定。
- **可视化看板**：全球议程地图、议程时间线、议题网络图、跨国对比视图、传播链路图（React + Apache ECharts 自研）。
- **议题预警与订阅推送**：规则配置 + 邮件/Webhook 推送。
- **一键报告导出**：面向业务专家的预设模板报告（PDF/Word）。
- **私有化部署（唯一交付形态）**：Docker Compose 单机部署，用户自有服务器 7×24 常驻运行，含安装向导与系统管理后台；**私有化部署 + 经机构批准的出网通道**：LLM 与嵌入走云端 API（数据不出域，仅文本出域推理）、离线地图瓦片或内网地图服务、无外部依赖安装包。

### 2.2 Out of Scope（明确不做什么）

- **不做社交媒体全量监控**：不采集微博/X/TikTok/抖音等社媒全量数据。原因：反爬与合规成本高、社媒数据授权复杂，且与本产品"主流媒体议程"的理论定位不符。V2.0 再评估接入公开社媒 API。
- **不做公众议程直接测量**：MVP 只测量**媒体议程**。公众议程（民调数据、搜索趋势、社媒公众讨论）的数据接入为 **V2.0** 范围。这意味着 MVP 的时滞互相关/Granger 因果用于**媒体间议程设置**（如一国媒体引领另一国媒体），不声称测量"媒体→公众"的效果。
- **不做电视/广播内容监控**：GDELT 的 TV API 与广播转写不在 MVP 范围，仅作为数据源元信息记录。
- **不做内容生产**：不生成新闻稿、不提供 AI 自动写报告全文（报告为图表+数据的模板化组装；LLM 仅用于议题命名、分类、归并与摘要，不代写分析报告全文）。
- **不做移动端 App**：响应式 Web 适配平板即可，不开发 iOS/Android 原生应用。
- **不做 SaaS 平台（无 SaaS 形态）**：安全保密场景 SaaS 不适用，私有化部署为唯一交付形态；不设个人订阅档位，账号体系仅服务于私有化实例内部。

## 第四章: 功能详述与交互逻辑

### 4.1 功能架构

```
┌────────────────────────────────────────────────────────────────────┐
│                    AgendaScope 观澜（Web 前端 React+ECharts）        │
│  ┌──────────┬──────────────┬──────────────┬───────────┬──────────┐ │

### 4.2 核心流程：新闻从发布到平台可见（延迟链路）

**正常流程 (Happy Path)：**

```
媒体发布文章
   │
   ├─[路径 A：自有采集]─> RSS 轮询（重点源 1–5 min / 普通源 15 min）
   │                        │ feedparser 解析
   │                        ▼
   │                     去重（URL 哈希 + 标题相似度，Redis）
   │                        │
   │                        ▼
   │                     trafilatura 正文抽取 ──失败──> readability-lxml 兜底
   │                        │                              │仍失败
   │                        │                              ▼
   │                        │                        仅存摘要+元数据
   │                        ▼
   ├─[路径 B：GDELT 兜底]─> 每 15 min 拉取 GDELT DOC 2.0（100+ 语言）
   │                        │ 与自有采集按 URL/标题去重合并
   ▼
NLP 管线：fastText lid.176 语言识别
   → 云端嵌入 API（SiliconFlow bge-m3，1024 维 /embeddings）生成跨语言向量
   → BERTopic 在线/增量聚类，归属议题 Topic
   → 云端 LLM API（讯飞星辰 MaaS /chat/completions）：议题命名 / 主题分类 /
     重复议题归并 / 摘要（不可用则 c-TF-IDF 关键词标签兜底）
   → 情感属性（正/负/中性）+ 实质属性抽取
   ▼
写入 PostgreSQL（结构化）+ Elasticsearch（全文检索）
   ▼
分析引擎每 15 min 刷新 AgendaSnapshot（议题显著性排名）
   ▼
前端看板可见 ✅   （目标：全链路 P95 ≤ 30 min，红线 ≤ 2 h）
```

**异常流程 (Error Path)：**

- **RSS 源失效**（连续 3 次抓取失败）→ 标记源状态 `degraded`，自动切换 GDELT 补该媒体覆盖，同时向管理员发告警（US-03）；连续 24 小时失败 → `failed`，计入覆盖率滑坡告警。
- **正文抽取失败** → 降级 readability-lxml；再失败则仅保留标题+摘要+GDELT 元数据入库，文章标记 `content_status=partial`，仍参与话题聚类（用标题+摘要向量）。
- **GDELT 不可用** → 自有 RSS 链路独立运行，覆盖缺口在源健康看板黄灯提示；GDELT 恢复后自动回补最近 3 个月窗口内缺失数据（DOC API 支持滚动 3 个月窗口）。
- **NLP worker 积压** → Redis Streams 队列长度超阈值（默认 10,000 条）时自动扩 worker 并发并降级为"先入库后聚类"（文章先可见，话题标签稍后补），保证可见性红线 ≤ 2 h 优先于聚类完整性。
- **服务器资源告急**（CPU>85% 持续 10 min）→ 自动下调普通源轮询频率（15→30 min），重点源频率不变，管理后台横幅提示。

**边界条件 (Edge Cases)：**

- **单源短时间爆发**（如重大突发单小时 >500 篇）→ 按源限流采样入库，分析层仍计全量显著性（GDELT 交叉校验），界面标注"报道量激增"。
- **文章无发布时间或时区异常** → 以首次抓取时间代替，字段标记 `time_source=crawled`，分析时按 UTC 统一。
- **重复报道/转载** → URL 哈希精确去重 + 标题向量相似度 >0.92 判为转载，合并为一组，保留首发为主记录，转载数计入显著性权重。
- **小语种低资源语言**（如阿姆哈拉语）→ fastText 识别置信度 <0.8 时归入该国默认语言；embedding 一律走 bge-m3 多语言向量（云端 API），不按语言分管线。

#### 4.4.2 功能：三层显著性测量看板（US-05）

**第一层（客体显著性）**：议题显著性 = 时间窗内报道量加权（媒体权重 × 篇数，转载计权重）的标准化得分，输出"国家 × 议题"显著性排名表与 Top-N 榜单（默认 Top 10）。

**第二层（属性议程设置）**：每个议题下展示——情感属性（正/负/中性占比条，按媒体可下钻）；实质属性（该议题下高频子面向/框架词，如"经济议题"下的"通胀/就业/汇率"），以属性显著性排名呈现。

**第三层（NAS 网络分析）**：

```
议题-属性共现矩阵 ──> 议题网络图（节点=议题/属性，边=共现强度）
     │
     ├─ 节点中心性 → 网络显著性排名
     ├─ 跨国两两比较 → QAP/MRQAP 网络相关系数矩阵（热图）
     └─ 议题时间序列 → 时滞互相关（lag 0–14 天）+ Granger 因果检验
                        → "媒体间议程设置"结论：A 国媒体是否领先 B 国媒体 N 天
```

**页面元素（分析看板）**

| 元素 | 类型 | 规则 | 默认值 |
|------|------|------|--------|
| 分析对象选择 | 下拉（国家+议题） | 单国单议题 / 多国同议题 / 双国全议题网络 | 最近活跃议题 |
| 时间窗 | 滑块 | 7/14/30/90 天，最小粒度 1 天 | 30 天 |
| 显著性榜 | 表格+条形图 | 第一层输出，支持导出 CSV | Top 10 |
| 属性面板 | 标签云+占比条 | 第二层输出 | 情感占比优先展示 |
| 网络图 | ECharts 关系图 | 节点大小=中心性，边粗=共现强度；可拖拽缩放 | 力导向布局 |
| 统计检验结果卡 | 指标卡 | QAP 相关系数 r、Granger p 值、最优滞后天数；p<0.05 绿色标注"显著" | - |

**异常与边界**：时间窗内文章 <100 篇 → 不计算 Granger/QAP，显示"数据量不足，统计检验不可用"（避免输出伪显著结果）；用户无统计背景 → 每个指标配"一句话解读"悬浮说明（如"Granger p=0.03 表示：在 5% 显著性水平下，A 国媒体的该议题报道量变化能预测 B 国 3 天后的变化"）。

#### 4.4.3 功能：议程溯源与跨国传播链路（US-06，P0 差异化核心）

**目标**：回答"这个议题是谁先提出来的、哪些国家跟着报道、各隔了多久"，自动判定"议程设置事件"并告警。典型场景：某国官员/媒体率先提出"新疆棉"议题 → 多国媒体跟随报道 → 平台识别首发源、跟随国序列与时滞，判定为议程设置事件。

     │
     ▼

     ├─ 媒体首发：最早文章所属媒体 → 国家/媒体两级归属
     │    （通讯社原文优先于其转载；转载组合并见 4.2 去重逻辑）
     └─ 人物/机构首发：LLM 判定"首发表述"（某官员讲话/智库报告/

     b) ≥3 个国家媒体在首发后 14 天内跟随报道（估算阈值，可配置）
     c) 时滞互相关或 Granger 检验显著（p<0.05），方向为首发国→跟随国
     d) 议题处于新兴/升温状态
```

│ 佐证: 时滞互相关最优 lag=1天 r=0.81(p=0.002) / Granger US→UK 显著│
│ [查看完整链路图] [导出证据链报告] [误报反馈]                      │

前端渲染为世界地图上的流向动画（首发国 → 跟随国箭头 + 时滞标注），议程设置事件以**中国红（#C8102E）**高亮（见 4.9 视觉规范）。

**议程设置事件状态机（AgendaEvent）：**

```
                条件 a–d 全部满足           人工复核确认
┌────────────┐ ──────────────────> ┌──────────┐ ─────────────> ┌──────────┐
│ 议题升温中  │                     │ 疑似事件  │                │ 确认事件  │
│ (监测中)    │ <────────────────── └────┬─────┘                │ (已告警)  │
└────────────┘   14天窗口内条件不再满足     │                     └────┬─────┘
                                            │ 人工判定误报            │ 议题归档
                                            ▼                          ▼
                                      ┌──────────┐               ┌──────────┐
                                      │ 已排除    │               │ 已归档    │
                                      └──────────┘               └──────────┘
```

- `疑似事件`：系统自动生成，推送站内 + 邮件告警（对接 US-10/US-11 通道），需人工复核；告警文案含首发源、跟随国序列、时滞与统计佐证摘要。
- `确认事件`：分析师确认后进入持续跟踪，跟随国新增时增量更新链路图并再通知；可一键导出"证据链报告"（首发源、时间线、各国代表报道、统计检验结果）。
- `已排除`：人工判定误报（如多国独立自发报道同一突发事件），记录反馈用于评估首发判定准确率（见 8.4）。

**页面元素**：事件列表（判定状态、首发国、跟随国数、最大时滞、置信度）；事件详情（传播链路图 + 时间线 + 代表报道 + 检验结果卡）；筛选（状态、首发国、时间窗）。

**异常与边界**：首发源置信度不足（最早记录为转载或时间戳异常 `time_source=crawled`）→ 标注"首发源待核实"并不自动告警，进人工复核队列；窗口内跟随国 <3 → 仅记录传播链路不生成事件；LLM 首发表述判定不可用 → 降级为纯媒体时间锚点判定（标注"人物首发判定暂不可用"）。

#### 4.4.4 功能：关键人物与机构议题发起监测（US-15，P1）

**监测对象**：外国官员与重要政治人物（公开讲话、记者会、官方声明）、智库（研究报告）、国际组织（决议/文件）的公开报道与发布内容，维护 Person/Org 实体库（见 5.3.6）。

**交互逻辑**：

```
文章流 ──> 实体识别（人名/机构名，多语言 NER + 实体库匹配）
     │
     ▼
LLM 新表述判定：该人物/机构是否首次提出某新提法/新议题
     │（与历史语料比对，输出：新表述原文、首发时间、置信度）
     ▼
命中 → 记录"人物首发"锚点（写入 AgendaEvent 候选证据）
     │
     ▼
跟踪媒体扩散：首发后各媒体跟进报道 → "人物首发 → 媒体扩散"链路
     │    （如：某国官员讲话首次出现某提法 → 3 天内 N 家媒体跟进）
     ▼
达到 US-06 判定条件 → 升级为议程设置事件；未达到 → 以"发起信号"形式
在看板人物监测页列表呈现（人物/机构、新表述、首发时间、跟进媒体数）
```

**异常与边界**：实体识别置信度低（同名歧义）→ 合并人工确认队列；LLM 不可用 → 降级为"人物/机构提及量突增"规则监测（无法判定"新表述"，明确标注能力降级）。

#### 4.4.5 功能：议程演化与自我纠错（US-16，P0）

**目标**：识别结果不是一次性的——当前识别的议程可能不对（首发源误判、议题误并/误拆），或者一个新议程今天尚未形成（只有零星报道）、第二天才成形。系统必须随证据积累**自动更新与修正**（自动归并、自动修正首发判定、自动升降置信度），且全程留痕可审计。与 US-06 的边界：**US-06 管"识别一次议程设置"（首发源、跟随序列、事件判定），US-16 管"识别结果的持续演化与纠错"**。

**议题生命周期状态机（Topic.lifecycle_state）：**

```
┌──────────┐  证据积累(多源/多国跟进)  ┌──────────┐  达到成簇阈值  ┌──────────┐
│   萌芽    │ ──────────────────────> │  形成中   │ ────────────> │  已确认   │
│(孤证微簇) │ <────────────────────── └────┬─────┘               └────┬─────┘
│ size=1   │   证据不足回落                │                          │
└────┬─────┘                               │ 与历史议题相似            │ 新证据显示
     │                                      ▼ (≥0.85,估算)            ▼ 应合并/分裂
     │                                ┌──────────────────────────────────────┐
     │                                │   演化（合并 merged_into / 分裂 split） │
     │                                └──────────────────┬───────────────────┘
     │                                                    │
     ▼              连续 N 天无新报道（N=7，估算）            ▼
┌──────────────────────────────────────────────────────────────┐
│              消亡 → 自动归档（archived，保留可查）              │
└──────────────────────────────────────────────────────────────┘
```

**次日自动归并流程（解决"今天没形成的议程明天成形"）：**

```
当日新文章/新微簇（含昨日孤证微簇）
     │
     ▼
① 回声消除与来源保留：同日相似度 ≥0.65 或 3 日内 ≥0.85 的报道
   折叠为同一议题节点，保留全部来源列表（related_docs）——
   这是跨国跟随链路的算法基础；首发源 = 节点内最早发布时间
     │
     ▼
② 跨语言向量比对：新议题候选与历史活跃议题逐一比对
     │
     ├─ 相似度 ≥0.85（估算）→ 并入旧议题，topic_id 复用，
     │    原议题 last_seen_at 刷新，lifecycle_state 推进
     │    （昨日"孤证"今日随多国跟进而成形，不另开新议题）
     └─ 不相似 → 开新议题（新 topic_id），孤证保留为 size=1
          微簇（议题萌芽不丢弃，等待次日证据）
     ▼
③ 增量重估与判定修正：新证据（更早报道、新来源）出现时
   自动重跑首发源判定与事件判定
     │
     ├─ 判定变化 → 自动更新并写入修正历史（revision_log），
     │    前端标注"该判定已于 X 时修正"
     └─ AgendaEvent 置信度随证据自动升级
          （观察中→疑似→确认）或撤销
     ▼
④ 全程留痕：每次自动修正记录修正前/后值、触发证据、
   模型与 prompt 版本；分析师可人工确认/否决
   （人工校正优先级高于机器）
```

**聚类与归并策略升级（配合 4.4.1）：**

- **聚类算法**：BERTopic 之外增加 **Agglomerative 硬距离阈值聚类**（cosine 阈值 0.25，average linkage，估算）作为议题成簇策略，规避超大簇黑洞与孤证被当噪声；**孤证保留为 size=1 微簇**（首发单源的议题萌芽必须保留）。
- **在线增量聚类**：双阈值（T_event=0.85 归簇 / T_dup=0.95 判重，估算）事件驱动增量归簇 + **每小时全局重聚类校正**（估算），防止纯在线聚类误差累积；重聚类期间前端读上一版快照，不阻塞查询。
- **动态高频实体黑名单**：每 24h 统计近 30 天 Top-50 高频实体（如大国名、名人，估算），防止超级节点造成虚假关联。

**修正历史（revision_log）页面元素**

| 元素 | 类型 | 规则 | 默认值 |
|------|------|------|--------|
| 修正记录列表 | 表格 | 列：修正时间、议题/事件、修正字段、修正前值 → 修正后值、触发证据、修正方（机器/人工）、模型与 prompt 版本 | 按时间倒序 |
| 修正标注 | 行内徽标 | 被修正的判定（首发源/置信度/议题归属）在原展示位标注"该判定已于 X 时修正"，点击展开修正详情 | 显示最近一次 |
| 人工确认/否决 | 操作按钮 | 分析师对每条自动修正可确认或否决；否决即回滚到修正前值并记为新一条 revision_log；**人工校正优先级高于机器**，机器不再自动推翻人工结论 | 待处理修正进复核队列 |
| 误并回滚 | 操作按钮 | 误并的议题可一键拆分回滚（恢复两个 topic_id 及各自文章归属），回滚本身写入 revision_log | - |

**参考实现**：开源项目 IntelligenceIntegrationSystem（Apache-2.0，380★，https://github.com/SleepySoft/IntelligenceIntegrationSystem）的**主题档案合并（topic_id 复用）**与**在线增量聚类双阈值**设计，以及回声消除（同日 ≥0.65 / 3 日内 ≥0.85 折叠节点并保留来源列表）与 LLM 终审机制；注意其合并/分裂回写为未完成状态（writeback TODO），本平台需自行落地并超越——**增加议题分裂与消亡机制**（IIS 只有 merge 设计，无 split 与议题衰减/关闭）。决策见 `4-运营计划.md` D-007。

**异常与边界**：误并（两个不同议题被自动归并）→ 分析师一键拆分回滚，回滚留痕，该对议题对写入"不可归并"名单防止再次误并；误拆（同一议题被拆成两个）→ 次日归并环节自动再合并或管理员一键合并；重聚类校正期间 → 前端读上一版快照并标注"校正中"，不产生读写不一致；LLM 终审见第八章（评分 <5 分自动降为疑似/驳回）；自动修正风暴（单议题 24h 内修正 >5 次，估算）→ 冻结该议题自动修正转人工复核队列。

**异常与边界**：磁盘 >85% → 自动清理 90 天前的文章原始 HTML（保留结构化数据与正文文本）并告警；备份失败连续 2 次 → P1 告警；授权到期前 30/7/1 天三级提醒，到期后系统只读不删数据。

### 4.9 前端视觉设计规范

面向国家安全机关与国际关系研究机构的视觉风格：**庄重、权威、专业、克制**；深色主题为主，信息密度高但不杂乱。

## 第八章: AI 专项设计（LLM 专项）

### 8.1 LLM 可行性分析

| 维度 | 评估 | 说明 |
|------|------|------|
| 输入弹性 | 高 | 新闻文本质量参差（摘要/全文/多语言/噪声），LLM 对多语言、长短不一文本的议题命名/分类/摘要天然容忍；传统聚类输入弹性同样高（正文缺失时标题+摘要仍可聚类） |
| 规则可语言化 | 高 | 议题命名、主题分类、重复归并、首发表述判定均可自然语言指令化 + few-shot 示例约束；"议程设置事件"的判定口径（首发源+跟随序列+统计显著）已在 4.4.3 规则化，LLM 只做其中的语义判定环节 |
| 安全敏感度 | 中 | 最坏情况是议题分错/漏分、首发源误判，影响分析质量而非人身安全；所有 LLM 输出（命名/首发判定）均可被人工改判并留痕，议程设置事件需人工复核确认后才正式告警 |
| 示例可用性 | 有 | 议题命名/分类有海量新闻标题可构造 few-shot；首发判定可用历史已知议程设置案例（如"新疆棉"类事件）构造评测集；组件生态成熟（BERTopic 7.8k★、bge-m3 18.9k★，2026-07-24 实测） |
| 云端 API 可行性 | 可行 | 云端 API 已验证：LLM 走讯飞星辰 MaaS（OpenAI 兼容 /chat/completions，生产并发上限 2），嵌入走 SiliconFlow bge-m3（1024 维，L2 归一化，RPM 2000 / TPM 500000，按 32 篇/批远低于限）；无需本地推理 GPU；机构不批准云通道时的极端降级兜底可启用本地 Qwen 分支（非默认） |

**技术路线可行性结论**：传统管线（跨语言向量 bge-m3 云端嵌入 + BERTopic 在线/增量聚类）负责"把文章聚成簇"这一重计算环节；**LLM（云端 API，讯飞星辰 MaaS）负责语义理解环节——议题命名、主题分类、重复议题归并、议题摘要、首发表述判定、终审**，替代自研分类器/命名规则的工程量，并显著提升输出可读性。LLM 与聚类解耦：LLM 不可用只损失"可读性与语义判定"，不损失"聚类与测量"主链路。

### 8.2 模型交互设计

- **模型角色**：后台分析引擎（非对话式 AI）。LLM 六个角色：议题命名器（簇内代表标题+top 词 → 可读议题名）、主题分类器（预置分类体系，支持部署方扩展）、议题归并器（判定重复/子议题，给出合并建议）、摘要生成器（议题 2–3 句中文摘要）、首发表述判定器（US-06/US-15：判定某人物/机构/媒体是否"首次提出"某提法）、**终审审查官**（US-06/US-16：议程设置事件判定后，LLM 扮演"高级情报审查官"评逻辑连贯性，1–10 分，<5 分自动降为疑似/驳回（REJECTED），≥5 分维持（COMPLETED）；被驳回的低价值样本作为负例积累，用于后续 prompt 与阈值优化）。传统组件角色不变：语言识别器（fastText lid.176）、语义向量化器（云端嵌入 API：SiliconFlow bge-m3 1024 维）、话题聚类器（BERTopic + Agglomerative 硬距离阈值聚类，见 4.4.5）、展示翻译器（argos-translate/LibreTranslate，离线）。
- **上下文来源**：命名/分类/归并输入 = 簇内代表标题 5–10 条 + c-TF-IDF top 词 + 议题关键词（≤2,000 token，估算）；首发表述判定输入 = 候选文章/讲话全文片段 + 该实体历史表述摘要（≤4,000 token，估算）；统计检验输入不变（AgendaSnapshot 日粒度显著性时间序列与共现矩阵，不走 LLM）。
- **Human-in-the-loop**：① 议题自动命名 → 用户可重命名（US-04，`name_auto` 留痕）；② 议题归并 → 系统建议、管理员确认；③ 议程设置事件 → 系统判定为"疑似"后必须人工复核才"确认"告警（US-06）；④ 首发表述判定 → 低置信度进人工确认队列（US-15）；⑤ 统计检验结论（Granger/QAP）→ 界面强制显示样本量与"统计关联≠因果"提示；⑥ 预警规则由人配置，系统不自动创设监控对象；⑦ **自我纠错自动修正 → 分析师可人工确认/否决，人工校正优先级高于机器**（US-16，全部写入 `revision_log`，否决即回滚）。

### 8.3 提示词策略概要

1. **结构化输出强制**：所有 LLM 调用要求 JSON Schema 输出（如议题命名：`{"name","name_zh","category","confidence"}`），解析失败自动重试 1 次后降级，不允许自由文本进入数据层。
2. **few-shot + 口径锚定**：议题命名给 3–5 个"好命名/坏命名"对照示例；主题分类在系统提示中固化分类体系定义与边界示例，防止分类漂移。
3. **判定留痕**：首发表述判定要求输出 `evidence_quote`（原文依据片段）与 `confidence`，无依据片段的判定结果直接丢弃进人工队列——可审计优先于召回率。
4. **语言策略**：分析层统一以原文 + 中文双语处理（多语言模型直接理解原文，避免翻译误差进入判定层）；展示层翻译仍走 argos-translate。
5. **降级链显式化**：LLM 每个角色都有声明式降级（见 8.5），降级状态写入 `naming_method`/`detection_method`/`cluster_method` 字段并上报告警，绝不静默降级。
6. **prompt 版本留痕与重跑**：每次 LLM 判定（命名/分类/归并/首发表述/终审评分）记录模型名与 prompt 版本号，随判定结果与 `revision_log` 持久化；prompt 更新后可对历史判定批量重跑对比，重跑导致的判定变化按 4.4.5 修正流程写入 `revision_log`（标注为 prompt 版本变更触发），保证全链路可审计、可复现。

### 8.4 评估标准

| 维度 | 评估方法 | 通过标准 |
|------|---------|---------|
| 聚类质量 | 人工抽验：每周随机 5 个议题 × 20 篇文章，研究员标注"归属是否正确"（李思远画像用户参与标注计划） | 簇内一致率 ≥ 80%（估算目标） |
| LLM 议题命名质量 | 自动命名盲评（研究员 5 分制，对比 c-TF-IDF 兜底命名） | 均分 ≥ 4.0，且显著优于兜底方案（估算目标） |
| LLM 主题分类准确率 | 人工标注 500 个议题对照预置分类体系 | 宏平均 F1 ≥ 0.80（估算目标） |
| 议题归并准确率 | 抽样 100 组合并建议人工复核 | 精确率 ≥ 85%（估算目标，宁缺毋滥） |
| 首发源判定准确率（US-06/US-15） | 构造 20 个已知议程设置历史案例（含"新疆棉"类事件）回放验证；上线后统计人工复核"误报反馈"率 | 首发国/源判定准确率 ≥ 80%；事件误报率 ≤ 20%（估算目标） |
| 跨语言匹配准确性 | 构造已知同事件多语言报道对（如重大国际事件的中/英/阿语报道），检验归入同一议题比例 | ≥ 70%（估算目标） |
| 显著性有效性 | 与 GDELT 主题声量排名做 Spearman 相关（外部基准） | ρ ≥ 0.7（估算目标；参照 Chapel Hill 研究 0.97 的经典量级，放宽至工程可达水平） |
| 情感属性准确性 | 抽样 200 篇/语种 × 5 语种人工标注对比 | 宏平均 F1 ≥ 0.65（估算目标，多语言情感为已知难点，GDELT 官方亦提示误差） |
| 统计检验稳健性 | 数据不足保护 + 结果复核：p 值、样本量、滞后窗全部展示 | 样本 <100 篇时系统拒绝输出检验结论（硬性规则） |
| 延迟（AI 链路贡献） | 向量化+聚类单篇耗时；LLM 单议题处理耗时 | 聚类 P95 ≤ 5s/篇；LLM（云端 API）P95 ≤ 10s/议题（估算目标，受并发 2 限制影响） |

### 8.5 失败降级

| 失败场景 | 降级策略 |
|----------|---------|
| **LLM 不可用**（云端 API 超时率 >20%/配额耗尽/网络断连） | **降级为 BERTopic c-TF-IDF 关键词标签兜底**：议题名 = top 词拼接 + 代表标题（`naming_method=ctfidf_fallback`）；主题分类/议题摘要暂停；议题归并退回向量相似度 >0.85 规则建议；首发表述判定暂停（`detection_method=media_time_fallback`，仅保留媒体时间锚点判定）；界面标注"LLM 降级中"，P1 告警；LLM 恢复后对降级期议题重新命名/分类回填 |
| **BERTopic 聚类不可用**（服务崩溃/模型文件损坏/内存不足） | 降级为**关键词匹配聚类**：用历史议题的 keywords 表 + 国家-主题词典做规则匹配，新文章归入最相似议题，无法匹配的入"未归类"池；`cluster_method=keyword_fallback`，界面标注"聚类降级中"，P1 告警；恢复后对降级期文章重新聚类回填 |
| 云端嵌入 API 不可用（bge-m3 /embeddings） | 降级为 fastText 语言识别 + 关键词 TF-IDF 粗聚类；跨国议题匹配暂停（标注"跨语言匹配暂不可用"） |
| fastText 不可用 | 回落到源默认语言标注，`language` 字段标记低置信 |
| 翻译服务（argos/LibreTranslate）不可用 | 界面显示原文 + 浏览器自带翻译提示；不阻塞任何核心功能 |
| LLM 输出不合规（JSON 解析失败/缺 evidence_quote） | 自动重试 1 次 → 仍失败则该次调用按"LLM 不可用"单点降级，不阻塞管线 |
| LLM 终审不可用（终审审查官调用失败/超时） | 议程设置事件判定跳过终审环节，直接进人工复核队列（不自动告警），事件标注"终审暂不可用"；LLM 恢复后对跳过终审的疑似事件补审 |
| 聚类输出质量低（簇内一致率抽检 <60% 或单议题文章数暴涨 >10 倍均值） | 自动冻结该议题增量归入 → 人工复核队列；防止坏簇污染显著性排名 |
| 统计检验计算超时（>5 min） | 跳过当次刷新保留上一版结果，下周期重试；连续 3 次失败告警 |
| 全文抽取失败（trafilatura + readability 均失败） | 标题+摘要入管线，`content_status=partial`；可见性红线优先，不阻塞入库 |
